## 0. 先建立心智模型

PPO 训练做的事，一句话：

> **不断试错，把"奖励高的动作"概率调大。**

所以出问题时，永远先问**两个问题**：

| 问题 | 如果答案是"否" | 后果 |
|---|---|---|
| **奖励函数是否真的在奖励我想要的行为？** | 策略会学出你没想到的怪招 | 奖励设计错误 |
| **策略有没有"不做正事也能拿高分"的退化解？** | 策略一定选退化解 | **奖励作弊** |

第 2 条是新手最容易忽略的。我在这个项目上就踩了：加的相位奖励机制**完全正确**，但策略发现"原地踏步刷满它"比"真的往前走"更划算 —— `cmd=0` 时它倒退 0.20 m/s。

**记住：策略不道德，只优化数字。** 只要作弊路径的收益 ≥ 正解路径，它一定作弊。

## 2. 动手跑第一次

```bash
# ① 激活环境（每个新终端都要做一次）
source $RLCAT_ROOT/scripts/env.sh

# ② 确认物理正常（应当只有足端球着地、机身 ~0.13 m）
cd $RLCAT_ROOT
python scripts/03_stand_test.py --urdf robot_sim.urdf --stiffness 20 --damping 0.5

# ③ 先训站立，约 1 分钟
bash scripts/run_train.sh rlcat_stand --num_envs 2048 --max_iterations 300

# ④ 再训行走，约 8 分钟
bash scripts/run_train.sh rlcat --num_envs 2048 --max_iterations 1500

# ⑤ 验收
python scripts/07_eval.py --task rlcat --num_envs 32 --seconds 15 \
    --speeds="-0.3,0.0,0.2,0.3,0.5"

# ⑥ 看它走
python scripts/12_play.py
```

**训练速度参考**（RTX 4060 Laptop 8GB）：2048 环境下达 **12~19 万 steps/s**，一次迭代 0.25~0.45 秒，1500 迭代约 **8 分钟**。

## 3. 看懂训练日志

每次训练会实时打印，同时存到 `logs/rlcat_<时间戳>.log`：

```
                       Computation: 145308 steps/s (collection: 0.265s, learning 0.073s)
               Value function loss: 0.0857        ← critic 准不准，下降是好事
                    Surrogate loss: -0.0033       ← PPO 的策略损失
             Mean action noise std: 1.00          ← 探索强度，收敛时会下降
                       Mean reward: 30.12         ← 整个 episode 的累计回报 ⭐
               Mean episode length: 2002.00       ← episode 步数 ⭐⭐ 见下方警告
      Mean episode rew_action_rate: -0.1726       ← 下面每项都是【每秒】贡献
       Mean episode rew_ang_vel_xy: -0.2018
      Mean episode rew_base_height: -0.0616
        Mean episode rew_collision: -0.0859
          Mean episode rew_dof_acc: -0.6810
       Mean episode rew_gait_phase: 0.4170
 Mean episode rew_tracking_lin_vel: 2.3522        ← 任务奖励，应当占主导
```

### ⚠️ 单位别搞混

| 指标 | 单位 |
|---|---|
| `Mean reward` | **整个 episode 的累计回报**（20 秒的总和） |
| `Mean episode length` | episode 步数（满值 = `episode_length_s / dt` = 2002） |
| `Mean episode rew_xxx` | **每秒**的贡献（× 20 s = 该 episode 的总贡献） |

验算：`rew_tracking_lin_vel 2.35` × 20 s ≈ 47，减去各项惩罚约 29，得 `Mean reward ≈ 30`。

### ⚠️⚠️ 最重要的一条：**看 reward 必须同时看 episode length**

`Mean reward` 在不同 episode 长度下**不可比**。机器人早摔 → episode 短 → 惩罚累积少 → reward 可能反而"好看"。

**判断标准**：
```
episode length 接近满值（2002）  → reward 可直接横向比较
episode length 明显下降         → 先别比 reward，这是【训练变差】的信号
```

本项目的真实案例：第 8 轮把 `tracking_lin_vel` 提到 6.0，末期 reward 看起来还行，但 **episode length 掉到 891** —— 实际是开始摔了，比之前差得多。

## 5. 调参方法论（**最重要的一节**）

### 铁律 1：一次只改一个变量

我在这个项目上跑了 9 轮。第 4 轮同时改了「对称化 URDF + 刚度 40 + base_height 权重」，结果变差了 —— **完全无法归因**，这一轮白跑。

```
改 1 个变量 → 结果变好/变坏  → 知道是这个变量的功劳/锅
改 3 个变量 → 结果变了        → 什么都不知道
```

### 铁律 2：验收必须用**固定指令**单独测，不能只看训练日志

训练日志里的 `tracking_lin_vel` 是所有指令的**平均值**，会被"小指令容易跟"稀释。

真实案例（第 6 轮）：
```
训练日志: rew_tracking_lin_vel 原始值 0.868   看起来很好
固定指令实测: cmd=0.3 时实际只走 -0.068 m/s  → 根本没在走！
```
因为很多指令接近 0，机器人原地站着也能拿到不错的平均分。

```bash
# 永远用这个来验收
python scripts/07_eval.py --task rlcat --num_envs 32 --seconds 15 \
    --speeds="-0.3,0.0,0.2,0.3,0.5" --load_run <run名> --checkpoint <N>
```

### 铁律 3：每轮都保留，用 run 名区分

`save_interval = 25` 意味着每 25 迭代存一个检查点。别删 —— 崩溃时用来回退，调参时用来对比。

### 铁律 4：奖励权重的绝对值要和**任务奖励量级**匹配

看第 9 轮的最终平衡（每秒贡献）：

```
任务奖励    tracking_lin_vel  +2.35   ← 必须占主导
            gait_phase        +0.42
            tracking_ang_vel  +0.09

惩罚项      dof_acc           -0.68   ← 最大的一项惩罚
            ang_vel_xy        -0.20
            action_rate       -0.17
            lin_vel_z         -0.12
            collision         -0.09
            base_height       -0.06
            ...
```

**判断法则**：所有惩罚加起来不该超过任务奖励的 ~5 倍。如果惩罚总和是任务奖励的 20 倍，策略会选"什么都不做"（第 3 轮就是这样：tracking 掉到 0.17）。

## 6. 逐参数详解（含实测可用区间）

### 6.1 `tracking_sigma` —— 跟踪奖励的宽容度 ⭐ 影响最大

**定义**：`tracking_reward = exp(-误差² / sigma)`

| sigma | 效果 |
|---|---|
| 大（0.5） | 奖励曲线平缓，大误差也能拿不错的分 → **策略欠响应** |
| 小（0.1） | 奖励曲线陡峭，大误差迅速掉到 0 → **策略被逼着精确跟踪** |

**本项目实测**：
```
sigma = 0.25 -> 速度增益只有 0.58（cmd 0.3 只走 0.144）  ❌
sigma = 0.10 -> 速度增益 0.87（cmd 0.3 走 0.239）        ✅ 全部验收达标
```

**什么时候调它**：跟踪误差偏大、且不是"不跟"而是"跟不足"（欠响应）时。

```python
class rewards(LeggedRobotCfg.rewards):
    tracking_sigma = 0.10     # 0.25 → 0.10
```

> 💡 这是本项目**性价比最高的一个参数**：只改一个数，增益从 0.58 提到 0.87。

### 6.2 `feet_air_time_target` —— 目标抬脚滞空时间 ⭐ 尺度匹配问题

**背景**：upstream 在奖励函数里**硬编码**了 0.5 秒。我们的覆写版把它变成可配置。

**为什么必须改**：0.5 s 是给几十 kg、腿长半米的 anymal/a1 调的。RL-CAT 腿长只有 0.14 m，自然摆动相约 0.12~0.15 s。用 0.5 s 会让 `(滞空时间 - 0.5)` **恒为负 —— 等于在惩罚抬脚**。

**实测后果**：策略学会"永远不落地"，右后腿触地占空比 **0.00**，靠两条腿蹦。

```
feet_air_time_target = 0.5   -> 占空比 [0.74, 0.003, 0.00, 0.31]  两条腿蹦
feet_air_time_target = 0.15  -> 占空比 [0.41, 0.19, 0.38, 0.32]   均衡小跑 ✅
```

**怎么估**：`摆动相 ≈ 0.5 × 腿长 / 速度`。腿长 0.14 m、速度 0.3 m/s → 约 0.23 s；取一半保守值 0.15 s。

### 6.3 奖励权重 `scales.*`

**实测可用区间**（这是本项目最宝贵的经验之一）：

| 参数 | 值 | 结果 |
|---|---|---|
| `tracking_lin_vel` | 1.0 | ❌ 被辅助奖励偷走主导权 → 策略原地踏步刷相位奖励 |
| | **3.0** | ✅ **可用（最终采用）** |
| | 6.0 | ❌ 破坏稳定性 → episode 从 2002 掉到 891 |
| `feet_airborne`（反蹦跳） | 0 | ✅ 关闭（最终） |
| | -0.6 | 🟡 轻微有效 |
| | -2.0 | ❌ 策略直接放弃任务，tracking 掉到 0.17 |
| `base_height` | -3.0 | ✅ 可用（配合绝对偏差版） |

**结论：奖励权重的可用区间很窄，而且两头都会坏。** 每次只动 1 个，幅度别超过 2 倍。

### 6.4 `base_height` 的形式（在 rlcat_env.py 里）⭐ 形状比权重更重要

原版是**平方**误差：
```python
torch.square(base_height - target)      # ❌ 目标附近梯度趋零
```
实测：机身掉到 0.102 m（目标 0.13），误差 0.028，平方后只有 0.0008 → 乘 -3.0 只有 **-0.0024**，完全压不住。

改成**绝对偏差**：
```python
torch.abs(base_height - target)         # ✅ 整个区间梯度恒定
```

**这条通用经验**：想让某个量被"钉在目标附近"，用**绝对值**；想惩罚"偶尔的大偏离"，用**平方**。用错了就是"惩罚看着有、实际不起作用"。

### 6.5 `stiffness` / `damping` —— 关节 PD 增益

**怎么定**：从"能站住的最小值"试起。用扫描脚本一次看一组：

```bash
python scripts/03_stand_test.py --urdf robot_sim.urdf --sweep --seconds 4
```

输出（实测）：
```
stiffness=20.0 damping=0.50 -> base_z=0.1327  roll=-0.28  pitch=-2.45   ← 最好
stiffness=20.0 damping=1.00 -> base_z=0.1206  roll=-0.07  pitch=-5.41
stiffness=30.0 damping=1.00 -> base_z=0.1288  roll=-0.26  pitch=-4.04
stiffness=40.0 damping=1.50 -> base_z=0.1266  roll=-0.21  pitch=-5.03
stiffness=60.0 damping=2.00 -> base_z=0.1298  roll=-0.30  pitch=-3.61
```

**经验关系**：`damping ≈ stiffness / 20 ~ stiffness / 40`

### 6.6 `num_envs` —— 只影响速度，不影响结果

| 值 | 显存 | 用途 |
|---|---|---|
| 64 | 很小 | 只验证"能不能起来"（`--max_iterations 3`） |
| 512 | ~1.5 GB | 快速试验 |
| **2048** | ~3.5 GB | **标准训练**（8 GB 显存的安全值） |
| 4096 | ~6 GB | 可能吃紧，注意观察 |

改它**不影响学习结果**，只影响每个 iteration 的采样量。所以调参时用小值快速筛，最终训练用 2048。

### 6.7 PPO 超参

大多数情况**先用默认值**。真要动的话：

| 参数 | 默认 | 什么时候动 |
|---|---|---|
| `learning_rate` | 1e-3 | 训练震荡/崩溃时降到 3e-4 |
| `schedule` | `'adaptive'` | 配合 `desired_kl` 自动调学习率。**别改成 fixed**，除非你知道为什么 |
| `desired_kl` | 0.01 | 训练不稳时降到 0.005 |
| `num_steps_per_env` | 24 | 增大 → 梯度更稳但更慢 |
| `entropy_coef` | 0.01 | 策略过早收敛/探索不足时调大 |

**本项目实测**：PPO 默认值一直能用，9 轮里没改过。**问题几乎总在奖励侧，不在优化器侧。**

## 7. 诊断手册：症状 → 处方

| 症状 | 最可能的原因 | 处方 |
|---|---|---|
| **原地不动 / 干脆不走** | 惩罚总和 >> 任务奖励 | 减小惩罚权重，或提高 `tracking_lin_vel` |
| **原地踏步刷某个奖励** | **奖励作弊** | 问"不做正事能不能拿满它？"→ 按任务量**门控**该奖励 |
| **跟不足（欠响应）** | `tracking_sigma` 太大 | 调小（0.25 → 0.10） |
| **两条腿蹦 / 某条腿永不落地** | `feet_air_time_target` 尺度不匹配 | 按腿长估真实摆动相，调小 |
| **训练中途突然崩（reward 变巨大负数）** | 平方惩罚无界增长 | 给所有平方项加 `torch.clamp` |
| **机身高度不对但惩罚很小** | 用了平方形式，梯度趋零 | 改绝对偏差 |
| **步态左右不对称** | ①URDF几何不对称 ②缺步态结构约束 | ①对称化 URDF ②加相位奖励（必须门控！） |
| **起步就摔** | PD 增益不足 / 动作尺度太大 | 先跑 `03_stand_test.py`；降 `action_scale` |
| **episode 越来越短** | 训练在变差 | 看是不是某个惩罚权重过大；降学习率 |
| **所有指标都不动** | 学习率太低 / 观测有问题 | 检查观测维度是否和 `num_observations` 一致 |
| **显存不足 OOM** | `num_envs` 太大 | 降到 1024 |

### 三个真实的诊断案例（来自本项目）

**案例 A：训练在第 681 迭代突然崩溃，reward 掉到 -45533**
```
排查：看分项 → base_height 惩罚冲到 -2417，lin_vel_z -277
诊断：机器人被弹飞 → 平方惩罚无界增长 → 天量优势值摧毁策略
处方：所有平方项加 torch.clamp(...) 截断
```

**案例 B：机器人不走路，原地踏步**
```
排查：固定指令实测 → cmd=0.3 实际 -0.068（倒退）
诊断：相位奖励每步 +1.08，且不门控 → "原地踏步"是最优解
处方：rew *= clamp(|cmd|/0.3, 0, 1)  +  tracking_lin_vel 1.0 → 3.0
```

**案例 C：跟踪误差 0.13，但训练日志显示 tracking 0.845"很好"**
```
排查：固定指令实测 → 速度增益只有 0.58（欠响应）
诊断：tracking_sigma=0.25 太平缓，大误差也不怎么扣分
处方：tracking_sigma → 0.10，增益提到 0.87，全部达标
```

## 8. 实战模板：一次完整的调参循环

假设你想试试"提高机身高度"（当前 0.112，目标 0.13）。

```bash
source $RLCAT_ROOT/scripts/env.sh
cd $RLCAT_ROOT

# ---------- 步骤 1：先记录基线（改之前必须测一次！）----------
python scripts/07_eval.py --task rlcat --num_envs 32 --seconds 15 \
    --speeds="-0.2,0.0,0.2,0.3,0.5" --load_run Oct06_03-32-41_ --checkpoint 500 \
    > /tmp/baseline.txt 2>&1
grep -E "^ +[0-9-]" /tmp/baseline.txt

# ---------- 步骤 2：只改一个参数 ----------
#  编辑 ~/legged_gym/legged_gym/envs/rlcat/rlcat_config.py
#  base_height: -3.0  ->  -6.0
nano ~/legged_gym/legged_gym/envs/rlcat/rlcat_config.py

# ---------- 步骤 3：先跑 3 个迭代确认没写错 ----------
cd $RLCAT_LEGGED_GYM
python legged_gym/scripts/train.py --task=rlcat --headless --num_envs 64 --max_iterations 3 \
    2>&1 | grep -E "rew_|Traceback|Error"
cd $RLCAT_ROOT
```

## 9. 怎么加一个新的奖励项

以本项目的 `gait_phase` 为例，完整三步：

**① 在 `rlcat_env.py` 里写函数**（名字必须是 `_reward_<你在 scales 里的键名>`）：
```python
def _reward_gait_phase(self):
    if self.phase_sign is None:
        return torch.zeros(self.num_envs, device=self.device)
    s = torch.sin(2.0 * math.pi * self.phase).unsqueeze(1)
    want = torch.sign(s) * self.phase_sign.unsqueeze(0)
    contact = (self.contact_forces[:, self.feet_indices, 2] > 1.0).float()
    actual = contact * 2.0 - 1.0
    rew = torch.mean(want * actual, dim=1)
    # ⚠️ 门控！否则策略会"原地踏步刷分"
    cmd_mag = torch.norm(self.commands[:, :2], dim=1)
    return rew * torch.clamp(cmd_mag / 0.3, 0.0, 1.0)
```

**② 在 `rlcat_config.py` 的 `scales` 里给权重**：
```python
class scales(LeggedRobotCfg.rewards.scales):
    gait_phase = 1.0
```

**③ 先跑 3 个迭代，确认新项出现在日志里**（legged_gym 靠名字自动匹配，名字写错会静默不生效）：
```bash
python legged_gym/scripts/train.py --task=rlcat --headless --num_envs 64 --max_iterations 3 2>&1 | grep gait_phase
```

**注意事项**：
- 权重设为 **0** 就等于关闭（legged_gym 会跳过它），不用删代码
- 新项的形状、量级要和现有项可比（先跑一次看日志里的数值）
- **加完必须问自己：有没有"不做正事也能拿满它"的退化解？**

## 10. 常见错误清单

| 错误 | 现象 | 正确做法 |
|---|---|---|
| 忘了 `source scripts/env.sh` | `ModuleNotFoundError: isaacgym` | 每个新终端先 source |
| 训练没加 `--headless` | 慢一倍，还可能报错 | `run_train.sh` 已默认加上 |
| 同时改多个参数 | 无法归因 | **一次一个** |
| 只看训练日志的 reward 就下结论 | 被平均值骗（第 6 轮） | 必须用固定指令验收 |
| 改完 reward 没跑小规模冒烟测试 | 名字写错 → 静默不生效 | 改完先跑 `--max_iterations 3` |
| 看 reward 不看 episode length | 早摔反而显得分高 | 两者一起看 |
| 用 `ls -t \| head -1` 选 run | 冒烟测试的垃圾目录会排在前面 | 按检查点数量筛选（步骤 5 有命令） |
| `--speeds "-0.3,..."` | argparse 报 `expected one argument` | 用 `--speeds="-0.3,..."` |
| 改 `decimation` / `action_scale` | 和固件的接口对不上了 | 这两个别动，是**固件契约** |
| 删掉旧 run | 崩溃时无法回退 | 全留着，用 run 名区分 |
| 期望一次就调好 | 我跑了 9 轮 | 预留半天到一天 |

## 11. 什么时候该停下来问

碰到下面这些，先别自己硬扛 —— 它们通常是**结构性问题**，不是调参能解决的：

- **站立都站不住**（`rlcat_stand` 训不出来）→ 物理/资产有问题，回阶段 0/1
- **所有参数都试过还是不走** → 观测或动作接口可能有 bug（检查 `num_observations` 是否真的等于 `compute_observations` 拼出来的维度）
- **训练几轮都是同一个怪招** → 奖励结构缺了关键约束，需要新增奖励项而不是调权重
- **数值爆炸（reward 出现 1e4 量级）** → 有未截断的项，或者 PD 增益/时间步不对
