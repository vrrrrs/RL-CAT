## 2. 环境搭建（P1）

### 2.1 起点

交接文档没有交代：本机其实**已经有** Isaac Gym（`~/isaacgym_ws/isaacgym`）和 conda 环境 `isaacgym`（Python 3.8.20 + torch 1.12.1+cu113），但**从未被真正跑通过**。没有 legged_gym、没有 rsl_rl、没有 git、没有 C++ 编译器。

### 2.2 踩到的 5 个坑（全部在无 sudo 条件下解决）

| # | 症状 | 根因 | 解决 |
|---|---|---|---|
| 1 | `ModuleNotFoundError: No module named 'isaacgym'`（其实是 import 报错） | 系统 python 没装；要用 conda 环境 | `conda activate isaacgym` |
| 2 | `AttributeError: module 'numpy' has no attribute 'float'` | **isaacgym 自己的 `torch_utils.py:135` 用了 numpy 1.24 已移除的别名** | [scripts/06_patch_isaacgym_numpy.py](scripts/06_patch_isaacgym_numpy.py)（1 行补丁，全仓库仅此 1 处） |
| 3 | `Command '['which', 'c++']' returned non-zero` | 系统**没有任何 C++ 编译器**，而 gymtorch 需要 JIT 编译 | `conda install -c conda-forge gxx_linux-64=10 gcc_linux-64=10`（无需 sudo） |
| 4 | `fatal error: crypt.h: No such file or directory` | conda 的 sysroot 里没有 `crypt.h`（glibc 2.28+ 拆到 libxcrypt） | `conda install -c conda-forge libxcrypt` + `CPATH=$CONDA_PREFIX/include` |
| 5 | `ModuleNotFoundError: No module named 'tensorboard'` | rsl_rl 的 runner 导入它 | `pip install tensorboard` |

**另外两件容易误判的事：**

- `nvidia-smi` 第一次调用报"找不到驱动"，但随后就正常了 —— 这是笔记本 dGPU 的运行时电源管理，**不是环境坏了**，重试即可。
- **`use_gpu_pipeline=True` 时调用 `get_actor_rigid_body_states` 会直接报 CUDA illegal memory access**（不是普通异常，看起来像环境崩了）。这是 API 用法违规：训练代码必须走 tensor API（legged_gym 本来就是），调试脚本则设 `use_gpu_pipeline=False`。

**统一入口**：[scripts/env.sh](scripts/env.sh) 把上述所有环境变量收在一起，所有脚本先 `source` 它。

### 2.3 版本锁定（关键）

```
legged_gym   master 分支（重构版：LeggedRobot 继承 BaseTask，不是老版的 VecEnv）
rsl_rl       v1.0.2   ← README 明确要求，用 master 会 API 不匹配
```
动手前已逐项比对过 6 个接口契约（`OnPolicyRunner.__init__` / `load` / `learn` / `ActorCritic` / env 属性 / `reset` 返回值），**全部吻合**。

### 2.4 a1 冒烟测试（必做的前置验证）

```
python legged_gym/scripts/train.py --task=a1 --headless --num_envs=512 --max_iterations=5
→ 25100 steps/s，PPO 正常迭代
```
先证明"训练栈本身没问题"，再换自己的机器人 —— 否则出问题分不清是框架还是配置。

## 3. 资产改造（P2）

原 [urdf/robot.urdf](urdf/robot.urdf) **一字未动**，改动全部体现在生成物 [urdf/robot_sim.urdf](urdf/robot_sim.urdf)，生成器：[scripts/05_make_sim_urdf.py](scripts/05_make_sim_urdf.py)。

### 3.1 三处改动

**1. 放宽 `*_thigh` 限位：30° → 90°**
> 交接文档把这条标为「🔴 阻塞：站立需要 +31.19° > 上限 +30°」，**这是误判** —— 文档混淆了「大腿连杆相对竖直的绝对夹角」和「关节相对 CAD 零位的转角」。既然 q=0 就是装配好的站立姿态，站立时 thigh 关节角 = 0，离上限还有 30° 余量。实测机器人确实站得住。放宽纯粹是为了给摆腿留空间。

**2. 碰撞体：STL 三角网格 → 基本几何体**

实测发现 **visual 和 collision 网格几何完全相同**（同为 618/642 顶点、同最低点），即原碰撞体就是全精度三角网格，2048 环境下会拖垮 PhysX。

| link | 新碰撞体 | 依据 |
|---|---|---|
| `base_link` | box `(164.0, 130.5, 68.0) mm` | 机身本来就是方块状 |
| `*_hip` / `*_thigh` | capsule（沿连杆轴数据拟合） | 细长连杆 |
| `*_calf` | **sphere r=9 mm（足端橡胶球）+ capsule（小腿本体）** | 真机足端是 9 mm 橡胶球 |

**足端球坐标**（在各自 calf 坐标系，球底面与网格最低点重合）：

| link | origin xyz |
|---|---|
| `lf_calf` | `0.071332 -0.079404 0.012500` |
| `lb_calf` | `0.075518 -0.074932 0.012500` |
| `rf_calf` | `0.072495 -0.078210 -0.004500` |
| `rb_calf` | `0.077654 -0.072452 -0.004500` |

> ⚠️ 这些坐标不能凭直觉填「(0,0,腿长)」：本项目的 link 坐标系没对齐连杆方向（小腿网格在自身系里沿 (x,−y) 对角线延伸）。
> ⚠️ 更关键的是**必须在「站立姿态的 base 系」里找网格最低点再变换回 link 系** —— 直接在 link 系里取 argmin(z) 会选到另一个顶点，球就放偏了（我第一版就是这么错的，自检脚本抓了出来）。

**3. 修掉 CAD 导出的左右不对称**

实测原始 URDF 有两处 1.5 mm 的导出误差，会给策略系统性偏置：
```
lf_hip   origin x : 0.0395  ->  0.041     （其他三个髋是 ±0.041）
lf_thigh origin z : 0.0586  ->  0.0571    （其他三个大腿是 ±0.0571）
```
用右侧腿的值镜像修正。

### 3.2 实测验收

| 项 | 结果 |
|---|---|
| 解析自检：所有碰撞体是否低于足端 | ✅ 无（否则机器人会"浮"在盒子上） |
| 站立高度（stiffness 20 / damping 0.5） | **0.1327 m** |
| 触地刚体 | ✅ **只有 4 个足端球**（接触力合计 ≈13.6 N = 1.386 kg 重力） |
| `base_height_target` | **0.13**（换碰撞体前后几乎一致：网格 0.130 → 胶囊 0.129） |

**踩坑记录**：第一版对细长连杆用了轴对齐 AABB box，太"胖"，实测机器人**塌掉**（机身从 0.130 掉到 0.068，四条大腿同时触地）。改用沿轴数据拟合的胶囊体后恢复正常。

## 4. 训练环境（P3）

配置：[rlcat_config.py](~/legged_gym/legged_gym/envs/rlcat/rlcat_config.py)（绝对路径 `$RLCAT_LEGGED_GYM/legged_gym/envs/rlcat/rlcat_config.py`）
覆写：[rlcat_env.py](~/legged_gym/legged_gym/envs/rlcat/rlcat_env.py)

### 4.1 观测：方案 C，47 维（用户拍板）

顺序**刻意对齐交接文档 §12**，这样固件侧拼接顺序不用改：

```
 0- 2  重力向量（IMU 姿态反算）      3
 3- 5  机身角速度（陀螺）            3   ← 陀螺仪在这里，四个方案都有，不是可选项
 6- 8  速度指令                      3
 9-20  关节位置（相对 q_default）    12
21-32  关节速度                      12
33-44  上一帧动作                    12
45-46  步态相位 sin/cos              2   ← 内部时钟，真机无需任何传感器即可复现
                                     ──
                                     47
```
> C 方案 = 交接文档 50 维设计的**前 47 维**。文档里那 3 个「保留维」将来想加，直接往后接，已有顺序一字不动。

**legged_gym 原生 48 维里那 3 维机身线速度被删掉了** —— 真机没有这个传感器，策略一旦依赖它 sim-to-real 必崩。

**量纲**：角速度 ×0.25、关节速度 ×0.1（⚠️ upstream 默认 0.05，已按交接文档改成 0.1）、关节位置 ×1.0、动作裸输出。

### 4.2 四处必要覆写（不写就跑不起来 / 跑不对）

| # | 覆写 | 为什么必须 |
|---|---|---|
| 1 | `_reset_dofs` | 父类是 `default_dof_pos * rand(0.5,1.5)`；我们的默认姿态**全是 0**，`0 × rand = 0`，等于**每个 episode 都从精确站立姿态出发、毫无初始随机化**（a1 默认姿态非零所以没这问题） |
| 2 | `_get_noise_scale_vec` | 父类按它自己的 48 维布局逐段硬编码下标，我们是 47 维，下标全变 |
| 3 | `compute_observations` | 方案 C 的布局与相位时钟 |
| 4 | `_reward_feet_air_time` | upstream 把目标滞空时间**硬编码 0.5 s**，那是给几十 kg 的 anymal/a1 调的（详见 §6.1） |

### 4.3 关键配置

| 项 | 值 | 依据 |
|---|---|---|
| `default_joint_angles` | 全 0 | ✅ 实测 q=0 就是站立姿态 |
| `action_scale` | 0.25 | 与交接文档 §12 一致 |
| `decimation` | 2（sim dt=1/200 → **100 Hz**） | 对齐固件 |
| `foot_name` | `"calf"` | **URDF 没有独立足端 link**（13 刚体里没有 foot），只能用小腿充当 |
| `penalize_contacts_on` | `["thigh"]` | 必须把 calf 从惩罚里删掉，否则"一边用小腿当脚、一边惩罚小腿触地" |
| `terminate_after_contacts_on` | `["base_link"]` | 我们的根刚体叫 base_link（不是 a1 的 base） |
| `terrain.mesh_type` | `plane` | 先平地 |
| `commands.lin_vel_x` | `[-0.3, 0.5]` | 机身仅 200 mm，1 m/s 太激进 |

> ⚠️ 训练侧**不需要关节顺序映射**：legged_gym 用 `default_joint_angles[name]` 按名字查表，顺序自动处理。只在导出到固件时需要对一次表：`A2C = [3,0,9,6,4,1,10,7,5,2,11,8]`。

### 5.2 P5：训行走 —— 一共跑了 8 轮，这是完整记录

| 轮 | 配置变化 | 结果 | 结论 |
|---|---|---|---|

| 2 | 目标改 0.15 s；新增 `feet_air_excess`；`base_height` 改绝对偏差；加截断 | **稳定不发散**，tracking 0.77，reward −6.7 | ✅ 可用 |

### 5.3 第 5 轮结果（隔离实验：只改对称化 URDF）

**配置**：完全等于第 2 轮，唯一变量 = 对称化 URDF。

```
运行目录: ~/legged_gym/logs/rlcat_flat/Oct06_02-36-37_/
最佳检查点: model_500.pt   (iter 494)
跟踪奖励 0.845（历轮最高）    episode 长度 2002（20 s 全程不摔）
全程稳定，无发散            训练 1000 迭代 / 367 秒
```

**保留 checkpoints**：`model_0.pt` ~ `model_1000.pt`，每 25 迭代一个。

> 对称化并没有解决步态不对称（见 §7）—— 说明不对称主要来自**奖励设计**（策略主动选择了一个对角不均的解），不是 URDF 的 1.5 mm 几何偏差。但对称化本身是对的，保留。

### 5.4 第 6 轮：加显式 trot 相位约束

见 §8.1 的思路 1。观察到的策略主导接触频率约 6 Hz（对应腿周期 ~3 Hz），因此把相位时钟频率从 1.5 Hz 调到 **3.0 Hz**，并新增 `gait_phase` 奖励（权重 +1.5），同时把 `feet_air_time` 从 3.0 降到 1.0 让位。

相位符号在运行时按足端名字自动推导，实测输出：
```
[rlcat] 足端顺序     = ['lb_calf', 'lf_calf', 'rb_calf', 'rf_calf']
[rlcat] trot 期望相位 = [-1.0, 1.0, 1.0, -1.0]
```
即 **lb + rf 同相、lf + rb 同相** —— 标准对角小跑配对，推导正确。

**结果：成败参半 —— 而且失败的方式很有意思：**

| 指标 | run 5（无相位奖励） | **run 6（有相位奖励）** | 变化 |
|---|---|---|---|
| 平均回报 | −7.35 | **+25.12** | 大幅提升 |
| 跟踪奖励 | 0.845 | **0.868** | 略升 |
| 左右占空比差（对称性） | 0.36 ~ 0.59 | **0.076 / 0.016** | ✅ **改善 10~30 倍** |
| 触地占空比 | `[0.71, 0.03, 0.13, 0.47]` | `[0.48, 0.23, 0.47, 0.30]` | 四条腿负担接近均衡 |
| **实际速度跟踪** | `v ≈ 0.7·cmd + 0.05` | **`v ≈ 0.5·cmd − 0.20`** | ❌ **崩了** |

**相位奖励确实修好了对称性**（这是根因层面的修复），但同时触发了**奖励作弊**：

```
cmd = 0.0 m/s  ->  实际 −0.196 m/s（倒退！）
cmd = 0.3 m/s  ->  实际 −0.068 m/s（还是倒退）
cmd = 0.5 m/s  ->  实际 +0.055 m/s（只到指令的 11%）
```

策略发现**「原地踏步把相位奖励刷满」比「真的往前走」更划算**：相位奖励每步能给 +1.08，而跟踪奖励最多 +1.0，且移动本身还要付出力矩、加速度、碰撞等惩罚。

**修复**（run 7）：把相位奖励**按指令强度门控**（`rew *= clamp(|cmd|/0.3, 0, 1)`，零指令时不给），并把 `tracking_lin_vel` 权重从 1.0 提到 **3.0**，让"真的走起来"重新占主导。

### 5.5 第 7 轮：修好作弊之后的最终交付模型

```

最佳检查点: model_500.pt   (iter 485)
平均回报 +31.92（历轮最高）   跟踪奖励原始值 0.891（历轮最高）
```

| 指标 | run 5 | run 6 | **run 7** |
|---|---|---|---|
| 跟踪误差 @0.0 / 0.2 / 0.3 | 0.113 / 0.117 / 0.130 | 0.128 / 0.251 / 0.302 | **0.083 / 0.134 / 0.162** |
| 左右占空比差（对称性） | 0.36 ~ 0.59 ❌ | 0.076 / 0.016 ✅ | **0.10~0.12 / 0.03~0.05** ✅ |
| 机身高度 | 0.098 | 0.109 | **0.112** |
| 摔倒 | 0 | 0 | 0 |

**run 7 是三个维度的最佳折中**：对称性和 run 6 同档，跟踪比 run 6 好一倍。

### 5.6 第 8 轮：继续压"欠响应"

run 7 的速度增益仍只有 **0.58**（cmd 0.3 → 实际 0.144），是典型的欠响应。把 `tracking_lin_vel` 从 3.0 再提到 **6.0**、`gait_phase` 从 1.5 降到 1.0，训练 1500 迭代。

结果：**失败**。`tracking_lin_vel = 6.0` 把任务奖励压得太极端，训练后半段 episode 长度掉到 **891 步**（开始摔），跟踪原始奖励反而降到 0.27。

**这条也印证了 §6.3 的规律**：任务奖励权重不是越大越好，**过头会连稳定性一起破坏**。3.0 是可用的，6.0 不行。

### 5.7 第 9 轮：锐化跟踪奖励，一举修好欠响应 ⭐ 最终交付

**只改一个变量**：`tracking_sigma` 从 0.25 → **0.10**（跟踪奖励 `exp(-err²/sigma)` 对误差更敏感，大误差的惩罚急剧加重）。`tracking_lin_vel` 恢复 run 7 的 3.0。

### 5.8 九轮实验的完整结论

## 6. 训练中发现的问题与修复（这部分是本报告技术含量最高的地方）

### 6.1 `feet_air_time` 的尺度不匹配 —— 策略因此学会了"永远不落地"

legged_gym 在奖励函数里把目标滞空时间**硬编码成 0.5 s**：

```python
rew_airTime = torch.sum((self.feet_air_time - 0.5) * first_contact, dim=1)
```

**这个 0.5 s 是给 anymal/a1 调的**（几十 kg、腿长半米、摆动相 ~0.3 s）。
RL-CAT 腿长只有 0.14 m、1.386 kg，按步幅 ≈0.5L、速度 0.3 m/s 估算，摆动相只有 **0.12~0.15 s**。

于是 `air_time - 0.5` **恒为负** —— 这个奖励在**惩罚抬脚**。

**实测后果**（第 1 轮的步态分析）：策略发现"把两条腿永久抬着、用另外两条蹦"是局部最优，因为一直不落地的脚**既拿不到奖励也不受罚**：

```
触地占空比 = [0.74, 0.003, 0.00, 0.31]     ← 右后腿一次都没落地
机身高度 max = 0.202 m                      ← 站立才 0.13，它在跳
```

**修复**（两处）：
1. 目标滞空时间改成从配置读，设为 **0.15 s**
2. 新增 `_reward_feet_air_excess`：显式惩罚"滞空超过目标两倍"的脚，**堵死"永远不落地"这个漏洞**（并 clamp 到 0.5 让惩罚有界）

### 6.2 训练在第 681 迭代崩溃 —— 平方惩罚的无界增长

```
 iter 650:  reward   8.41   ep_len 2002   ← 一切正常
 iter 681:  reward -50.42                 ← 突然崩
 iter 950:  reward -11471   base_height 惩罚 -967
 iter 1100: reward -54984   base_height 惩罚 -2417
```

**根因**：机器人被弹飞后，`base_height`、`lin_vel_z`、`ang_vel_xy` 这三项都是**平方**形式，越界后增长极快（弹到 12 m/s 时 `lin_vel_z` 项冲到 −277）。天量的优势值反过来摧毁策略，再也回不来。

**修复**：
- 三项全部加 `torch.clip` 截断
- `base_height` 从**平方改成绝对偏差** —— 平方形式在目标附近梯度趋零（实测机身掉到 0.102 m，惩罚只有 −0.005，完全压不住），绝对偏差在整个区间梯度恒定

**效果**：第 2 轮起训练**全程稳定**，1000 迭代没有再崩（见 `plots/` 里的曲线）。

### 6.3 一个反例：惩罚不是越重越好

第 3 轮把反蹦跳惩罚加到 `feet_airborne = -2.0`，结果：

```
tracking_lin_vel: 0.17      ← 机器人放弃了移动
episode length:   1138      ← 开始摔
```

各项惩罚加起来 −5 以上，而跟踪奖励最多 +1 —— **策略发现"站着不动"比"走"更划算**。
第 5 轮改回 −0 并只保留温和约束。**这条经验值得记：奖励权重的绝对值要和"任务奖励的量级"匹配，否则会得到"什么都不做"的退化策略。**

### 6.4 关于「蹦」这件事 —— 尚未完全解决

第 2 轮的最佳策略：机身高度在 0.09~0.20 m 之间振荡，**平均只有 1.27 只脚同时着地**，主导频率 6 Hz。它是"蹬跳式前进"，不是平滑步态。

已尝试的抑制手段及效果：
- 抬脚滞空奖励（目标 0.15 s）：把"两条腿蹦"改善成"四条腿都用"（右后腿占空比 0.00 → 0.13）
- 直接惩罚三脚以上腾空：轻度有效，重度（−2.0）直接把策略压死
- 加强机身高度跟踪：效果有限，且过强会同时压低前进速度

**判断**：这是小型轻量四足 + 位置控制 PD + 简化奖励的共同结果，属于**调参问题而非框架问题**。后续建议见 §8。

### 6.5 奖励作弊：加了"对的"奖励，反而把任务做废了

第 6 轮加的 `gait_phase` 奖励在**机制上完全正确** —— 它直接约束"对角腿同相"的小跑结构，也**确实修好了步态对称性（改善 10~30 倍）**。但同时它把速度跟踪做废了：

```
策略选择:  原地踏步  ->  相位奖励 +1.08,  跟踪奖励 ~0.9 (小指令下误差本来就不大)
策略放弃:  真的走    ->  相位奖励 +1.08,  跟踪奖励 ~0.9,  但要多付力矩/加速度/碰撞惩罚
```

**只要"作弊"路径的收益 ≥ "正解"路径，策略一定选作弊** —— 这跟人的道德无关，是纯粹的优化行为。

**这条经验的价值**：调奖励时不能只看"这个奖励是否在鼓励我想要的行为"，还要问**"有没有一个不做正事也能拿满这个奖励的退化解"**。第 6 轮就是漏了这一问。

**通用防御手段**：
1. 新增奖励项一律**按任务相关量门控**（这里是按指令强度）
2. 关键任务奖励的权重必须**明显高于**辅助奖励（第 7 轮把 `tracking_lin_vel` 提到 3.0）
3. 验收时必须**用固定指令单独测跟踪精度**，不能只看训练日志里的平均奖励 —— 平均奖励会被"小指令容易跟"稀释（run 6 训练日志 tracking 0.868 看起来很好，实测速度增益只有 0.5）

### 8.2 已经验证过、**不要**再走的路

| 做法 | 实测结果 |
|---|---|
| 加大反蹦跳惩罚（`feet_airborne` −2.0） | 策略直接放弃任务（tracking 0.17） |
| 加大任务奖励权重（`tracking_lin_vel` 6.0） | 破坏稳定性（episode 从 2002 掉到 891） |

3. **新增奖励要问"有没有不做正事也能拿满它的退化解"** —— 相位奖励机制完全正确，却让策略学会了原地踏步
