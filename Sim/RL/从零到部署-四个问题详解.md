# 问题 1：只有 URDF，手动做一遍的完整流程

## 1.1 先认清哪一步最难

新手会以为"难在训练算法"。**实际上最难的是环境搭建和资产正确性，训练本身反而是最标准化的一步。**

本项目的真实分布：

```
环境搭建（装 Isaac Gym + 依赖）    ████████████████  最难，5 个坑，全都要自己爬
资产正确性（URDF/物理/PD）         ████████          次难，错了训练必然失败
训练与调参                         ██████            最容易，有方法论可循
```

## 1.2 阶段 0：环境搭建（预计 2~4 小时）

**这是唯一没有捷径的一步。** 本项目踩到的 5 个坑，你几乎一定会遇到：

| # | 症状 | 根因 | 解决 |
|---|---|---|---|
| 1 | `AttributeError: module 'numpy' has no attribute 'float'` | **isaacgym 自己的 `torch_utils.py:135` 用了 numpy 1.24 已移除的别名** | 补丁脚本 [scripts/06_patch_isaacgym_numpy.py](scripts/06_patch_isaacgym_numpy.py)（全仓库仅此 1 处） |
| 2 | `Command '['which', 'c++']' returned non-zero` | 系统没有任何 C++ 编译器，而 gymtorch 必须 JIT 编译 | `conda install -c conda-forge gxx_linux-64=10 gcc_linux-64=10`（无需 sudo） |
| 3 | `fatal error: crypt.h: No such file` | conda 的 sysroot 缺 `crypt.h` | `conda install -c conda-forge libxcrypt` + `CPATH=$CONDA_PREFIX/include` |
| 4 | `No module named 'tensorboard'` | rsl_rl 的 runner 要它 | `pip install tensorboard` |
| 5 | **报 CUDA illegal memory access**，看着像环境崩了 | `use_gpu_pipeline=True` 时调了非 tensor API（如 `get_actor_rigid_body_states`） | 这是 API 违规不是环境坏。训练代码走 tensor API；调试脚本设 `use_gpu_pipeline=False` |

**排查心法**：Isaac Gym 的报错经常"文不对题"。看到 CUDA 错误先怀疑**用法违规**，而不是驱动/显卡问题。

### 环境搭好的判断标准

跑通官方 demo 才算搭好。本项目用的是：

```bash
cd legged_gym
python legged_gym/scripts/train.py --task=a1 --headless --num_envs=512 --max_iterations=5
```

**为什么要跑 a1？** 它是官方自带、已知能训的任务。**先证明训练栈没问题，再换自己的机器人** —— 否则出问题分不清是框架还是配置。

## 1.3 阶段 1：资产准备（预计 半天~2 天，取决于 URDF 质量）

### 1.3.1 先做"不加载仿真"的静态检查

```bash
# ① 语法和树结构（需要 sudo apt install liburdfdom-tools）
check_urdf robot.urdf
#   期望：root Link: base_link has 4 child(ren)

# ② 用我们写的脚本打印所有关键量
python scripts/01_load_asset.py
#   期望：刚体数 13 / DOF 数 12 / 总质量与 CAD 一致
```

**必须核对的量**：
- 刚体数、DOF 数是否与设计一致
- 总质量是否与 CAD/实物一致（误差 >10% 就要查）
- 每个关节的 limit / effort / velocity 是否有值（不能是 0）
- **DOF 顺序** —— 这是个大坑，见下

### 1.3.2 ⚠️ DOF 顺序：Isaac Gym 会重排！

这是一个**反直觉但必须知道**的事实。本项目实测：

```
URDF 里的书写顺序:  lf_hip, lf_thigh, lf_calf, lb_hip, ...   （按腿分组）
Isaac Gym 实际顺序: lb_hip, lb_thigh, lb_calf, lf_hip, ...   （腿序被换成 lb,lf,rb,rf）
```

**解法的关键**：legged_gym 用 `default_joint_angles[关节名]` 按名字查表，所以**训练侧顺序自动处理**，你不用写映射。**只有导出到固件时**才需要对一次表：`A2C = [3,0,9,6,4,1,10,7,5,2,11,8]`。

### 1.3.3 碰撞体必须换成基本几何体

**不要用 STL 三角网格做碰撞体** —— 2048 个环境下 PhysX 会被拖垮。

本项目实测发现 visual 和 collision 网格是**几何完全相同**的（同为 618/642 顶点），即原碰撞体就是全精度网格。

替换方案（[scripts/05_make_sim_urdf.py](scripts/05_make_sim_urdf.py)）：

| link 类型 | 碰撞体 | 依据 |
|---|---|---|
| 机身 | box | 本来就是方块 |
| 细长连杆 | capsule（沿轴数据拟合） | 直接取轴对齐 AABB 会太"胖" |
| 足端 | **sphere r=9mm** | 真机是橡胶球 |

**⚠️ 我踩过的坑**：第一版对细长连杆用了轴对齐 AABB box，**太胖**，实测机器人直接塌掉（机身从 0.130 掉到 0.068，四条大腿同时触地）。必须用沿轴胶囊体。

### 1.3.4 ⚠️ 如果 URDF 没有独立足端 link

本项目 13 个刚体里**没有 `foot`**，只有 `base_link` + 每腿 `hip/thigh/calf`。

而 legged_gym 靠 `foot_name` 找脚来算步态奖励。解法：

```python
foot_name = "calf"                      # 用小腿当脚
penalize_contacts_on = ["thigh"]        # 必须把 calf 从惩罚里删掉！
```

否则就变成"一边用小腿当脚、一边惩罚小腿触地"，奖励自相矛盾。

## 1.4 阶段 2：物理自检（**这一步最值钱**，预计 1~2 小时）

**在训练之前，先证明纯 PD 控制能站住。**

```bash
python scripts/03_stand_test.py --urdf robot_sim.urdf --sweep
```

### 为什么这一步最值钱

它把"**奖励写错了**"和"**步态不好**"这两类问题**彻底分开**。如果站立都站不住，就不用谈走路了 —— 问题一定在物理/资产/PD，不在 RL。

### 要验证的四件事

| 验证项 | 期望 | 不对说明 |
|---|---|---|
| 能否撑起来 | 机身高度稳定、不塌 | PD 增益不足 / 质量属性错 |
| 姿态是否水平 | roll/pitch < 10° | 关节零位不是站立姿态 / 几何不对称 |
| **哪些刚体触地** | **只有足端** | 碰撞体太大，机器人"浮"在盒子上 |
| 四条腿是否对称 | 各腿高度接近 | 轴向符号错了（左右腿往反方向动） |

### ⚠️ 关于 `q_default`（站立姿态）

**本项目的重大发现**：交接文档推断 `q_default = [0]*12`，实测**证实**了 —— `q=0` 就是 CAD 装配好的弯腿站立姿态。

```
✅ 腿微弯、机身水平、四脚着地  →  q_default = [0]*12
❌ 腿伸直/折叠/机身歪斜        →  零位不是站立姿态，必须实测真实的 q_default
```

**如果实测发现 q=0 不是站立姿态**，你得用正向运动学反解出站立姿态的关节角，那会麻烦很多。

## 1.7 遇到问题怎么办：诊断树

```
训练不收敛 / 机器人不会走
│
├─ 先跑 03_stand_test.py：PD 能站住吗？
│   └─ 站不住 → 物理/资产问题，【别碰 RL】
│       ├─ 高度不对      → 查质量属性、PD 增益
│       ├─ 姿态歪        → 查关节零位、轴向符号
│       └─ 非足端触地    → 收缩碰撞体
│
├─ 能站住但不走
│   ├─ 完全不动          → 惩罚总和 >> 任务奖励（看日志分项）
│   ├─ 原地踏步刷奖励    → 奖励作弊！加门控
│   ├─ 走但方向不对      → 检查动作/观测顺序、关节符号
│   └─ 会走但不稳        → 域随机化、PD 增益、训练更长
│
└─ 训练中途崩（reward 变巨大负数）
    └─ 有平方惩罚无界增长 → 加 torch.clamp 截断
```

**三条通用心法**：
1. **分层排查**，永远从最底层（物理）往上查
2. **一次只改一个变量**
3. **用固定指令验收**，别只看训练日志的平均值

# 问题 2：Isaac Gym 是怎么用的

## 2.1 它是什么

一句话：**NVIDIA 做的"GPU 上并行跑几千个物理仿真 + 直接对接 PyTorch"的库。**

| | 说明 |
|---|---|
| 物理引擎 | NVIDIA PhysX（可以是 CPU 或 **GPU**） |
| 核心卖点 | **几千个环境同时在 GPU 上仿真**，状态直接是 torch 张量 |
| 速度 | 本项目 2048 环境达 **12~19 万 steps/s** |
| 状态 | ⚠️ 已被 NVIDIA 弃用，后继是 Isaac Lab / Isaac Sim 4.x。但因为它轻量、快、依赖少，**至今仍是四足 RL 最常用的平台** |
| 安装 | 需要 NVIDIA 开发者账号，从官网下载压缩包（不是 pip 包） |

## 2.2 核心抽象（看懂这 5 个词就够了）

```
Sim（仿真世界）
 └── Env（一个环境实例，比如"1 只机器人 + 它脚下的地"）
      └── Actor（环境里的一个物体，比如机器人本体）
           ├── Rigid Body（刚体：base_link, lf_thigh, ...）
           └── DOF（自由度 = 关节：lf_hip, lf_thigh, ...）
```

| 抽象 | 对应本项目 |
|---|---|
| Sim | 整个仿真世界（1 个） |
| Env | 一个训练环境（我们开了 2048 个，每个里面 1 只机器人） |
| Actor | 机器人本体 |
| Rigid Body | 13 个（base_link + 4 腿 × 3） |
| DOF | 12 个（4 腿 × 3 关节） |

**为什么开 2048 个环境？** 强化学习需要海量试错。2048 个机器人**同时**在不同初始条件下试，一个物理步就把 2048 条经验都采到了。这是 Isaac Gym 快的根本原因 —— 不是它物理算得快，而是**并行度高**。

## 2.3 编程模型：Tensor API（这是精髓）

**传统仿真**（MuJoCo/Gazebo）：
```python
for env in envs:                      # 逐个遍历，CPU
    state = env.get_state()           # 把数据从仿真器复制到 Python
    action = policy(state)
    env.set_action(action)
```

**Isaac Gym**：
```python
# ① 一次性"获取张量"（只是拿到一个指针，不复制数据）
self.dof_state = gymtorch.wrap_tensor(gym.acquire_dof_state_tensor(sim))

# ② 之后所有读写都是 torch 操作，数据【始终留在 GPU 显存里】
self.dof_pos = self.dof_state.view(n_envs, n_dof, 2)[..., 0]
self.torques = self.p_gains * (target - self.dof_pos) - self.d_gains * self.dof_vel
gym.set_dof_actuation_force_tensor(sim, gymtorch.unwrap_tensor(self.torques))

# ③ 一步仿真推 2048 个环境
gym.simulate(sim)
gym.fetch_results(sim, True)
gym.refresh_dof_state_tensor(sim)
```

**关键点**：
- 数据**不来回拷贝**（仿真器和 PyTorch 共享同一块 GPU 显存）
- 策略网络也跑在 GPU 上 → **观测→动作→物理全部在 GPU 内闭环**
- 这才是 10 万+ steps/s 的来源

### 一次 `step()` 到底发生了什么

legged_gym 里的一次策略步（`decimation=2`，即物理 200Hz、策略 100Hz）：

```
① 策略网络(47维观测) → 动作(12维)
② 动作变成目标角度:  q_target = q_default + 0.25 * action
③ 【重复 decimation=2 次】:
     - 算 PD 力矩:  tau = Kp*(q_target - q) - Kd*qd
     - 写入仿真器
     - gym.simulate() 推进 1/200 秒   ← GPU 上 2048 个环境同时推进
     - refresh 状态张量
④ 从新状态算观测、算奖励、判断是否摔倒
⑤ 返回给 PPO
```
所以**策略是 100 Hz，物理是 200 Hz**。这个频率必须和真机固件一致，否则策略行为会变。

## 2.4 ⚠️ 两个必知的坑

**坑 1：GPU pipeline 下禁用非 tensor API**

```python
sim_params.use_gpu_pipeline = True
...
gym.get_actor_rigid_body_states(env, actor, gymapi.STATE_ALL)   # ← 炸
# 报错: Gym cuda error: an illegal memory access was encountered
```
这不是环境坏了，是 **API 用法违规**。训练代码走 tensor API（legged_gym 本来就是），调试脚本设 `use_gpu_pipeline=False`。

**坑 2：数据在 GPU 上，想读出来必须 `.cpu()`**

```python
print(env.dof_pos)              # 打印出来是一堆 tensor(...device='cuda:0')
print(env.dof_pos[0].cpu())     # 正确
```

## 2.5 和 MuJoCo / Gazebo 的定位差异

| | Isaac Gym | MuJoCo | Gazebo |
|---|---|---|---|
| 定位 | **大规模 RL 训练** | 物理精度 / RL 研究 | 机器人系统集成 |
| 并行度 | 数千环境（GPU） | 单环境（CPU，MJX 可 GPU） | 单环境 |
| 速度 | 10 万+ steps/s | 100~1000 steps/s | 更慢 |
| 接触建模 | 够用（有时偏"软"） | **更准** | 一般 |
| ROS 集成 | 无 | 有 | **原生** |
| 适合 | 训策略 | 验证策略 / 精细操作 | 部署前系统测试 |

**一句话**：**Isaac Gym 用来"训"，MuJoCo 用来"验"，Gazebo 用来"接系统"。**

## 2.6 学习路径建议

```
1. 跑通官方 examples（不用 legged_gym）
   python isaacgym/python/examples/joint_monkey.py     ← 看关节怎么控制
   python isaacgym/python/examples/1080_balls_of_solitude.py  ← 看并行度
   python isaacgym/python/examples/interop_torch.py    ← 看 tensor 互操作

2. 读 legged_gym 的 LeggedRobot._init_buffers()（约 100 行）
   → 理解 tensor API 怎么用、状态量有哪些

3. 读 LeggedRobot.step() 和 _compute_torques()（约 30 行）
   → 理解一次策略步发生了什么

4. 再回头看配置文件，就都懂了
```

> 官方文档在 `~/isaacgym_ws/isaacgym/docs/index.html`，重点看 `programming/tensors.html`。

## 3.2 检查点里是什么

以 `model_500.pt`（1.3 MB）为例：

```python
{
  'model_state_dict': {          # ← 策略网络权重，部署只需要这部分
      'actor.0.weight': (256, 47),   # 输入层：47 维观测 → 256
      'actor.2.weight': (128, 256),
      'actor.4.weight': (64, 128),
      'actor.6.weight': (12, 64),    # 输出层：→ 12 维动作
      'critic.*': ...,               # ← 价值网络，【部署不需要】，训练才用
      'std': (12,),                  # ← 探索噪声，【部署不需要】
  },
  'optimizer_state_dict': {...},  # ← Adam 状态，【只有续训才需要】
  'iter': 0,                      # ⚠️ 这个字段不可靠，真实迭代号在文件名里
  'infos': None,
}
```

**要点**：
- **部署只用 `actor.*`**（4 层线性 + 3 个 ELU），一共约 47×256 + 256×128 + 128×64 + 64×12 ≈ 5.5 万个参数
- `critic` 和 `std` 是训练用的，导出时可以直接丢掉
- `optimizer_state_dict` 占了大部分体积（这就是为什么 5.5 万参数要 1.3 MB）

## 3.5 部署到真机：完整链路

```
                    ┌─────────────────────────────────────┐
   传感器           │        策略网络 (5.5万参数)          │
   JY901P IMU  ────→│  obs[47] → MLP → act[12]            │
     ├ 角速度       └──────────────┬──────────────────────┘
     └ 姿态→重力                    │
   12 个舵机 ──→ 关节位置/速度       ↓
                    q_target[i] = q_default[i] + 0.25 * act[i]
                    q_target = clip(q_target, 软限位)
                                   ↓
                    tau = Kp*(q_target - q) - Kd*qd
                                   ↓
                    12 个舵机目标位置（100 Hz）
```

### 固件要实现的（按顺序）

**① 拼观测 obs[47]** —— 顺序和缩放必须**逐位对齐**：

| 索引 | 内容 | 来源 | 缩放 |
|---|---|---|---|
| 0–2 | 重力向量（机体系） | JY901P 姿态反算 `Rᵀ·[0,0,−1]` | ×1.0 |
| 3–5 | 机身角速度 | JY901P 陀螺 | **×0.25** |
| 6–8 | 速度指令 [vx,vy,wz] | 遥控器/上位机 | ×1.0 |
| 9–20 | 关节位置 `q − q_default` | 舵机回读 | ×1.0 |
| 21–32 | 关节速度 | 舵机回读 | **×0.1** |
| 33–44 | 上一帧动作 | 自己缓存 | ×1.0 |
| 45–46 | 步态相位 sin/cos | **内部时钟** | ×1.0 |

**② 相位时钟**（唯一一个"免费"的观测量，不需要任何传感器）：
```c
phi = fmodf(phi + 0.01f * 3.0f, 1.0f);   // dt=10ms, 3 Hz
obs[45] = sinf(2*M_PI*phi);
obs[46] = cosf(2*M_PI*phi);
```

**③ 网络前向**：照抄 `policy_forward.py` 里的矩阵乘 + ELU

**④ 动作后处理**：
```c
q_target[i] = q_default[i] + 0.25f * act[i];
q_target[i] = clampf(q_target[i], soft_lower[i], soft_upper[i]);
```

**⑤ 关节 PD** → 舵机目标

### ⚠️ 部署的四个坑

| 坑 | 说明 |
|---|---|
| **关节顺序** | 仿真内部是 Isaac 顺序 C = `[lb,lf,rb,rf]×[hip,thigh,calf]`；固件按逻辑顺序 A。映射 `A2C = [3,0,9,6,4,1,10,7,5,2,11,8]` |
| **观测缩放** | 漏了 ×0.25 / ×0.1 之类，策略行为直接跑偏（而且极难排查） |
| **舵机零位偏移** | `joint_angle = servo_angle - joint_offset[i]`，标定姿态就是站立姿态（`joint_angle = 0`） |
| **控制频率** | 必须 100 Hz。频率不对等于改变了策略的时间尺度 |
| **驱动器延迟** | ⚠️ **仿真里舵机是理想的，真机有 1~3 步延迟**。这是 sim-to-real 最大的坑，见下 |

## 3.6 ⚠️ 部署前必须补的一件事：驱动器延迟

**现在仿真里的舵机是"理想伺服"**：你给目标角度，下一个物理步它就到位了。真机上：
- 总线通信延迟（SyncWrite 约 1 ms）
- 舵机内部 PID 响应时间
- 总延迟约 **1~3 个控制周期（10~30 ms）**

**后果**：真机上会震荡，而仿真里完全看不出来。

**补法**（交接文档 §8.1 也明确要求）：

```python
# 在 RlcatRobot.step() 附近加一个动作队列
if not hasattr(self, 'action_buffer'):
    self.action_buffer = [torch.zeros_like(actions) for _ in range(self.cfg.control.delay_steps)]

self.action_buffer.append(actions)
delayed_actions = self.action_buffer.pop(0)
# 用 delayed_actions 代替 actions 去算 PD
```

配置里加 `delay_steps = 2`，并把它纳入域随机化（每次 reset 随机 1~3 步）。

# 问题 4：什么是 sim2sim，需要 MuJoCo 吗

## 4.1 什么是 sim2sim

**在仿真器 A 里训练，把策略直接放到仿真器 B 里跑，看还能不能work。**

```
sim A (Isaac Gym)  ──训练──→  策略  ──直接部署──→  sim B (MuJoCo/PyBullet)
                                    ↑
                              不重新训练，不改任何东西
```

**它验证什么？** 验证"策略学到的是**通用规律**，还是**仿真器 A 的 bug/特性**"。

如果策略严重依赖 PhysX 的某种接触模型/求解器行为，那换到 MuJoCo 就会崩 —— 提前发现，总比上真机再发现好。

**它不验证什么？** 不能代替真机。sim2sim 成功不代表真机能跑（真机还有延迟、噪声、摩擦、装配误差）。

### sim2sim 在整条链路里的位置

```
Isaac Gym 训练
     ↓
  ★ sim2sim（换引擎验证）  ← 本文讨论的
     ↓
  域随机化 / 驱动器建模（同一引擎内加扰动）
     ↓
  真机部署（吊起 → 落地 → 低速 → 放开）
```

## 4.2 需不需要 MuJoCo

**分两种情况。**

### 情况 A：你想验证"策略有没有钻 PhysX 的空子"

**需要 MuJoCo。** 因为 MuJoCo 的接触模型和 PhysX 差异足够大，是很好的"换环境"测试。步骤：

1. 把 URDF 转成 MJCF（MuJoCo 的格式）—— `mujoco` 自带的转换器不完全可靠，通常要手工调
2. 用同样的 PD 增益、同样的控制频率、同样的观测缩放，在 MuJoCo 里重建环境
3. 加载导出的 `policy.pt`（或按 `policy_forward.py` 用 numpy 实现）
4. 对比步态、跟踪误差、稳定性

**成本**：2~5 天（建模 + 对齐接口 + 调试）。**最容易出错的地方是观测缩放和关节顺序没对齐** —— 一处不对，结果就完全不可比。

### 情况 B：你只想提高 sim-to-real 成功率

**不需要 MuJoCo。** 对这个项目来说，**收益最高的是补驱动器模型 + 域随机化**，而不是换引擎。

理由：本项目的 sim-to-real 风险**主要来自执行器**（理想舵机 vs 真实舵机），不是物理引擎的接触差异：

```
sim-to-real 差距来源（按本项目的影响排序）:
  1. 驱动器延迟/饱和        ████████  仿真里完全没有，必须手工补 ← 最高优先级
  2. 摩擦/质量不确定度       █████     域随机化可覆盖
  3. 传感器噪声             ███       仿真里已有（noise_scales）
  4. 物理引擎接触模型差异    ██        MuJoCo sim2sim 才能测
```

**4 项里前 3 项都不需要 MuJoCo。**

## 4.3 我的建议

### 短期（下一步该做的）

```
1. 补驱动器延迟模型（1~3 步），纳入域随机化        ← 最高性价比
2. 打开已有的域随机化：摩擦 0.5~1.25 ✓、加质量随机、加推力 ✓
3. 上地形（trimesh + 地形课程）
4. 在【同一个 Isaac Gym】里做"伪 sim2sim"：
   改 PD 增益 ±30%、加 20ms 延迟，看策略还稳不稳
   —— 这本质上就是域随机化，但实现成本几乎为零
```

### 中期

```
5. 如果真机表现和仿真差距仍然大 → 做真机系统辨识
   （阶跃响应、扫频、摩擦、延迟），把实测参数反哺仿真
6. 迭代 2~3 轮
```

### 什么时候才值得上 MuJoCo

- 你怀疑策略在钻 PhysX 的空子（比如靠穿透/软接触取巧）
- 需要向别人证明策略的鲁棒性
- 你的机器人要接 ROS 生态

**对本项目现在的阶段，我会先做短期那 4 条，MuJoCo 放到后面。**
