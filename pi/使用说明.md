# RL-CAT 树莓派侧 使用说明

> **这份文档是给"站在机器人旁边操作的人"看的。**
> 它讲清楚：装在哪、怎么跑、看到什么算对、出问题查哪里。
>
> 范围：**串口链路 / 遥测 / 标定 / 单关节点动 / 全身姿态**。
> 明确**不含**强化学习策略、ONNX/numpy 推理、仿真训练。
>
> 技术设计见 [`docs/31-pi-runtime.md`](../docs/31-pi-runtime.md)；
> 开发记录与固件行为清单见 [`README.md`](README.md)。

---

## 0. 三十秒上手

```bash
cd ~/RL-CAT/pi

./run_checks.sh                       # ① 不需要硬件：先确认程序本身是好的
python3 pi_hello.py --seconds 10      # ② 接上 STM32 后：读遥测、验链路
python3 status_panel.py --keepalive   # ③ 实时面板，一眼看全状态
python3 acceptance.py                 # ④ 阶段 1~5 一键验收（只读，不动舵机）
```

想动舵机之前，**先把机器人吊起或垫高**：

```bash
python3 acceptance.py --move --yes    # 含动作项的完整验收（吊起后）
python3 calib.py --show               # 看标定状态（只读，安全）
python3 jog.py --list                 # 看关节表，确认索引与关节名
python3 jog.py                        # 交互式点动，一次一个关节
```

## 1. 这台树莓派现在的状态

| 项 | 值 | 备注 |
|---|---|---|
| 系统 | Debian 13 (trixie)，内核 `6.18.39+rpt-rpi-2712` | Raspberry Pi 5 |
| 用户 | `<pi-user>`（本文档示例用 lbw，请换成你自己的） | 已在 `dialout` / `gpio` / `i2c` / `spi` / `docker` 组里 |

| 网络（开发通路） | eth0 静态 `169.254.100.2/16` + `192.168.50.2/24`，**无默认网关** | 直连 PC 的网线，不依赖 WiFi，重启自动恢复 |
| 网络（上网） | wlan0（热点 / 校园网） | 默认路由走这里 |
| CPU governor | `ondemand` | ⚠️ 跑长时间 100 Hz 循环前建议改 `performance`（见 §10.3） |
| 代码位置 | `~/RL-CAT/pi/` | |

**接线（树莓派 ↔ STM32）**：

| 树莓派 | 物理引脚 | 方向 | STM32 |
|---|---|---|---|
| GPIO14 (TXD0) | **8** | → | PA10 (USART1_RX) |
| GPIO15 (RXD0) | **10** | ← | PA9 (USART1_TX) |
| GND | 6 / 9 / 14 | — | GND |

⚠️ **交叉**接；3.3 V 直连（**不要接 5 V**）；**必须共地**。
⚠️ 这条是 USART1（对树莓派）。对舵机的那条 USART2 是**直连**，不要搞混。

## 3. 动手前的三项检查

```bash
# ① 串口节点在不在（必须看到 ttyAMA0）
ls -l /dev/ttyAMA0

# ② 有没有权限（应在 dialout 组里）
id | grep -o dialout

# ③ 物理层到底靠不靠谱 —— 短接物理引脚 8 和 10，然后：
python3 tools/uart_loopback.py
```

第 ③ 步的期望输出（**本机实测**）：

```
 0x55   发  100000  收  100000  误码      0  丢      0   1.004s     996 kbit/s  OK
 0xAA   发  100000  收  100000  误码      0  丢      0   1.007s     993 kbit/s  OK
 0xFF   发  100000  收  100000  误码      0  丢      0   1.007s     994 kbit/s  OK
 0x00   发  100000  收  100000  误码      0  丢      0   1.006s     994 kbit/s  OK
 PRBS   发  500000  收  500000  误码      0  丢      0   5.005s     999 kbit/s  OK
累计误码: 0
结论: ✅ 零误码、零丢字节 —— 这一路可以接 STM32 了
```

⚠️ **这一步不要跳。** 不做的话，后面链路出问题你分不清是 UART、是协议、还是接线。
**测完记得把那根短接线拔掉。**

## 4. 分阶段操作手册

### 阶段 1 — 打通链路

```bash
python3 pi_hello.py --seconds 30 --tilt
```

**期望输出（节选）**：

```
[启动自检] 等一帧 TEL_STATUS ...
  电压(TEL_STATUS) = 0 mV   ← ⚠️ 固件把这个字段写死为 0，真电压只在 TEL_FAST 里
  uptime = 1500 ms   mode = 0   err_flags = 0x00   seq_lost = 0
  status = 0x0F [READY|CALIBRATED|LINK_OK|IMU_OK]

  ✅ 收到 334 帧
  ✅ CRC 零错（实际 0）
  ✅ cycle_cnt 连续（跳变 0 次，丢 0 周期）
  ✅ TEL_FAST 帧率 ~100 Hz（实际 99.8）
  ✅ 处理耗时 P99 < 4 ms（实际 98 us）
  ✅ TEL_FAST 电压读数 11750 mV
```

**通过判据**：上面 6 条全 ✅，并且**手工确认**下面 3 条（脚本测不了）：

1. **用手掰某条腿** → 屏幕上的 `q` 对应分量跟着变
2. **把机身倾斜**（用 `--tilt`）→ 重力向量 `g=` 指向地面方向
3. **万用表量电池** → 与 `V=` 的读数差 < 50 mV

⚠️ 默认**不发任何指令**。固件的失联判定基于"距上次收到任意帧"，所以纯观察时
它会在 100 ms 后进 ESTOP（趴下）。只是看的话加 `--keepalive` 保持链路活跃。

### 阶段 2 — 遥测面板

```bash
python3 status_panel.py                      # 原地刷新的实时面板
python3 status_panel.py --mode once          # 打一次快照就退出（脚本/验收用）
python3 status_panel.py --mode log --interval 1 > panel.log &   # 记日志
```

**面板长这样**：

```
┌─ RL-CAT 遥测面板 ────────────────────────────────────────────────────────┐
│ 链路  /dev/ttyAMA0 @ 1000000       帧率   99.8 Hz   运行 00:01:23
│       收 5030 帧   CRC 错 0   半帧超时 0   丢 0 周期   发出 0 帧
│ 模式  请求 STAND    生效 STAND
│ 状态  READY|CALIBRATED|LINK_OK|IMU_OK
│ 错误  无
│ 电池  ✅ 11750 mV  正常
│ 温度  (原始 °C（固件实际行为）)
│       hip    [ 32.0   34.0   75.0!  38.0 ]
│       thigh  [ 33.0   35.0   37.0   32.0 ]
│       calf   [ 34.0   36.0   38.0   33.0 ]
│ 总线  rx_overflow 0   bus_err 0   bus_timeout 0   seq_lost 0   uptime 83.2 s
│ 关节  索引 A（髋外摆×4 → 髋俯仰×4 → 膝×4）
│       hip   +0.000 +0.000 +0.000 +0.000
│       thigh +0.000 +0.000 +0.000 +0.000
│       calf  +0.000 +0.000 +0.000 +0.000
│ 相位  sin +0.123  cos +0.992   cycle_cnt 8320
├──────────────────────────────────────────────────────────────────────────┤
│ ⚠️  舵机 [6] 超温（>70°C）—— 固件会强制趴下
└──────────────────────────────────────────────────────────────────────────┘
```

**通过判据**：

```
□ 电压读数与万用表对比，误差 < 50 mV     ← ⚠️ 看【电池】那一行（来自 TEL_FAST）
□ 12 个舵机温度都能读到且合理            ← 用手捂一个舵机：数值变几度=原始°C，变几十=0.1°C
□ mode / status 位能正确反映固件状态
```

**两个必须理解的点**：

- **为什么温度写着"原始 °C"**：协议规范写的是 0.1 °C，但固件实际塞的是原始 °C
  （`app_main.c:809-815`）。默认按固件实际行为解释。若你确认过是另一种，
  加 `--temp-unit deci`。
- **为什么面板要自己推算"生效模式"**：固件 `TEL_STATUS.mode` 给的是**请求的**模式。
  而 ACTIVE 有一道准入门（已标定 / 链路活 / IMU 好 / 有舵机反馈 / 安全层允许），
  过不了就**静默降级成 STAND**。不推的话，你会以为机器人在执行指令，其实它只是站着。
  面板在降级时会直接写出来，例如：`⚠️ 被降级：ACTIVE 被拒：未标定 (NOT_CALIB)`。

### 阶段 3 — 舵机标定

⚠️ **标定会让 12 个关节都动约 0.15 rad。必须先把机器人吊起或垫高。**

```bash
python3 calib.py --show      # ① 先看（只读、安全）
python3 calib.py --start --yes   # ② 启动全自动标定并等待（约 8.4 s）
python3 calib.py --check     # ③ 标定后自检
```

**期望输出**：

```
[1/3] 发送 CMD_CALIB(START) ...
      收到 TEL_ACK(action=0, result=0)（⚠️ result 恒为 0，无信息量）
[2/3] 等待标定完成（预期 8.4 s，超时 20 s）...
      ⚠️ 期间持续发帧保活，否则固件会在 100 ms 后开始趴下
      [ok] STAT_CALIBRATED 由 0 变 1 —— 新标定已完成并落盘（用时 8.41 s）
[3/3] 标定后自检 ...
      ✅ 12 个关节角都在硬件限位内
      ✅ 站姿下 |q| 最大 0.021 rad，合理
```

**通过判据**：

```
□ 标定能跑完，无超时
□ 标定后 q=0 时机器人呈【站立姿态】      ← calib.py --check
□ offset 存入 Flash，断电重启后仍有效      ← 重启后再 --show，应仍是 ✅
□ 失败时能给出可读的错误原因              ← ⚠️ 协议做不到，见下
```

#### ⚠️⚠️ 标定这一块，协议里能看到的东西很有限

| 想知道的 | 协议里 (USART1) | shell 里 |
|---|---|---|
| 能不能启动 | `CMD_CALIB(0)` 的 ACK | `C start` 的打印 |
| 进度百分比 | ❌ 没有 | ✅ `R` → `calib_progress` |
| 失败原因 | ❌ 没有（ACK 恒 `result=0`） | ✅ `R` → `calib_err` |
| 是否成功 | ✅ 只有 `STAT_CALIBRATED` 0→1 | ✅ `R` → `calib_state` |
| 逐关节 `dir`/`offset` | ❌ 没有 | ✅ `R` → `j0 id=.. off=.. dir=..` |
| 手动零点 | ❌ 动作 5 被解码器**拒收** | ✅ `C zero` |

**而 shell 这条路在树莓派上走不通**：固件里 `link_pi_poll()` 会把 USART1 的环形缓冲
抽干，之后 `bsp_shell_poll()` 什么都拿不到（`app_main.c:458-482` vs `link_pi.c:184-224`）。
所以拿进度/错误码/手动零点，需要：

- **推荐**：ESP32 无线口 —— 手机/电脑连 WiFi `RL-CAT-E959`（密码 `rlcat1234`），
  TCP 连 `192.168.4.1:3333`，敲 `R` 看 `calib_state` / `calib_err`，敲 `C zero` 做手动零点。
  `calib_err` 含义：`1`=读位置失败 `2`=写位置失败 `3`=舵机没动 `4`=方向判不出 `5`=结果超范围。
- 或者：台式 USB-TTL 直接接 STM32 的 USART1（**此时树莓派要先断开**）。

⚠️ **还有一个已知盲区**：**已经标定过的机器人，失败的重标定无法用协议识别**。
因为失败时固件不会清 `STAT_CALIBRATED`（旧表还在），位一直是 1，没有 0→1 跳变。
`calib.py` 遇到这种情况会明确写出"无法区分"，不会假装成功。

### 阶段 4 — 单关节点动

⚠️ **必须吊起/垫高。这是第一次真正驱动舵机。**

```bash
python3 jog.py --list                          # 先看关节表
python3 jog.py                                 # 交互式
python3 jog.py --sequence "4:+10;4:+10;4:-20;all:0" --dwell 1.0 --yes   # 脚本式
```

**交互命令**：

```
j <0-11>      选关节（也可以直接敲关节名，如 lf_thigh）
+ / -         按当前步长加/减
<数字>        直接给绝对角度（度）
s <度>        改步长
list          打印 12 个关节与当前目标角
home          全部回到 q_default
q             退出（会先发 MODE_IDLE 卸力）
```

**脚本模式输出（实测）**：

```
脚本模式：4 步，每步最多等 1.00 s，收敛判据 1.50°
  [1/4] lf_thigh → +10.00°
         收敛 ✅  最大误差 1.39°  实际   +8.61°
  [2/4] lf_thigh → +20.00°
         收敛 ✅  最大误差 1.18°  实际  +18.82°
  [3/4] lf_thigh →  +0.00°
         收敛 ✅  最大误差 1.35°  实际   +1.35°
  [4/4] 全部回到 q_default(0°)
         收敛 ✅  最大误差 1.35°  实际   +1.35°

结果：限位截断发生 0 次
```

**通过判据**：

```
□ 方向正确（正角度让关节往预期方向动）    ← 命令会同时打印"目标"与"实际"
□ 幅度正确（给 10° 就动约 10°）           ← 同上
□ 限位生效（超限被拒绝或截断）            ← 会打印"⚠️ …超出软限位，已截断到 xx°"并计数
□ 12 个关节逐个都能动                    ← --sequence 里把 0..11 走一遍
```

把 12 个关节走一遍：

```bash
python3 jog.py --sequence "0:+15;1:+15;2:+15;3:+15;4:+15;5:+15;6:+15;7:+15;8:+15;9:+15;10:+15;11:+15" \
    --dwell 1.2 --yes
```

⚠️ 未标定时 `jog.py` 会**直接拒绝**并说明原因。这不是多余的：固件会把 ACTIVE
静默降级成 STAND，关节根本不动——不拦住的话你会以为"发了指令没反应"。

### 阶段 5 — 全身姿态

```bash
python3 pose.py --list                     # 看预设与关节表
python3 pose.py --pose zero --yes          # 摆回站姿（唯一已验证的姿态）
python3 pose.py --pose-file poses/example.json --yes
python3 pose.py --pose zero --from "0,0,0,0,20,20,20,20,0,0,0,0" \
                --cycles 3 --ramp 15 --yes      # 来回缓慢变姿态
```

**实测输出**：

```
  限速 40.0°/s   收敛判据 2.0°   保持 0.3 s
[起始] 先摆到 --from 姿态
      起始：Δmax 42.50°，按 40.0°/s 预计 1.06 s；✅ 收敛（残差 0.27°）
[第 1/2 趟] → 目标姿态
      去程：Δmax 19.80°，按 40.0°/s 预计 0.50 s；✅ 收敛（残差 0.57°）
      保持 0.3 s 后残差 0.00°
[第 1/2 趟] ← 回起始姿态
      回程：Δmax 20.00°，按 40.0°/s 预计 0.50 s；✅ 收敛（残差 0.49°）
```

**通过判据**：

```
□ 能摆出站立姿态并保持          ← --pose zero，并观察保持阶段残差是否变大
□ 能缓慢改变姿态而不失稳          ← --from / --cycles + --ramp 调慢
```

**关键参数**：

| 参数 | 含义 | 建议 |
|---|---|---|
| `--ramp` | 最大关节速度（度/秒） | 第一次用 **10~15**；确认无误后再加快 |
| `--tol` | 收敛判据（度） | 默认 2.0 |
| `--timeout` | 收敛等待上限（秒） | 默认 8 |
| `--hold` | 到位后保持几秒 | 观察"重力下有无下垂" |

⚠️⚠️ **本脚本不发明姿态。** 唯一被实测确认过的是 **全 0 = 弯腿站姿**。
下蹲/抬腿这类姿态需要真实运动学与限位配合，得你自己算好角度，写进
`--pose` 或 `--pose-file`（[`poses/example.json`](poses/example.json) 是模板，
里面的数值**未经真机验证**）。

⚠️ 如果 `err_flags` 非 0，安全层会把动作幅度压到 **75%**，也就是说姿态只到目标的 3/4。
`pose.py` 会提前警告这件事。

### 4.6 一键验收：把上面五个阶段串起来

python3 acceptance.py --move --yes           # ⚠️ 含动作项，必须先把机器人吊起
python3 acceptance.py --move --calibrate --yes   # 未标定时顺便跑一次标定
```

**只读模式输出（实测）**：

================================================================================

  ✅ P1.2    TEL_FAST 帧率 ~100 Hz

   · P2.8 【人工】mode / status 位与实际状态一致
   · P3.5 【人工】标定后 q=0 时机器人呈站立姿态
   · P3.6 【人工】断电重启后 STAT_CALIBRATED 仍为 1（offset 已入 Flash）
================================================================================
```

**`--move` 模式额外跑**：12 个关节逐个动到 `+15°`（**并且确认只有它动**——这一条同时验证了关节索引对齐），限位截断，然后摆站姿、缓慢变姿态。

```
  ✅ P4.05   关节 4 lf_thigh 能动到 +15° 且【只有它动】
              实测 +14.04°（误差 0.96°，限 2.5°）；其余关节最大漂移 0.07°；已收敛到 1.0° 内
  ...
  ✅ P5.2    保持 2 s 后残差 < 3°（没有明显下垂）
  ⏸  P5.4    【人工】变姿态过程中不失稳（腿不打架、机身不晃到失稳）
```

**退出码**：`0` = 没有失败项；`1` = 有失败项；`2` = 打不开串口。
**人工项不会让脚本失败**——它们是列出来让你照做的。

⚠️ **只读模式也会发保活帧**：已标定时发 `MODE_STAND`（力矩使能、握住站姿、机器人纹丝不动）；
**未标定时只发 `MODE_IDLE`（卸力）**——原因见 §8 已知限制第 9 条，那是条安全规则。

## 7. 故障排查（按现象查）

| 现象 | 先查什么 |
|---|---|
| **一帧都收不到** | ① `ls -l /dev/ttyAMA0` 在不在 ② 接线是不是**交叉**（Pi TX→STM32 RX）③ **共地**了没有 ④ STM32 上电了吗 ⑤ 波特率是不是都是 1000000 |
| **CRC 错 / 半帧超时 持续出现** | 线太长/接触不良；先把引脚 8↔10 短接跑 `uart_loopback.py` 确认树莓派这侧干净，再查 STM32 侧 |
| **`STAT_READY` 未置位** | STM32 时钟不是 72 MHz 或 DWT 自检没过（看 PC13 状态灯有没有 5 Hz 快闪） |
| **`STAT_CALIBRATED` 未置位** | 标定表没落盘或无效。跑 `calib.py --show`，必要时 `calib.py --start` |
| **`STAT_IMU_OK` 未置位** | IMU 读不到。⚠️ 已知 `rlcat_config.h` 里 IMU 器件 ID 寄存器写错（读 `0x00`，那其实是 SAVE 寄存器），自检会 100% 失败——见 [`docs/42-pi-setup.md`](../docs/42-pi-setup.md) §B4 |
| **发了指令，关节不动** | ① 标定了吗 ② 是不是还在**上电 1000 ms 门控期**内（固件这期间不写舵机位置）③ 12 个关节反馈是否**全部**有效（缺一个就一直只读不动）④ 生效模式是不是被降级了（面板会写出来） |
| **只发心跳也不报失联** | 这是固件设计：失联判定基于"距上次收到**任意**帧"。所以**心跳不能替代控制指令**，Pi 要自己看 `cycle_cnt` / `q` 有没有在变 |
| **`err_flags` 非 0，动作变小** | 它是 **latch，只有重启才清**；只要非 0，安全层就把幅度压到 **75%**。跑 `status_panel.py` 看具体是哪一位 |
| **机器人上电就趴下** | 正常：收到第一帧之前固件按"失联"处理。Pi 一发帧就会解除，但**模式不会自动回到 ACTIVE，要主动请求** |
| **USB-TTL 敲 shell 没反应** | 已知问题：固件里 `link_pi_poll()` 把 USART1 抽干了，shell 拿不到字节。用 ESP32 无线口（TCP `192.168.4.1:3333`） |
| **`status_panel` 一直显示 ESTOP** | 只观察、没发过帧。加 `--keepalive` |
| **周期抖动大 / 帧率不足 100 Hz** | 把 governor 改成 `performance`（见 §10.3）；关掉树莓派上不必要的负载（它跑着 Docker） |

## 8. 已知限制（协议里做不到的事）

1. **标定进度 / 失败原因 / 逐关节 dir & offset**：协议不提供，且树莓派的 USART1 也敲不进 shell。只能走 ESP32 无线口。
2. **手动零点（`C zero`）**：`CMD_CALIB action=5` 被固件解码器拒收，Pi 发不出去。
3. **失败的重标定**：起始已标定时无法用协议区分"新标定成功"与"旧表还在"。
4. **`CMD_JOINT` 的 `flags`**：`FLAG_ENABLE` / `FLAG_RESET_ERR` / `FLAG_REQ_CALIB` **都没实现**，只有 `FLAG_REQ_STATUS` 有效；`kp_scale` 和 `led` 字段被解码但从不使用。
5. **`TEL_STATUS.voltage_mv` 恒为 0**：真电压只在 `TEL_FAST` 里。
6. **`TEL_STATUS.mode` 是"请求的模式"**，不是生效的。
7. **固件不发 HEARTBEAT、不发 TEL_LOG**。
8. **急停**：目前只有软路径（失联 >100 ms / ≤9.3 V / 舵机 >70 °C）。**硬件急停按钮未实现**（`RLCA_ESTOP_INPUT_EN = 0`）。
9. ⚠️⚠️ **未标定时【绝不能】发 `MODE_STAND` 或 `MODE_ACTIVE`。**
   固件只给 `ACTIVE` 加了准入门（`app_mode.c`），**`STAND` 没有任何准入检查**。
   而默认标定表是 `dir=+1 / offset=0`（`rlca_calib_load_defaults` 里 memset 出来的），
   `q_target = 0`（正是站姿）按 `rlca_q_to_step` 换算出来正好是 **舵机 step 0** ——
   于是 12 个舵机全部冲向绝对位置 0，也就是**机械行程的一端**。
   固件作者在 `app_main.c:695-709` 记录过这个撞机事故。
   **也就是说：「未标定 → ACTIVE 降级成 STAND」这个保护，对未标定的机器人本身就是危险的路径。**

   → 本层所有工具都遵守这条规则，并且有回归测试钉住它（`K2b` / `K2c` / `K3b`）：
   `jog.py` / `pose.py` / `acceptance.py` 在 `STAT_CALIBRATED` 未置位时**直接拒绝**，
   保活只发 `MODE_IDLE`（卸力）。

## 9. 安全须知

```
① 动舵机之前，机器人必须【吊起或垫高】。
   calib.py --start / jog.py / pose.py / acceptance.py --move
   都会真的驱动 12 个舵机。

② ⚠️⚠️ 未标定时【绝不能】发 STAND / ACTIVE。
   固件的 STAND 没有准入门，未标定（默认表 dir=+1/offset=0）时 q_target=0
   会换算成舵机 step 0，把 12 个关节全部驱到机械行程一端。
   本层所有工具都已按这条规则把关，并有回归测试（见 §8 第 9 条）。
   如果你自己写脚本，也请照这条来：先确认 STAT_CALIBRATED 再发带目标角的模式。

③ 一定要优雅退出。所有脚本在 finally 里都会先发 MODE_IDLE 再关串口。
   如果你直接 Ctrl-C 或拔线：固件会在 30 ms 降级、100 ms 后开始以 0.5 rad/s 趴下，
   大约 2.5 s 后卸力 —— 结果可能是机器人突然瘫倒。

④ 树莓派【不做】任何安全兜底。安全全在 STM32 上（低压 / 超温 / 失联）。
   树莓派崩了，STM32 必须能自己停下来。

⑤ 第一次跑新姿态，先用小角度（<=5°）、慢速（--ramp 10）、一次一个关节。
```
