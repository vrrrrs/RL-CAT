## 0. ⚠️ 先读这段：当前状态（2026-10-17 更新）

> **⚠️ 原来这节列的"两个未查明问题"【都已解决】。** 保留结论如下，避免有人按旧结论排查。

### 0.1 已解决：标定（原"标定表状态未知"）

**结论：标定流程本身没问题，问题出在**三个"零"的定义**和**符号约定**上。**

**最终确定的语义（这是本项目最容易搞错的地方，务必记住）：**

| 名字 | 姿态 | 关节角 | 舵机编码器读数 |
|---|---|---|---|
| **URDF 零位** | **弯腿站姿**（`default_joint_angles` 全 0） | **q = 0** | **= `offset`** |
| **标定姿态** | **腿伸直、垂直向下、髋水平** | q = ±`q_calib`（**幅值**） | **2048**（上位机里设） |
| 编码器零 | 舵机自己的 0 位 | 无关 | 0 |

```
换算：step = dir × q × (4096/2π) + offset
反推：offset = 2048 − dir × q_calib × (4096/2π)
```

**⚠️⚠️ `q_calib` 是【幅值，全为正】，符号完全交给 `dir` 表达。**

> `dir` 本身已编码了"关节角增大 → 编码器增大(+1) 还是减小(−1)"。
> 若再给 `q_calib` 加左右镜像符号，两个符号**互相抵消**，
> 于是左右两侧的 `offset` 跑到 2048 的**同一侧** —— 那是错的。

**最终 `dir` 表（按舵机 ID）：**

```
1↔+1   2↔−1   3↔−1   4↔+1      hip
5↔+1   6↔+1   7↔−1   8↔−1      thigh
9↔−1   10↔−1  11↔+1  12↔+1     calf
```

**⚠️ calf 那四个（ID 9~12）被**整体翻转**过一次** —— 初版按"与 thigh 同号"猜测，实测定为反向。**这是"不能靠推断、必须实测"的最好例证。**

**✅ 已验证的判据（在标定姿态下读 `TEL_FAST.q`）：**

```
hip   应 ≈ 0.000 / 0.083 / 0.000 / −0.002     (q_calib = 0)
thigh 应 ≈ 0.785 / 0.698 / 0.807 / 0.700     (45° / 40°)
calf  应 ≈ 1.569 / 1.483 / 1.574 / 1.483     (90° / 85°)
```

**⚠️ 若读到的是 ±3.14（≈π）而不是上面的值，说明 `offset[]` 全是 0**
（= 用的是 `rlca_calib_load_defaults()` 的虚表，不是真标定表）。
因为 `2048 × 2π/4096 = π`。

**⚠️ 另外固件已加两道防呆（2026-10-17）：**
1. `CMD_CALIB(RESTORE_DEFAULT)` 不再把 `s_calib_ok` 置 true（恢复默认 = 放弃标定）
2. 上电时若发现 12 个 `offset` 全为 0 ⇒ 认定未标定，不亮 `STAT_CALIBRATED`

### 0.2 已解决：上电/标定时舵机乱动（原"上电舵机就动"）

**根因是三条独立的错误路径，都已修掉：**

| # | 根因 | 修法 |
|---|---|---|
| **1** | `MODE_STAND` 在未标定时用默认虚表把 `q=0` 换算成 **step 0** | 未标定时 STAND/DAMP/IDLE 改为**卸力矩 + 目标跟随实测角** |
| **2** | 标定流程的"方向测试"要**先使能力矩**，而那一刻另外 11 个舵机的 `GOAL_POSITION` 还是它们自己存的旧值 ⇒ 一起奔向陈旧目标 | **整段方向测试删除**（方向改由 `RLCA_JOINT_DIR_INIT` 给出）。标定现在**全程不上力矩、不动任何关节**，只采样 |
| **3** | 标定采样把第 9 次读数也累加进 `accum`，导致 `offset` 偏大约一个读数 | `do_sample` 重写：统一累加，第 8 轮结束时一次性求平均 |

**⚠️ 另外固件现在有一条硬规则：没有明确指令（带 `ENABLE` 的 `CMD_JOINT`）之前，**
**不准上力矩、不准写位置。** `K` 里的 `pos_write_allowed` 可直接确认。

### 0.3 ⚠️ 仍然存在：`status_panel.py` 会让固件进 ESTOP —— **已修**

**现象（原文档 §0 提到的那条）：观察工具自己把链路踩死。**

**根因：** 固件的链路判据是"距上次收到任意帧的间隔"——
`> 30 ms` 降级、`> 100 ms` 急停。而面板在主循环里 `render_panel()` + `print()`，
输出到 SSH 管道时**一次可能阻塞几十毫秒**，把保活饿死。

**✅ 修复（2026-10-17）：保活改到**后台线程**（`_KeepAlive`，`status_panel.py:205`）。**

**⚠️ 如果你看到这个自相矛盾的组合：**

```
状态  READY|CALIBRATED|LINK_OK|IMU_OK|ESTOP
      ↑ LINK_OK 亮着          ↑ 却同时 ESTOP
```

**那就是这个 bug（或同类的"主循环阻塞"）。修复后不该再出现。**

**⚠️ 其他工具（`jog.py` / `pose.py` / `acceptance.py`）不受影响** ——
它们是按控制周期**连续发帧**的，天然满足 30 ms。

## 0.4 ⚠️⚠️ 一条硬规则（新代码也必须遵守）

**未标定（`STAT_CALIBRATED` 未置位）时，绝不能发 `MODE_STAND` 或 `MODE_ACTIVE`。**

原因：固件**只给 `ACTIVE` 加了准入门**，`STAND` 没有任何准入检查。
而默认标定表是 `dir=+1 / offset=0`（`rlca_calib_load_defaults` 里 `memset` 出来的），
`q_target = 0`（正是站姿）按 `rlca_q_to_step` 换算正好是 **舵机 step 0**
→ 12 个舵机全部冲向绝对位置 0（机械行程一端）。

也就是说「未标定 → ACTIVE 降级成 STAND」这个被文档当"保护"的设计，**对未标定的机器人本身就是危险路径**。

**⚠️ 固件侧已加两道保护（2026-10-17），但本层这条规则仍然要遵守：**
1. `app_mode.c` 的 STAND / DAMP / IDLE 在未标定时改为**卸力矩 + 目标跟随实测角**
2. `app_main.c` 的 ⑦ 在未标定时**一条位置指令都不发**

**⇒ 双保险。但不要依赖固件侧的保护来省掉本层的把关。**

本层所有工具都已按这条把关，并有回归测试钉住它（`K2b` / `K2c` / `K3b`）：

```
✅ K2b ⭐ 未标定时【从未】发出 STAND
✅ K2c ⭐ 未标定时【从未】发出 ACTIVE
✅ K3b 拒绝时确实一个 STAND 都没发
```

## 1. 通路：一根网线 + link-local（**不需要管理员权限**）

```
┌──────────────────┐   一根网线（交叉/直通都行，千兆口自动协商）  ┌──────────────┐
│   Windows PC     │◄──────────────────────────────────────────►│  树莓派 5     │
│ 以太网口          │                                            │  eth0        │
│ 169.254.x.x/16   │   💡 PC 侧【什么都不用配】                    │ 169.254.100.2│
│ (APIPA 自动)      │                                            │ +192.168.50.2│
└──────────────────┘                                            └──────────────┘
```

**为什么这么配（这是这套方案的关键，和 `docs/42-pi-setup.md` §B1 原始的 192.168.50.x 方案不同）：**

| 事实 | 后果 |
|---|---|
| Windows 的以太网口在没有 DHCP 服务器时会自己拿一个 `169.254.x.x`（APIPA / link-local） | **PC 侧不需要管理员权限去设静态 IP** |
| PC 路由表里 `169.254.0.0/16` 本来就是 on-link | 只要 Pi 也在这条链路上，两边就能直通 |
| 所以：**只给 Pi 的 eth0 加一个 `169.254.100.2/16`** | PC 一个设置都不用改 |
| Pi 的地址是**静态写死在 nmcli profile 里**的 | 重启自动恢复；PC 的 APIPA 值会变，但**不影响**（我们总是连固定的 `169.254.100.2`） |

**三条可用通路（按优先级）：**

| 通路 | 地址 | 依赖 | 备注 |
|---|---|---|---|
| **主：网线 link-local** | `169.254.100.2` | 一根网线 | ⭐ 不依赖 WiFi / 热点 / 校园网，重启持久 |
| 备：网线静态 | `192.168.50.2` | PC 侧把以太网口配成 `192.168.50.1/24`（**需管理员**） | 已同时配在 Pi 上，随时可用 |
| 备：WiFi | 由路由器/热点分配 | 树莓派连上 WiFi | ⚠️ IP 会变，需要重新发现 |

## 3. 这套配置是怎么来的（以及怎么恢复）

### 3.1 Pi 侧：串口

`/boot/firmware/config.txt` 末尾（`[all]` 之后）：

```ini
# --- RL-CAT: 专用 UART0 (PL011) on GPIO14/15 for STM32 ---
dtoverlay=uart0-pi5
```

重启后验证：

```bash
ls -l /dev/ttyAMA0                 # 应出现（crw-rw---- 204,64）
pinctrl get 14,15                  # 应显示 GPIO14=TXD0、GPIO15=RXD0
dmesg | grep ttyAMA                # 应看到 "pl011-axi 1f00030000.serial: ttyAMA0 ... PL011 AXI"
ls -l /dev/serial0                 # 应仍指向 ttyAMA10（说明 console 没被抢走）
```

**备用 / 还原**：

```bash
sudo cp /boot/firmware/config.txt.bak-rlcat /boot/firmware/config.txt   # 如果有备份
# 或者手动删掉上面那两行，然后 sudo reboot
```

### 3.2 Pi 侧：网络

```bash
sudo nmcli con mod "Wired connection 1" \
  ipv4.method manual \
  ipv4.addresses "192.168.50.2/24,169.254.100.2/16" \
  ipv4.gateway "" \
  ipv4.never-default yes \
  ipv4.dns "" \
  ipv4.route-metric 100 \
  connection.autoconnect yes
sudo nmcli con up "Wired connection 1"
```

⚠️ **`ipv4.never-default yes` 是关键** —— 否则这条直连会抢默认路由，机器就上不了网了。

验证：

```bash
ip -br a show eth0     # 应有两个 IPv4：169.254.100.2/16 和 192.168.50.2/24
ip route               # 应【没有】经 eth0 的 default；默认路由仍在 wlan0
```

**还原成 DHCP**：

```bash
sudo nmcli con mod "Wired connection 1" ipv4.method auto ipv4.addresses "" ipv4.gateway "" ipv4.never-default no
sudo nmcli con up "Wired connection 1"
```

### 3.3 物理层自检（⚠️ 接 STM32 之前必做）

把**物理引脚 8 (GPIO14)** 和**引脚 10 (GPIO15)** 用一根杜邦线短接：

```bash
cd ~/RL-CAT/pi && python3 tools/uart_loopback.py
```

期望：90 万字节，**零误码、零丢字节**，~999 kbit/s。**测完把短接线拔掉。**

## 5. 开发流程：**离线优先**

这是**唯一安全且快速**的迭代方式 —— 不接真机，用假 STM32。

### 5.1 假 STM32（PTY 测试替身）

```bash
cd ~/RL-CAT/pi
# 终端 A
python3 tools/fake_stm32.py --pty-file /tmp/fake.pty --calibrated -v
# 终端 B
P=$(cat /tmp/fake.pty)
python3 acceptance.py --port $P --move --yes
python3 status_panel.py --port $P --mode once --keepalive
python3 calib.py --port $P --show
python3 jog.py --port $P --sequence "4:+10;4:-10" --yes
python3 pose.py --port $P --pose zero --yes
```

故障注入开关：`--drop-rate` `--crc-rate` `--calib-fail` `--calib-start-fail`
`--hot-servo N` `--err-flags 0x40` `--startup-gate-ms` `--battery-invalid`。

⚠️ **假 STM32 的存在意义是"验证协议与状态机"，不是"验证电信号"。**
1 Mbps 的物理层误码率要用 `tools/uart_loopback.py` 单独实测（见 §3.3）。

### 5.2 全量自检

```bash
cd ~/RL-CAT/pi && ./run_checks.sh          # 3 套自检 + 141 + 20 + 102
python3 tests/test_basic_offline.py -v     # 看每一条
```

**什么才算"改完"：**

```
☑ ./run_checks.sh 全绿（117 项一项都不能掉）
☑ 新功能有自己的离线测试（加进 tests/test_basic_offline.py）
☑ 涉及"发指令"的改动，必须遵守 §0 那条硬规则，并加安全回归
☑ 改完在 Pi 上跑过（不是只在 PC 上编译过）
```

### 5.3 代码风格约定（沿用现有代码）

- `from __future__ import annotations` 放最前面
- 输出前把 stdout/stderr 切成 UTF-8（Windows 控制台是 GBK）——现有脚本都有这段
- 参数集中在 `config.py`，不要在脚本里写魔法数字
- 时间用 `time.perf_counter()`（不是 `time.time()`）
- 统计用 `stats.Percentiles`（**有界**，100 Hz 循环里不能无界 append）
- 串口 I/O 一律走 `link.PiLink`，不要自己 `import serial` 重写一遍

### 6.2 ❌ 不要做的事

| # | 禁 | 理由 |
|---|---|---|
| 1 | 逆运动学 / 观测组装 / 策略推理 | **本轮范围外**（强化学习） |

| 3 | 用 `input()` 或阻塞读做主循环 | 会卡死 100 Hz 循环；键盘必须放独立线程（参考 `jog.py`） |

| 5 | 给 Pi 装重依赖 | 目前只依赖 `pyserial`。`numpy`/`onnxruntime` 属 RL 范围 |
| 6 | 在未标定时发 `STAND`/`ACTIVE` | 见 §0 |

## 9. 如果你在**别的机器**上开发

本文默认"同一台 PC"。换机器时：

1. **私钥**：把 `~/.ssh/rlcat_pi_ed25519` 拷过去（简单，但私钥多一份泄露面），
   或者给新机器单独生成一把公钥、追加到 Pi 的 `~/.ssh/authorized_keys`（**推荐**）。
2. **网络**：新机器也必须**用网线直连树莓派**，并且它的以太网口要能拿到 `169.254.x`
   （Windows 默认行为；Linux 桌面一般也是）。
   如果它拿不到，就把它的以太网口配成 `192.168.50.1/24` 走备通路。
3. **代码**：仓库没有 git，需要用 U 盘/网盘/共享目录搬一次 `pi/` 目录。
