## 1. 项目背景

**RL-CAT** 是一只 12 自由度四足机器人。

```
上位机：树莓派 5 (4GB)  →  跑强化学习策略（MLP 256-128-64, PPO）
下位机：STM32F103C8T6   →  100 Hz 控制环 + 传感器采集 + 安全保护
执行器：12 × Feetech ST-3215-C018 总线舵机
通信：  USART1 ↔ 树莓派 (1 Mbps)
        USART2 ↔ 舵机控制板 (1 Mbps)      ← 全双工 TTL
        USART3 ↔ ESP32-C3 无线 (115200，低频调试通道)
传感器：JY901P IMU（软件 I2C，PB8/PB9）  内部融合，直接输出姿态
        电池电压（ADC 分压，PA0）
```

### 1.1 ⚠️ 上位机 / 下位机职责边界

**这个边界必须严格，否则会出问题：**

| 职责 | 树莓派 | STM32 |
|---|---|---|
| 策略推理 | ✅ | ❌ |
| 关节目标角生成 | ✅ | ❌ |
| 舵机总线时序 | ❌ | ✅ |
| PD 位置闭环 | ❌ | ✅（舵机内部 PID） |
| 传感器采集 | ❌ | ✅ |
| 姿态解算 | ❌ | ❌（JY901P 内部完成） |
| **安全保护** | ❌ | ✅ **（不依赖上位机）** |
| 日志上报 | 接收侧 | 采集侧 |

**⚠️ 最重要的一条：安全保护必须在 STM32 上，且不能依赖树莓派的正常运行。** 链路断了要能自己识别并趴下。

## 2. 硬件平台与约束

### 2.1 STM32F103C8T6 资源

| 资源 | 容量 | 备注 |
|---|---|---|
| Flash | 64 KB | ⚠️ 紧张，不要引入 printf 浮点、不要用 CMSIS-DSP/NN |
| RAM | **20 KB** | ⚠️ **最紧张的资源**，缓冲区要算着用 |
| 主频 | **72 MHz** | 已配好（HSE 8 MHz × PLL9） |
| APB1 | 36 MHz | USART2、USART3 挂这里 |
| APB2 | 72 MHz | USART1、ADC 挂这里 |
| 定时器 | TIM1-TIM4 | TIM2 空闲，可做 1 kHz 节拍 |

**⚠️ 20 KB RAM 的分配建议：**

```
舵机接收缓冲（512 B）× 1          =  512 B
树莓派发送缓冲（128 B）            =  128 B
树莓派接收缓冲（128 B）            =  128 B
环形缓冲（UART1/2/3 各 256 B）     =  768 B
关节状态数组（12 × 32 B）          =  384 B
标定参数（12 × 8 B）               =   96 B
协议编解码临时区                   =  256 B
栈（CubeMX 默认 0x400）            = 1024 B
堆（CubeMX 默认 0x200）            =  512 B
────────────────────────────────────────
小计                               ≈ 3.8 KB
余量                               ≈ 16 KB  ← 足够
```

**⚠️ 原版舵机库在 `syncReadBegin` 里用了 `malloc` —— 必须改成静态缓冲。**

### 2.2 舵机：Feetech ST-3215-C018

| 参数 | 值 | 固件需要注意 |
|---|---|---|
| 型号 | **ST-3215-C018（12V 版）** | ⚠️ 只有这个型号能用 3S |
| 通信 | 半双工异步串口 8N1 | 见 §2.3 |
| 默认波特率 | **1 Mbps** | 与 USART2 一致 |
| 位置分辨率 | 4096 步 / 360° | 0.0879°/step |
| 位置范围 | 0 – 4095 | ⚠️ 多圈会回绕，要处理 |
| **位置更新周期** | **最快 1 ms** | 控制环 10 ms，够用 |
| 反馈量 | 位置/速度/负载/电压/温度/电流/移动标志 | 见 §5.4 |
| 保护 | 过流 >2 A 持续 2 s 切断 / 过温 >70 °C / 过压 >14 V | 固件要读回并上报 |

### 2.3 ⚠️ 关于"全双工还是半双工"

**这个问题容易搞混，这里说清楚：**

```
舵机侧的物理总线：半双工（单根信号线，收发分时）
        ↑
        │  由【舵机控制板】内部处理
        │
MCU 侧（USART2）：全双工 TTL（独立的 TX 和 RX）
```

**结论：**

| 项 | 配置 |
|---|---|
| **USART2 模式** | **全双工（普通异步）** ✅ 不要开 HDSEL |
| **控制板跳线** | 必须拨到 **A** 位 |
| **控制板型号** | Waveshare Bus Servo Adapter (A)，SKU 25514 |

**⚠️ 接线是"直连"（RX→RX、TX→TX）而不是交叉 —— 这点和常规串口不同。**

**依据**：[Waveshare 官方接线文档](https://docs.waveshare.com/Bus_Servo_Adapter_A/Product-Wiring-Example) 原文：
> *The connection must be **RX-RX, TX-TX** correspondingly. At this time, the jumper cap on the bus servo driver board must be in the **A** position.*

**⚠️ 原因：控制板上的 TX/RX 端子丝印是【按 MCU 侧】标注的，不是按控制板自身标注。所以照丝印一对一接就是直连。**

**⚠️ 对照：USART1 ↔ 树莓派那条是【标准交叉】。两条链路接法不同，不要搞混。**

### 2.4 ⚠️ 控制板 5 A 限制与供电

**Waveshare 控制板有 5 A 总电流上限，但 12 个舵机堵转要 32 A。**

**所以供电必须绕过控制板：**

```
电池 + ──┬── 16 AWG 粗线 ──→ 舵机 V（全部并联）
         ├── 16 AWG 粗线 ──→ 舵机 G（全部并联，与控制板共地）
         └── 细线 ────────→ 控制板 DC 输入（板子自身 20~50 mA）

舵机信号线（D）──→ 控制板信号输出
```

**⚠️ 固件侧的含义：** 电压采样采的是**电池总电压**（PA0 分压），不是控制板电压。所以电压读数反映真实电池状态。

### 3.4 关节零位与偏置（⭐ 核心概念）

```
舵机内部零位（编码器电气零点）  ←  硬件固定，改不了
        ↕  差值 = joint_offset[i]
关节坐标系零位（URDF 的 q = 0）  ←  由 CAD 装配姿态决定
```

**本项目的关节零位 = 弯腿站立姿态（即 URDF 的 `q = 0` 时机器人处于站立姿态）。**

**转换公式：**

```c
// 关节角（rad）→ 舵机位置（步数）
int16_t joint_to_servo(uint8_t idx, float q_rad) {
    // 关节角转步数：4096 步 / 2π rad
    float steps = q_rad * (4096.0f / (2.0f * 3.14159265f));
    // 加偏置，并乘方向（右腿可能反相）
    float s = g_joints[idx].dir * steps + g_joints[idx].offset;
    return (int16_t)(s + 0.5f);
}

// 舵机位置（步数）→ 关节角（rad）
float servo_to_joint(uint8_t idx, int16_t pos) {
    float s = (float)(pos - g_joints[idx].offset) * g_joints[idx].dir;
    return s * (2.0f * 3.14159265f / 4096.0f);
}
```

**⚠️ `dir` 字段：右腿的舵机安装方向可能和左腿相反，用 `+1 / -1` 处理，不要在上层代码里写 if。**

**⚠️ 标定流程见 §6。**

## 4. 软件架构

### 4.1 分层

```
┌──────────────────────────────────────────────────────────────┐
│  App 层                                                       │
│  ├─ app_main.c      主循环调度（100 Hz 节拍驱动）              │
│  ├─ app_mode.c      状态机：INIT / IDLE / STAND / ACTIVE /    │
│  │                        ESTOP / CALIB                       │
│  └─ app_safety.c    低压 / 超温 / 失联 / 超差 → 保护动作       │
├──────────────────────────────────────────────────────────────┤
│  Service 层                                                   │
│  ├─ servo_bus.c     舵机总线事务调度（核心，见配套文档）        │
│  ├─ servo_proto.c   STS 协议编解码 + 错误码                   │
│  ├─ joint.c         关节映射 / 偏置 / 限位 / 方向              │
│  ├─ imu.c           JY901P 解析（软件 I2C）                    │
│  ├─ battery.c       ADC → 电压 → 分级告警                     │
│  └─ link_pi.c       与树莓派的帧协议（见配套文档）              │
├──────────────────────────────────────────────────────────────┤
│  BSP 层                                                       │
│  ├─ bsp_uart.c      UART 初始化 + 中断 + 环形缓冲              │
│  ├─ bsp_softi2c.c   软件 I2C（PB8/PB9，开漏）                 │
│  ├─ bsp_tick.c      1 kHz 时基（TIM2）                        │
│  ├─ bsp_flash.c     标定参数持久化                             │
│  └─ bsp_gpio.c      LED / 心跳 / 预留足底开关                  │
└──────────────────────────────────────────────────────────────┘
```

**⚠️ 分层原则：**
- **BSP** 只碰 HAL/寄存器，不含业务逻辑
- **Service** 一个模块负责一个外设或一个概念，提供 `_init()` / `_poll()` / `_selftest()`
- **App** 只做调度、状态机、决策

### 4.3 主循环结构

```c
int main(void) {
    // ── 初始化 ──
    HAL_Init();
    SystemClock_Config();          // 72 MHz
    MX_GPIO_Init(); MX_DMA_Init(); MX_ADC1_Init();
    MX_USART1_UART_Init(); MX_USART2_UART_Init(); MX_USART3_UART_Init();

    bsp_tick_init();               // TIM2, 1 kHz
    bsp_uart_init();               // 开中断 + 环形缓冲
    bsp_flash_load_calib();        // 读标定参数
    joint_init();
    servo_bus_init();
    imu_init();
    battery_init();
    link_pi_init();

    app_init();                    // 状态机 → INIT

    // ── 主循环：由 1 kHz 节拍驱动状态机 ──
    uint32_t last_cycle = 0;
    while (1) {
        uint32_t now = bsp_tick_ms();

        // 高频任务（每圈都跑）
        servo_bus_poll();          // 推进舵机总线状态机
        link_pi_poll();            // 解析树莓派帧

        // 100 Hz 任务
        if (now - last_cycle >= 10) {
            last_cycle += 10;
            app_cycle_100hz();
        }

        // 低频任务（心跳灯、日志）
        app_housekeeping();
    }
}
```

### 4.4 ⭐ 100 Hz 周期时序

```
t=0.0 ms  ├─ 读上次 SyncRead 的结果 → 更新关节状态
          ├─ 读 IMU（软件 I2C，约 0.3 ms）
          ├─ 读 ADC 电池电压（DMA 后台完成，直接取）
t=0.5 ms  ├─ 组装 TEL_FAST 帧（85 B）→ 发给树莓派
t=0.6 ms  ├─ 进入"等待指令"状态（超时 4 ms）
t≈2.0 ms  ├─ 收到 CMD_JOINT（31 B）
          ├─ 解析 + 校验 CRC + 限幅
t=2.2 ms  ├─ SyncWrite 下发 12 个目标位置（440 µs，44 字节）
t=3.2 ms  ├─ 启动 syncRead 请求（200 µs，20 字节；回复不阻塞，由中断收）
t=3.3 ms  └─ 周期结束，回主循环

t=10.0 ms 下一周期开始（此时上次的 syncRead 数据应已收齐）
```

**⚠️ 关键设计：`syncRead` 是异步的 —— 发起后不阻塞，数据由 USART2 中断收进环形缓冲，下一个周期开始时才解析。**

**余量：约 6.7 ms（67%），健康。**

### 4.5 ⚠️ 中断优先级分配（待修改）

**当前 CubeMX 配置把三个 UART 都设成了抢占优先级 0 —— 需要改：**

| 中断 | 当前 | **建议** | 理由 |
|---|---|---|---|
| `DMA1_Channel1`（ADC） | 5 | 5 | 保持 |
| **`USART2`（舵机总线）** | 0 | **6** ⭐ | 1 Mbps，每字节 10 µs，丢字节=丢帧 |
| `USART1`（树莓派） | 0 | **7** | 允许丢帧（有 CRC + 序列号） |
| `USART3`（ESP32） | 0 | **8** | 非关键 |
| `TIM2`（1 kHz 节拍） | — | 9 | 调度用 |
| `SysTick` | 15 | 15 | 保持 |

**⚠️ 舵机总线优先级必须高于树莓派链路。**

**⚠️ 但更彻底的方案：USART2 用 DMA 接收，彻底摆脱中断丢字节风险。** 见配套文档《伺服总线模块设计》。

## 5. 各模块职责

### 5.1 `bsp_uart` —— UART 抽象

```c
typedef struct {
    UART_HandleTypeDef *huart;
    uint8_t  *rb_buf;       // 环形缓冲
    uint16_t  rb_size;
    volatile uint16_t head, tail;
    volatile uint32_t rx_overflow;   // ⚠️ 必须统计溢出，否则丢数据无感知
    volatile uint32_t rx_total;
} uart_port_t;

void     bsp_uart_init_all(void);
void     bsp_uart_write(uart_port_t *p, const uint8_t *d, uint16_t n);
uint16_t bsp_uart_read(uart_port_t *p, uint8_t *d, uint16_t n);   // 返回实际读出
uint16_t bsp_uart_available(uart_port_t *p);
void     bsp_uart_flush(uart_port_t *p);
```

**⚠️ 三个必须做的：**

| # | 要求 |
|---|---|
| 1 | **环形缓冲大小 ≥ 256 B**。原舵机库用 128 B，1 Mbps 下不够 |
| 2 | **必须有溢出计数器**，并在遥测里上报 |
| 3 | 提供 `flush()` —— 舵机总线每轮开始前要清空残留 |

**⚠️ 参考你之前 `Cat/BSP/uart_port.c` 的实现，那套 ISR + 环形缓冲可以直接复用。**

### 5.2 `servo_bus` —— 舵机总线调度（最复杂）

**详见配套文档《伺服总线模块设计.md》。这里只列接口：**

```c
typedef enum {
    BUS_IDLE, BUS_WRITING, BUS_WAIT_TURNAROUND,
    BUS_READING, BUS_DONE, BUS_TIMEOUT
} bus_state_t;

void servo_bus_init(void);
bool servo_bus_write_positions(const int16_t *pos_steps, uint8_t n);
bool servo_bus_read_states(uint8_t n);
void servo_bus_poll(void);                 // 主循环调用
bool servo_bus_is_busy(void);
const servo_feedback_t* servo_bus_get_feedback(void);
```

**⚠️ 主循环不阻塞等待，只轮询状态。** 这是保证 100 Hz 稳定的关键。

### 5.3 `joint` —— 关节映射

```c
typedef struct {
    uint8_t  servo_id;      // 总线 ID
    int8_t   dir;           // +1 / -1，方向
    int16_t  offset;        // 零点偏置（步数）
    int16_t  limit_min;     // 限位（步数）
    int16_t  limit_max;
    float    q_min_rad;     // 限位（弧度，便于上层用）
    float    q_max_rad;
    uint8_t  flags;         // BIT0=使能 BIT1=反装 BIT2=保留
} joint_cfg_t;

extern joint_cfg_t g_joints[12];       // 索引 = §3.2 的逻辑索引

void  joint_init(void);
int16_t joint_to_servo(uint8_t idx, float q_rad);
float   servo_to_joint(uint8_t idx, int16_t pos);
bool  joint_check_limit(uint8_t idx, float q_rad);
```

**⚠️ 关节限位（来自 URDF，必须一致）：**

| 关节类型 | lower | upper |
|---|---|---|
| 髋外摆 `*_hip` | 0° | **+40°** |
| 髋俯仰 `*_thigh` | −35° | **+90°** ⚠️ 见下方说明 |
| 膝 `*_calf` | −60° | **+60°** |

**⚠️ 关于 `*_thigh` 的 +90°（⚠️ 这里曾有一个错误结论，已修正）：**

```
❌ 旧说法（已证伪）："站立需要 +31.19° > 上限 +30°，站立姿态超出限位"
   错误来源：混淆了「大腿连杆相对竖直的绝对夹角」与「关节相对 CAD 零位的转角」

✅ 实际：q = 0 就是装配好的站立姿态，
        所以站立时 thigh 关节角 = 0，离 +30° 还有 30° 余量。
        仿真实测：机器人以原始 URDF 成功站立并行走。
```

**👉 采用 +90° 的理由：给摆腿留空间。**

**⚠️ 依据：训练用的 URDF 用的是 90°（`Sim/RL/urdf/robot_sim.urdf`），策略是在 90° 下训出来的。固件必须一致，否则真机上策略的摆腿幅度会被硬性削掉。**

**⚠️ 详见 [`docs/30-firmware.md`](../../docs/30-firmware.md) §3.1 与 [`archive/README.md`](../../archive/README.md) 勘误 1。**

### 5.4 `imu` —— JY901P

**⚠️ JY901P 内部做姿态融合，MCU 只需读结果。**

```c
typedef struct {
    float quat[4];      // w, x, y, z
    float gyro[3];      // rad/s
    float accel[3];     // m/s²
    float yaw, pitch, roll;
    uint32_t last_update_ms;
    uint32_t err_count;
} imu_state_t;
```

**⚠️ 关于"波特率"的说法（⚠️ 这里曾有一个概念错误，已修正）：**

```
❌ 旧说法（错误）："必须把 JY901P 的波特率设成 921600"
   错误原因：JY901P 走的是【软件 I2C】，I2C 器件没有"波特率"这个概念。
            921600 那个数字来自它【串口模式】的配置，与 I2C 模式无关。
```

**✅ 走 I2C 时真正要配的是这三个参数（都在 JY901P 上位机里设）：**

| 参数 | 说明 | 本项目的要求 |
|---|---|---|
| **I2C 器件地址** | JY901P 的从机地址 | 从模块手册确认（常见 0x50） |
| **输出速率 / 回传频率** | 模块多久更新一次寄存器 | **≥100 Hz**（匹配控制环） |
| **输出内容** | 哪些量参与回传 | 需要：四元数 + 角速度（加速度可选） |

**⚠️ 为什么"输出速率"是关键：**

```
如果 JY901P 只按 10 Hz 更新，而控制环按 100 Hz 去读，
就会读到同一份数据 10 次 —— 姿态观测变成阶梯状，策略会抖。
必须在模块上把输出速率提到 ≥100 Hz。
```

**⚠️ 软件 I2C 的实现注意：**

- **SCL 频率目标 100~400 kHz**（用示波器量，不要靠数 `__NOP()` 猜）
- PB8/PB9 已配成开漏（OD）+ 高速
- 需要外部 4.7 kΩ 上拉到 3.3 V（⚠️ 确认硬件已装）
- **开漏模式下不要用 `HAL_GPIO_WritePin` 输出高电平驱动** —— 靠外部上拉
- 72 MHz 下每次翻转的延时数量要按实测调整

**⚠️ 读一帧的时间预算：**

```
读四元数(8 B) + 角速度(6 B) = 14 B
I2C 每字节 9 位（含 ACK），加地址与寄存器开销约 20 B
@ 400 kHz → 约 0.45 ms
@ 100 kHz → 约 1.8 ms

⚠️ 若 SCL 只有 100 kHz，100 Hz 周期里 IMU 就占 1.8 ms（18%）—— 可接受但偏多。
   建议把 SCL 提到 400 kHz。
```

### 5.5 `battery` —— 电池监测

**硬件：PA0 接分压器（R1 = 100 kΩ，R2 = 22 kΩ，C1 = 100 nF）**

```c
// 分压比 = (100 + 20) / 20 = 6.000   （2026-10-18 更正，原写 22k）
#define BATT_DIV_NUM   122.0f
#define BATT_DIV_DEN    22.0f
#define ADC_VREF_MV   3300.0f     // ⚠️ 必须实测校准，见下
```

**⚠️ 两步标定（必须做）：**

```
第一步：万用表量 STM32 模块 3.3 V 引脚的真实值 → 填 ADC_VREF_MV
        （标称 3300 mV，实际可能 3260 ~ 3340）
第二步：对比固件读数和万用表量的电池电压 → 微调分压比
        目标：误差 < 50 mV
```

**电压分级（来自设计文档）：**

| 电压 | 行为 |
|---|---|
| > 10.5 V | 正常 |
| **10.5 V** | ⚠️ L1 警告：LED 慢闪 + 上报 |
| **9.9 V** | ⚠️ L2：上报 + 限制动作幅度 |
| **9.3 V** | 🔴 L3：卸载力矩 → 趴下 |

**⚠️ ADC 配置已是"连续转换 + DMA 循环"，直接读 DMA 缓冲区即可，不用软件触发。**

### 5.8 `app_safety` —— 安全机制

**⚠️ 这是最重要的模块，必须在 STM32 上独立完成。**

    SAFE_OK = 0,

    // 建议：如果高度 > 80 mm 用 A，否则用 B

## 6. ⭐ 关节零点标定

### 6.1 原理

**关节零位 = 弯腿站立姿态（由 CAD 装配姿态决定）。**

```
站立时，所有关节的逻辑角 q = 0
所以：joint_offset[i] = 站立时舵机 i 的读数
```

**⚠️ 这是本设计的优点 —— 标定姿态就是机器人自然站立的姿态，不需要特殊夹具，也不要把腿掰直（那会落在运动学奇异点上）。**

### 6.2 标定流程

```
① 把机器人放在水平地面上，让它自然站立（腿撑着机身）
② 上位机发送 CMD_START_CALIB
③ 固件进入 CALIB 状态：
     · 所有舵机设为【力矩卸载】
     · 机器人自然沉到最稳姿态
     · 等 1~2 秒让振荡停止
④ 依次读取 12 个舵机的当前位置
⑤ 存入 g_joints[i].offset
⑥ 写入 Flash（bsp_flash_save_calib()）
⑦ 退出 CALIB 状态
```

**精度：靠自重 ±2~3°。** 对 RL + 域随机化够用。

**⚠️ 如果要做更高精度（±0.5°），加一个定位块把机身托到站立髋高（约 122.7 mm）。**

### 6.3 Flash 存储布局

```c
#define CALIB_MAGIC      0x524C4341u    // "RLCA"
#define CALIB_VERSION    1

typedef struct {
    uint32_t magic;
    uint16_t version;
    uint16_t crc16;
    int16_t  offset[12];       // 零点偏置（步数）
    int8_t   dir[12];          // 方向
    int16_t  limit_min[12];
    int16_t  limit_max[12];
    uint16_t checksum;         // 全结构校验
} calib_data_t;
```

**⚠️ 上电时必须校验 magic 和 checksum，失败则用默认值并进入 CALIB 状态。**

**⚠️ STM32F103C8 的 Flash 页大小是 1 KB。标定数据放最后一页（0x0800FC00）。**

## 7. 舵机错误码处理

**STS 协议里 `getErr()` 返回的位定义（来自官方库 `SCServo.h`）：**

| 位 | 名称 | 含义 | 固件动作 |
|---|---|---|---|
| BIT0 | 电压错误 | 电压超范围 | 上报 |
| BIT1 | 角度错误 | 目标角超出限位 | 检查限幅逻辑 |
| BIT2 | 过温 | > 70 °C | **降级 + 上报** |
| BIT3 | 过流 | > 2 A | **上报** |
| BIT4 | 角度错误 | 位置反馈异常 | 检查接线 |
| BIT5 | 过载 | 负载超限 | **上报 + 可能限幅** |

**⚠️ 每次 SyncRead 后必须调用 `getErr()`，把非零错误码汇总上报给树莓派。** 这是 RL 训练时判断"真机异常"的关键信号。

## 8. 开发阶段与验收标准

```
┌─────────────────────────────────────────────────────────────┐
│ 阶段 A  配置修正与 BSP 层                                     │
│   产出：能编译、能烧写、串口能收发（自环或 USB-TTL）            │
│   验收：① LED 1 Hz 心跳  ② 三路 UART 自发自收 1 万字节无丢失   │
├─────────────────────────────────────────────────────────────┤
│ 阶段 B  servo_bus + servo_proto                              │
│   产出：能控 1 个舵机 → 再到 12 个                            │
│   验收：① 单舵机位置跟随  ② 12 舵机 SyncWrite 后全部到位       │
│         ③ syncRead 12 个反馈无丢帧，连续 1000 轮零错误        │
├─────────────────────────────────────────────────────────────┤
│ 阶段 C  imu + battery                                        │
│   产出：能稳定读 IMU 姿态和电池电压                            │
│   验收：① IMU 100 Hz 无丢帧  ② 电压读数与万用表差 < 50 mV     │
├─────────────────────────────────────────────────────────────┤
│ 阶段 D  link_pi                                              │
│   产出：与 PC 端 Python 模拟器通信                            │
│   验收：① 100 Hz 稳定收发  ② 注入丢帧/错帧能正确检测并恢复     │
│         ③ 链路断开 30 ms 内进入 ESTOP                        │
├─────────────────────────────────────────────────────────────┤
│ 阶段 E  标定 + app_mode + app_safety                         │
│   产出：完整状态机 + 标定流程 + 安全机制                       │
│   验收：① 标定后 q=0 时机器人站立  ② 各项安全阈值触发正确      │
├─────────────────────────────────────────────────────────────┤
│ 阶段 F  与树莓派联调                                          │
│   验收：① 100 Hz 闭环延迟 < 5 ms  ② 连续运行 30 min 无异常    │
└─────────────────────────────────────────────────────────────┘
```

**⚠️ 阶段 B 和 D 可以并行**（一个调舵机、一个调通信），互不阻塞。

**⚠️ 但阶段 A 必须先做完** —— 时钟/中断/缓冲是后面所有层的地基。

## 9. 已知风险与对策

| # | 风险 | 后果 | 对策 |
|---|---|---|---|
| 1 | **20 KB RAM 不够用** | 编译失败 / 运行时栈溢出 | 静态分配一切；禁用 malloc；栈保持 1 KB；用 `-Os` 优化 |
| 2 | **1 Mbps 下丢字节** | 舵机帧损坏，控制异常 | 环形缓冲 ≥256 B；优先 DMA；统计溢出 |
| 3 | **软件 I2C 时序不准** | IMU 读失败 | 用示波器量 SCL 频率（目标 100~400 kHz）；必要时改用硬件 I2C |
| 4 | **舵机 ID 冲突** | 总线混乱 | 逐个设置 ID；上电先扫描并校验 |
| 5 | **原舵机库的单字节超时** | 舵机失联时阻塞整个周期 | 外层加整帧超时（见配套文档） |
| 6 | **`*_thigh` 限位不够** | 腿伸不直 | 在 URDF/仿真侧确认后同步修改 |
| 7 | **`syncReadBegin` 的 malloc** | 每次调用分配内存 → 碎片 | 改成静态缓冲 |
| 8 | **Flash 写入期间中断** | 写失败 | 写 Flash 前关中断，写完开；或放到 IDLE 状态做 |
