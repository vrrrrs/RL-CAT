# 伺服总线模块设计（servo_bus / servo_proto）

> **文档编号**：FW-SERVO-001
> **版本**：v1.0
> **日期**：2026-10-09
> **面向对象**：负责舵机通信层的固件开发者
> **配套文档**：`固件设计书.md`、`协议规范_树莓派通信.md`
> **重要程度**：⭐⭐⭐ **这是整个固件最复杂的模块**

---

## 0. 为什么这个模块最复杂

```
① 1 Mbps 下每字节只有 10 µs —— 错过一个字节就丢一帧
② 12 个舵机共享一条总线，要 SyncWrite/SyncRead 批量操作
③ 官方库有 4 个已知缺陷必须修
④ 半双工总线的收发切换有时序要求
⑤ 不能阻塞主循环（100 Hz 节拍要保住）
```

## 1. 硬件与物理层

### 1.1 连接拓扑

```
STM32F103                        Waveshare                   12 × ST-3215
USART2 (PA2/PA3)                 Bus Servo Adapter (A)
┌──────────┐                    ┌──────────────┐            ┌──────────┐
│  PA2 TX  ├───────────────────→│ RX           │            │          │
│  PA3 RX  │←───────────────────┤ TX           │            │          │
│          │                    │              │            │          │
│   GND    ├────────────────────┤ GND          ├───────────→│ 信号 D   │
└──────────┘                    │              │            │          │
                                │ 跳线：A 位 ⚠️ │            │          │
                                └──────────────┘            └──────────┘
                                        ▲
                                        │ 细线（20~50 mA）
                                      电池 DC 输入

        电池 + ──16 AWG 粗线──┬──────────────────────────────→ 舵机 V（全部并联）
        电池 - ──16 AWG 粗线──┴──────────────────────────────→ 舵机 G（全部并联）
```

### 1.2 ⚠️ 关键硬件要点

| # | 要点 | 说明 |
|---|---|---|
| 1 | **控制板跳线必须在 A 位** | 跳错会导致电平/协议不匹配（A = UART 控制，B = USB 控制） |
| 2 | **接线是「直连」**：RX→RX、TX→TX | ⚠️ 控制板端子丝印**按 MCU 侧标注**，所以照丝印一对一接。见 [Waveshare 官方接线文档](https://docs.waveshare.com/Bus_Servo_Adapter_A/Product-Wiring-Example) |
| 3 | **控制板只供 20~50 mA** | 舵机动力从粗线直供，绕过控制板（其 5 A 上限撑不住 12 舵机堵转的 32 A） |
| 4 | **必须共地** | 舵机 G、控制板 GND、STM32 GND 必须连在一起 |
| 5 | **USART2 是全双工，不要开 HDSEL** | 半双工是舵机侧总线的事，由控制板内部处理 |

**⚠️ 对照：USART1 ↔ 树莓派那条是【标准交叉】（TX→RX、RX→TX）。两条链路接法不同，接线时别搞混。**

### 1.3 USART2 配置参数

| 参数 | 值 |
|---|---|
| 波特率 | **1 000 000** |
| 数据位 | 8 |
| 停止位 | 1 |
| 校验 | 无 |
| 模式 | **全双工（`UART_MODE_TX_RX`）** |
| 流控 | 无 |
| 过采样 | 16 |

**⚠️ 72 MHz 下，APB1 = 36 MHz，1 Mbps 需要 `36000000 / 1000000 = 36` 分频，完美整除，误差 0%。这是把时钟修到 72 MHz 的额外好处。**

## 2. STS 协议要点

### 2.1 帧结构

```
┌──────┬──────┬──────┬──────┬────────────┬──────┐
│ 0xFF │ 0xFF │  ID  │ LEN  │ INSTR + P  │ CHK  │
└──────┴──────┴──────┴──────┴────────────┴──────┘
```

| 字段 | 说明 |
|---|---|
| 头 | 固定 `0xFF 0xFF` |
| ID | 舵机 ID（0xFE = 广播） |
| LEN | **从 INSTR 到 CHK 之前的字节数**（= 指令参数长度 + 2） |
| INSTR | 指令码，见 §2.2 |
| P... | 参数 |
| CHK | 校验和 = `~(ID + LEN + INSTR + 所有参数) & 0xFF` |

### 2.2 用到的指令码

| 码 | 名称 | 用途 |
|---|---|---|
| `0x01` | PING | 探测舵机是否在线 |
| `0x02` | READ | 读单个舵机寄存器 |
| `0x03` | WRITE | 写单个舵机寄存器 |
| `0x04` | REG_WRITE | 异步写（等 ACTION） |
| `0x05` | ACTION | 触发 REG_WRITE |
| **`0x83`** | **SYNC_WRITE** | **批量同时写多个舵机** ⭐ |
| **`0x82`** | **SYNC_READ** | **批量读多个舵机**（不同固件版本可能是 `0x92`）⭐ |

**⚠️ `SYNC_READ` 的指令码在不同固件版本里不一样（0x82 / 0x92）。** 必须用官方库的 `INST_SYNC_READ` 宏，不要硬编码。如果读不到数据，先确认这个码。

**⚠️⚠️ 实现陷阱（2026-10-10 补）：`0x83` 与 `0x82` 的同一个参数字段含义不同。**

```
SYNC_WRITE (0x83)： 0xFF 0xFF 0xFE LEN 0x83 addr 每舵机【写入字节数】 ID1 D1L D1H ...
                    此字段受寄存器块大小限制（写位置就是 2）

SYNC_READ  (0x82)： 0xFF 0xFF 0xFE LEN 0x82 addr 每舵机【要读的字节数】 ID1 ID2 ...
                    ⚠️ 此字段可以远大于 2 —— 本模块要读 9 字节的反馈块（位置2+速度2+负载2+电压1+温度1+移动1）
```

**⚠️ 把 SyncWrite 的 "长度 ≤ 4" 限制套到 SyncRead 上会直接报参数错误（本项目实测踩到过）。
两者必须分别校验：写 ≤ 4，读按需（本项目 9）。**


### 2.3 用到的寄存器地址

**⭐ 以下地址全部来自官方 `ST.h`（已核实，可直接使用）：**

| 地址 | 宏名 | 字节 | 说明 |
|---|---|---|---|
| **40** | `SMS_STS_TORQUE_ENABLE` | 1 | **力矩使能**（0=卸载，1=使能）|
| **41** | `SMS_STS_ACC` | 1 | 加速度 |
| **42** | `SMS_STS_GOAL_POSITION_L` | 2 | **目标位置** ⭐ |
| 44 | `SMS_STS_GOAL_TIME_L` | 2 | 运行时间 |
| **46** | `SMS_STS_GOAL_SPEED_L` | 2 | **运行速度**（步/秒）|
| **55** | `SMS_STS_LOCK` | 1 | 锁标志（写 0 才能改 ID/偏置）|
| **56** | `SMS_STS_PRESENT_POSITION_L` | 2 | **当前位置反馈** ⭐ |
| 58 | `SMS_STS_PRESENT_SPEED_L` | 2 | 当前速度 |
| 60 | `SMS_STS_PRESENT_LOAD_L` | 2 | 当前负载（bit10 = 方向）|
| **62** | `SMS_STS_PRESENT_VOLTAGE` | 1 | 电压（0.1 V 单位）|
| **63** | `SMS_STS_PRESENT_TEMPERATURE` | 1 | 温度（°C）|
| 66 | `SMS_STS_MOVING` | 1 | 移动标志 |
| 69 | `SMS_STS_PRESENT_CURRENT_L` | 2 | 电流 |

**EPROM 区（改这些要先写 `SMS_STS_LOCK = 0`）：**

| 地址 | 宏名 | 说明 |
|---|---|---|
| 3–4 | `SMS_STS_MODEL_L/H` | 型号（只读）|
| **5** | `SMS_STS_ID` | **舵机 ID** |
| **6** | `SMS_STS_BAUD_RATE` | **波特率索引**（0 = 1 Mbps）|
| 9–12 | `SMS_STS_MIN/MAX_ANGLE_LIMIT_L/H` | 角度限位 |
| 26/27 | `SMS_STS_CW/CCW_DEAD` | 死区 |
| **31–32** | `SMS_STS_OFS_L/H` | **中位偏置** ⭐ 标定用 |
| 33 | `SMS_STS_MODE` | 模式 |

**⚠️ 波特率索引（地址 6）：**

```
0 = 1 Mbps      1 = 0.5 Mbps    2 = 250 k      3 = 128 k
4 = 115200      5 = 76800       6 = 57600      7 = 38400
```

**出厂默认通常是 `0`（1 Mbps），正好匹配我们的配置。但**必须逐个确认**，因为别人用过的舵机可能被改过。**

**⚠️ 读到多字节量时注意小端：`L` 是低字节，`H` 是高字节。**

### 2.4 反馈帧格式

```
┌──────┬──────┬──────┬──────┬──────┬──────────┬──────┐
│ 0xFF │ 0xFF │  ID  │ LEN  │ ERR  │  DATA    │ CHK  │
└──────┴──────┴──────┴──────┴──────┴──────────┴──────┘
```

**⚠️ 反馈帧比指令帧多一个 `ERR` 字节（在 LEN 之后）。这是最常见的解析错误来源。**

### 2.5 错误码（`ERR` 字节）

| 位 | 名称 | 含义 |
|---|---|---|
| BIT0 | 电压错误 | |
| BIT1 | 角度错误 | 目标角超限 |
| BIT2 | **过温** | > 70 °C |
| BIT3 | **过流** | > 2 A |
| BIT4 | 角度错误 | 反馈异常 |
| BIT5 | **过载** | |

**⚠️ 每次 SyncRead 后必须检查 ERR，非零要上报给树莓派（见协议文档 §4.6）。**

## 3. 官方库的四个缺陷（⚠️ 必须修）

**官方库位置**：`reference/servo/STServoBCL_keil_f103/`（相对项目根目录 `RL-CAT/`）

**官方库文件清单（已核实）：**

| 文件 | 大小 | 内容 | 处理 |
|---|---|---|---|
| `SCServo.h` | 177 B | 只是聚合头，include 三个 | 不改 |
| `INST.h` | 403 B | 指令码宏 | 不改 |
| `ST.h` | 2793 B | 寄存器地址宏 + 应用层函数原型 | 不改（结构不动） |
| `SC.h` | 2005 B | 协议层原型 | 不改 |
| `SC.c` | 8025 B | 协议层（校验、读写包、syncRead） | **改 1 处**（malloc） |
| `SCSerail.c` | **1504 B** | **⚠️ 实际是串口底层**（名字拼错了，应为 SCSerial） | **改 2 处**（超时语义、缓冲） |
| `ST.c` | 4993 B | 应用层（WritePosEx / SyncWritePosEx / 反馈解析） | 改 1 处（返回值） |
| **`uart.c` / `uart.h`** | 4244 B / 228 B | 基于 **StdPeriph** 的串口驱动 | **⚠️ 必须整体替换** |

**⚠️ 关键陷阱：`SC.c` 和 `SCSerail.c` 是【两个不同的文件】。**
- `SC.c` = 协议层（组帧、校验、`syncReadBegin`）
- `SCSerail.c` = 串口底层（`readSC`、`readSCTimeOut`、`writeSC`、`SCDelay`、`IOTimeOut` 定义）

**搜"超时"相关代码要去 `SCSerail.c`，不是 `SC.c`。** 这点很容易搞错。

### 缺陷 1：超时是"每收到一字节就重置"，不是整帧超时

**⚠️ 这个缺陷在 `SCSerail.c` 里（不是 `SC.c`）。官方原码：**

```c
// SCSerail.c
uint32_t IOTimeOut = 5000;                  // 每字节超时计数

int readSC(unsigned char *nDat, int nLen) {
    int Size = 0; int ComData; uint32_t t_user = 0;
    while (1) {
        ComData = Uart_Read();
        if (ComData != -1) {
            if (nDat) nDat[Size] = ComData;
            Size++;
            t_user = 0;                     // ⚠️ 每收到一字节就清零
        }
        if (Size >= nLen) break;
        t_user++;
        if (t_user > IOTimeOut) break;      // 连续 5000 次空轮询才超时
    }
    return Size;
}
```

**⚠️ 后果：** `t_user` 在**每收到一个字节时清零**，所以这是"字节间最大间隔"，不是整帧超时。

某字节一直不来时，要空转 5000 次 `Uart_Read()` 才退出。在 72 MHz 下，一次空轮询约 0.1~0.2 µs，所以**单个字节的超时就约 0.5~1 ms**。

**如果 12 个舵机全失联，每次 `readSC` 都要等满这个时间，累计 6~12 ms，直接吃掉整个 10 ms 周期。**

**修复：外层加整帧超时（用硬件计时，不靠循环计数）。**

```c
// servo_bus.c
#define FRAME_TIMEOUT_US   3000        // 整帧 3 ms（1 Mbps 下 12 舵机只需 1.53 ms）

bool servo_bus_read_states(uint8_t n) {
    uint32_t t0 = bsp_micros();
    // 发起 syncRead
    while (bus_is_receiving()) {
        if (bsp_micros() - t0 > FRAME_TIMEOUT_US) {
            s_stats.timeout++;
            bus_abort();
            return false;
        }
    }
    return true;
}
```

### 缺陷 2：`syncReadBegin` 里的 `malloc`

```c
// 官方 SC.c
int syncReadBegin(u8 id, u8 len, u8 *data) {
    // ...
    u8 *buf = (u8*)malloc(...);        // ⚠️ 每次调用都分配
}
```

**⚠️ 后果：** 20 KB RAM 的 MCU 上反复 malloc 会导致内存碎片，最终分配失败。而且堆只有 512 B。

**修复：改成静态缓冲。**

```c
static uint8_t s_syncread_buf[SCS_RX_BUF_SIZE];   // 512 B，静态
```

### 缺陷 3：环形缓冲只有 128 B

**1 Mbps 下，12 个舵机的一次完整回复约 12 × 8 = 96 字节，加上指令回显和噪声，128 B 会溢出。**

**修复：改成 512 B，并加溢出计数。**

```c
#define SCS_RX_BUF_SIZE   512
volatile uint32_t g_rx_overflow_cnt;    // ⚠️ 必须统计
```

### 缺陷 4：`SyncWritePosEx` 返回 `void`

**没法知道写入是否成功。**

**修复：改为返回 `bool`，并暴露 `getErr()` 的结果。**

```c
bool servo_bus_write_positions(const int16_t *pos, uint8_t n);
uint8_t servo_bus_get_last_err(void);      // 最近一次读到的 ERR 汇总
```

## 4. 模块接口设计

### 4.1 状态机

```c
typedef enum {
    BUS_IDLE = 0,          // 空闲
    BUS_WRITE_REQ,         // 请求写
    BUS_WRITING,           // 正在发送 SyncWrite（阻塞，约 1 ms）
    BUS_READ_REQ,          // 请求读
    BUS_READING,           // 正在接收（由中断/DMA 驱动）
    BUS_PARSING,           // 解析反馈
    BUS_DONE,              // 本轮完成
    BUS_TIMEOUT,           // 超时
    BUS_ERROR,             // 总线错误
} bus_state_t;
```

**⚠️ `BUS_WRITING` 是唯一允许阻塞的阶段（约 1 ms，可接受）。`BUS_READING` 必须异步。**

### 4.2 数据结构

```c
// 舵机反馈（12 个）
typedef struct {
    int16_t  position;      // 当前位置（步数）
    int16_t  speed;         // 当前速度
    int16_t  load;          // 当前负载（bit10 是方向位）
    uint8_t  voltage;       // 电压（0.1 V）
    uint8_t  temperature;   // 温度（°C）
    uint8_t  moving;        // 移动标志
    uint8_t  err;           // 错误码
    uint8_t  valid;         // 本次是否读到有效数据
} servo_feedback_t;

// 总线统计（诊断用）
typedef struct {
    uint32_t tx_frames;
    uint32_t rx_frames;
    uint32_t crc_errors;
    uint32_t timeouts;
    uint32_t rx_overflow;       // ⚠️ 关键指标
    uint32_t err_flags_accum;   // ERR 累计
} bus_stats_t;
```

### 4.3 对外接口


## 5. ⭐ 推荐的接收方案：DMA + IDLE 中断

### 5.1 为什么不用纯中断

**1 Mbps 下每 10 µs 一个字节 —— 12 个舵机一次回复 96 字节 = 0.96 ms 内 96 次中断。** 如果此时正好有更高优先级中断（如 SysTick），会丢字节。

### 5.2 方案对比

| 方案 | 优点 | 缺点 | 推荐度 |
|---|---|---|---|
| **纯中断 + 环形缓冲** | 实现简单，写起来快 | 高负载下可能丢字节 | ⭐⭐ |
| **DMA 循环接收 + IDLE 中断** ⭐ | **零丢字节，CPU 负担极低** | 要用 DMA1 通道，配置稍复杂 | ⭐⭐⭐ |
| DMA 单次接收 + 完成中断 | 也可靠 | 每帧要重启 DMA | ⭐⭐ |

**👉 推荐 DMA + IDLE。** DMA1_Channel6 是 USART2_RX 的默认映射。

### 5.3 DMA + IDLE 的工作方式

```c
// 初始化：DMA 循环模式，永远在收
HAL_UART_Receive_DMA(&huart2, s_dma_buf, DMA_BUF_SIZE);   // 循环

// IDLE 中断：一帧结束时触发
void USART2_IRQHandler(void) {
    if (__HAL_UART_GET_FLAG(&huart2, UART_FLAG_IDLE)) {
        __HAL_UART_CLEAR_IDLEFLAG(&huart2);
        // 计算本次收到的字节数
        uint16_t pos = DMA_BUF_SIZE - __HAL_DMA_GET_COUNTER(&hdma_usart2_rx);
        uint16_t n = (pos - s_last_pos + DMA_BUF_SIZE) % DMA_BUF_SIZE;
        // 把这 n 个字节拷进环形缓冲（或直接交给解析器）
        servo_rx_isr(s_dma_buf + s_last_pos, n);
        s_last_pos = pos;
    }
    HAL_UART_IRQHandler(&huart2);   // 处理错误标志
}
```

**⚠️ 三个必须注意的点：**

| # | 注意 |
|---|---|
| 1 | **IDLE 中断需要在 `MX_USART2_UART_Init` 之后手动使能**（CubeMX 不生成）：`__HAL_UART_ENABLE_IT(&huart2, UART_IT_IDLE);` |
| 2 | **`DMA_BUF_SIZE` 要足够大**（建议 512 B），且 DMA 循环模式永远不会停 |
| 3 | **IDLE 中断里不要做耗时操作** —— 只把数据搬走或置标志，解析放到主循环 |

### 5.4 ⚠️ 半双工 turnaround 时序

**虽然 MCU 侧是全双工，但舵机总线是半双工的，控制板需要时间切换收发方向。**

```
STM32 发完 SyncWrite 最后一个字节
        │
        ├─ 等 50~100 µs（turnaround 时间）⚠️
        │   （让控制板把总线方向从"发"切到"收"）
        │
        └─ 发起 syncRead
```

**⚠️ 这个延时太短会导致丢首字节，太长会浪费周期。**

**⭐ 好消息：官方库已经有这个延时了。** `SCSerail.c` 里的 `SCDelay()`：

```c
// SCSerail.c —— 官方原有实现
void SCDelay(void) {
    uint8_t i = 180;
    while(i--){}          // 注释写的是 0.056*i (us)，即约 10 µs @72MHz
}

void rFlushSC(void) {     // 每次接收前调用
    SCDelay();
    Uart_Flush();
}
```

**⚠️ 但这个 10 µs 是【按 72 MHz 调的】—— 如果系统时钟不是 72 MHz，延时会不准。** 现在我们时钟是 72 MHz，所以合适。

**⚠️ 注意 `rFlushSC()` 会在【每次读写操作】前都延时 10 µs。** 12 个舵机做 syncRead 时，每个包前都有一次，累计约 120 µs。**这个开销要算进周期预算。**

**⚠️ 如果实测发现丢首字节，把 `i = 180` 改成 `i = 360`（约 20 µs）。**

**⚠️ 另一个省事的做法：`SyncWrite` 之后先做别的事（读 IMU、ADC），再发起 syncRead。反正周期里有 5 ms 余量。**

## 6. SyncWrite / SyncRead 的时序

### 6.1 SyncWrite 帧构造

```
SyncWrite 12 个舵机的位置（地址 42，长度 2）:

┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬─────────────┬──────┐
│ 0xFF │ 0xFF │ 0xFE │ LEN  │ 0x83 │ 0x2A │ 0x02 │ ID1 D1L D1H │ ...  │
│      │      │ 广播 │      │SYNC_W│ 地址 │ 长度 │  舵机1 数据  │      │
└──────┴──────┴──────┴──────┴──────┴──────┴──────┴─────────────┴──────┘

LEN = 4 + 3×12 = 40
总长 = 2 + 1 + 1 + 40 + 1 = 45 字节
@1 Mbps（含起止位） = 45 × 10 µs = 450 µs
```

**⚠️⚠️ 勘误（2026-10-10，由单元测试核实）：上面这 4 行自相矛盾，实际是 44 字节 / 440 µs。**

```
帧结构： H0 H1 ID LEN [LEN 个字节，其中最后 1 字节是 CHK]
        ⇒ 帧长 = 2(头) + 1(ID) + 1(LEN) + LEN = LEN + 4

LEN   = 参数数 + 2 = (addr 1 + item_len 1 + 12×3) + 2 = 40
帧长  = 40 + 4 = 44 字节          ← 不是 45
@1 Mbps = 44 × 10 µs = 440 µs     ← 不是 450 µs
```

**⚠️ 原文的 "45" 是按 `LEN + 5` 算的，与本文件自己给出的 LEN 定义（"从 INSTR 到 CHK 之前的字节数"）不自洽。**

**✅ 校验方式：** 跑 `firmware/tools/test-host.ps1`，`[Feetech STS protocol]` 一节直接断言 SyncWrite 12 舵机帧长 = **44**。

**⚠️ 之前估算的 "1.02 ms" 是按官方库的 `SyncWritePosEx`（可能带额外延时）算的。实际串行时间只要 440 µs（44 字节）。**

### 6.2 SyncRead 帧构造与响应

```
请求帧:
┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────────┬──────┐
│ 0xFF │ 0xFF │ 0xFE │ LEN  │ 0x82 │ 0x38 │ 0x0E │ ID1..ID12│ CHK  │
│      │      │ 广播 │      │SYNC_R│ 起始 │ 读长 │  12 个ID │      │
└──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────────┴──────┘
总长 = 2+1+1+ (2+1+1+12) +1 = 21 字节 → 210 µs

⚠️ 勘误（同上）：LEN = 2+12+2 = 16，帧长 = LEN + 4 = 20 字节 → 200 µs。
   原文的 "21" 同样是 LEN+5 的算法。单元测试断言 = 20。


响应帧（每个舵机一帧）:
┌──────┬──────┬──────┬──────┬──────┬──────────┬──────┐
│ 0xFF │ 0xFF │  ID  │ LEN  │ ERR  │  DATA    │ CHK  │
└──────┴──────┴──────┴──────┴──────┴──────────┴──────┘
读 14 字节时：LEN = 14 + 2 = 16，帧总长 = 2+1+1+1+14+1 = 20 字节
12 帧 = 240 字节 → 2.4 ms @ 1 Mbps
```

**⚠️ 实际总时间取决于读多长。如果只读位置（2 字节），12 帧只要约 0.5 ms。**

**建议读出：位置(2) + 速度(2) + 负载(2) + 电压(1) + 温度(1) + 移动(1) = 9 字节。** 从地址 56 读 9 字节。

```
每帧: 2+1+1+1+9+1 = 15 字节 → 150 µs
12 帧 = 1.8 ms
```

**⚠️⚠️ 勘误与实现注意（2026-10-10，由单元测试核实）：**

```
① 上面「读 14 字节 → 20 字节」那一行与本节自己的帧结构图不符：
   ⚠️ 反馈帧【比指令帧多一个 ERR 字节】。正确算式是
        H0 H1 ID LEN ERR DATA... CHK
        帧总长 = 数据长度 + 6          ← 不是 +5
   读 14 字节 → 20 字节（数字凑巧对，但 +5 的思路是错的）
   读  9 字节 → 15 字节（✅ 本节下面那段是对的）

② 实现时曾把「每帧总长」写成 数据长度 + 5 = 14，少了 CHK 那一个字节，
   导致帧长度检查 n < 15 必然失败、12 帧反馈被【全部丢弃】。
   已在 rlca_sts.h 里用 STS_FB_FRAME_LEN = 6 + STS_FB_DATA_LEN 明确，
   并有单测断言（firmware/tests/host/test_pure_logic.c 的 STS 一节）。

③ 12 帧 = 12 × 15 = 180 字节 → 1.8 ms（不是 240 字节 / 2.4 ms；
   240 是按"读 14 字节"算的，与实际采用的 9 字节方案不符）。
```

**⚠️ 这有点长。如果嫌慢，可以只读位置（2 字节），其他量低频读（如 10 Hz）。**

### 6.3 时序总览（100 Hz 周期）

```
t=0.0 ms   ├─ 解析上轮 syncRead 结果
           ├─ 读 IMU / ADC
t=0.5 ms   ├─ 发 TEL_FAST
t=2.0 ms   ├─ 收到 CMD_JOINT
t=2.2 ms   ├─ SyncWrite 下发（440 µs，44 字节）
t=2.65 ms  ├─ turnaround 等待（SCDelay 约 10 µs）
t=2.75 ms  ├─ 发 SyncRead 请求（200 µs，20 字节）
t=2.96 ms  ├─ 12 个舵机陆续回复（约 1.8 ms）
t=4.8 ms   ├─ 数据收齐（下一个周期开始时解析）
t=10.0 ms  └─ 下一周期
```

**余量：5.2 ms（52%），健康。**

## 7. 与官方库的集成方式

### 7.1 目录结构

```
Middlewares/SCServo/
├── INST.h                ← 官方，不改
├── SC.c / SC.h           ← 官方，改 3 处（见 §3）
├── ST.c / ST.h           ← 官方，改 1 处（SyncWritePosEx 返回值）
├── SCServo.h             ← 官方，不改
└── uart_port.c / .h      ← ⚠️ 我们自己写，替换官方 uart.c
```

### 7.2 `uart_port.c` 需要实现的 4 个函数（⚠️ 已从 `uart.h` 核实）

**官方 `uart.c` 用的是 StdPeriph 库（与 HAL 冲突），必须整体替换。**

**⭐ 确切签名（来自 `SCSLib/uart.h`，照抄即可）：**

```c
#ifndef _UART_H
#define _UART_H
#include <stdint.h>

void    Uart_Init(uint32_t baudRate);        // 初始化串口
void    Uart_Flush(void);                    // 清空接收缓冲
int16_t Uart_Read(void);                     // ⚠️ 读【单个字节】，无数据返回 -1
void    Uart_Send(uint8_t *buf, uint8_t len);// 发送 len 字节

#endif
```

**⚠️⚠️ 三个关键点（很容易写错）：**

| # | 要点 |
|---|---|
| 1 | **`Uart_Read()` 每次只读 1 个字节，返回 `int16_t`**，不是"读一个缓冲区并返回长度"。空时返回 **`-1`** |
| 2 | **`Uart_Send` 的 len 是 `uint8_t`**（最大 255），不是 `int`。SyncWrite 帧 44 字节，够用 |
| 3 | **`Uart_Init` 返回 `void`**，不返回状态 |

**⚠️ 官方 `uart.c` 里自带 `USART1_IRQHandler` / `USART2_IRQHandler` —— 会和 CubeMX 生成的 `stm32f1xx_it.c` 里的同名函数冲突。所以是"替换"而不是"并存"。**

**官方 `uart.c` 的环形缓冲只有 128 B（`%128` 硬编码）。我们的实现要改成 512 B，并加溢出计数。**

**⚠️ 另一个隐蔽问题：官方 `readSC` 在 `Uart_Read()` 返回 -1 时会立刻重试，没有 `__NOP()` 或延时。** 这会让循环以 CPU 全速空转。我们可以在自己的实现里保留这个行为（它保证了响应速度），但要用硬件计时器而不是循环计数来做超时。

### 7.3 集成到 servo_bus 的方式

**两种思路：**

| 思路 | 做法 | 评价 |
|---|---|---|
| **A. 直接调官方 API** | `servo_bus_write_positions()` 内部调 `SyncWritePosEx()` | 快，但受官方缺陷影响 |
| **B. 自己实现 SyncWrite/SyncRead** | 自己组帧、自己发、自己解 | 完全可控，但要重写约 200 行 |

**👉 建议 A + 修缺陷。** 官方库的帧构造逻辑是对的，只要修掉 §3 的四个缺陷，加上外层整帧超时，就够用了。自己重写反而容易引入协议错误。

## 9. ⚠️ 常见坑与排查

| 现象 | 可能原因 | 排查 |
|---|---|---|
| **完全收不到反馈** | ① 跳线不在 A 位 ② TX/RX 接反 ③ `SYNC_READ` 指令码不对 | 先 Ping 单个舵机 |
| **能写不能读** | TX 通了 RX 没通 | 检查 PA3 接线和 RX 中断使能 |
| **偶发丢字节** | 环形缓冲太小 / 中断优先级低 | 检查 `rx_overflow` 计数 |
| **首字节丢失** | turnaround 时间不足 | 把 §5.4 的等待从 100 µs 加到 200 µs |
| **舵机不动但无错误** | 力矩未使能 / 速度设为 0 | 检查 `TORQUE_LIMIT` 和 `MOVING_SPEED` |
| **舵机抖动** | 目标位置频繁小幅变化 | 这是正常的（RL 输出），可以在固件加小死区 |
| **位置反馈跳变** | 多圈回绕（0↔4095） | 需要处理回绕，做连续性判断 |
| **`malloc` 失败** | 官方库缺陷 2 | 改成静态缓冲 |
| **周期被拉长到 30 ms** | 官方库缺陷 1 | 加外层整帧超时 |

**⚠️ 位置反馈回绕的处理：**

```c
// 4096 步一圈，如果相邻两次读数差超过 2048，认为是回绕
int16_t delta = pos_new - pos_old;
if (delta > 2048)  delta -= 4096;
if (delta < -2048) delta += 4096;
```
