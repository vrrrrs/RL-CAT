## 为什么要有这份文档

**开源项目里，贡献者最常问的不是"这是什么"，而是"为什么不那样做"。**

**这份文档把"已考虑过的方案"和"否决理由"记录下来，避免：**

```
① 后来者重复讨论已否决的方案
② 后人不知道某个设计是有意选择还是历史遗留，误改
③ 决策的上下文丢失，导致"看起来没道理"的设计被推翻
```

**⚠️ 与 `archive/` 的区别：这里是【结论】，归档文档是【过程】。**

## DD-01：选择 Feetech ST-3215-C018（而不是其他舵机）

**问题**：12 个自由度需要 12 个带位置反馈的执行器。

**选择**：**Feetech ST-3215-C018（12V 版）**

**理由：**

| 因素 | 说明 |
|---|---|
| **必须有位置反馈** | PWM 舵机（如 MG996R）没有位置反馈 → RL 观测缺 `q, q̇` → **根本做不了强化学习** |
| **性价比** | 12 个约 ¥2500 级别；Dynamixel XM430-W350-T 性能更好但约 ¥25000，是 10 倍 |
| **12V 版必须** | C001 / C044 是 7.4V 版，用 3S 会被过压保护切断 |
| 编码器类型 | 12-bit 磁编码器（**不是电位器**）—— 无磨损、寿命长 |
| 总线协议 | 半双工串口，一条线带 12 个，布线简单 |

**代价：**

```
· 需要额外的控制板（Waveshare Bus Servo Adapter）
· 控制板有 5 A 电流上限 → 必须外部分流（见 DD-03）
· 官方库有 4 个缺陷需要修（见 firmware/doc/伺服总线模块设计.md §3）
```

**否决的方案：**

| 方案 | 否决理由 |
|---|---|
| PWM 舵机（MG996R 等） | **无位置反馈** → 观测缺 `q, q̇`，做不了 RL |
| Hiwonder HTS-35H | 官方页面标注「进口高精度**电位器**」→ 磨损 |
| LX-824HV | 同上，电位器反馈 |
| Dynamixel XM430-W350-T | 性能好，但价格是 C018 方案的 **10 倍** |

## DD-02：用 STM32 做下位机（而不是只用树莓派）

**问题**：能否只用树莓派直接控舵机？

**选择**：**树莓派（推理）+ STM32（实时控制）双芯片架构**

**理由：**

| 因素 | 说明 |
|---|---|
| **实时性** | 舵机总线时序需要确定性 —— 12 舵机一次 SyncWrite + SyncRead 约 2.5 ms，必须在 10 ms 周期内可靠完成 |
| **Linux 非实时** | 树莓派的 Linux 调度有抖动，纯 GPIO 串口时序不可靠 |
| **安全保护** | 保护逻辑必须在独立 MCU 上，不能依赖上位机正常运行 |
| **职责清晰** | Pi 只做推理，STM32 只做时序与传感器 |

**代价：**

```
· 需要设计一套通信协议（见 firmware/doc/协议规范_树莓派通信.md）
· 引入链路延迟（约 3 ms ~ 13 ms，取决于时序模型）
· 两个固件都要维护
```

**否决的方案：**「只用树莓派」—— 实时性不可靠、安全保护缺失。

## DD-03：舵机供电绕过控制板（外部粗线分流）

**问题**：Waveshare 控制板有 **5 A** 总电流上限，但 12 个舵机堵转需要约 **32 A**。

**选择**：**舵机动力从电池经 16 AWG 粗线直接并联，控制板只用细线供它自身（20~50 mA）**

**理由：**

```
控制板的 5 A 上限是它自身走线的限制，不是协议限制。
把动力路径绕开它，既保留了信号转换功能，又不受电流限制。
```

**代价：**

```
· 布线更复杂（粗线要单独走）
· 控制板上的电流检测不再反映舵机总电流
  —— 但本项目不做电流采样，所以无影响
```

**⚠️ 相关决策：** DD-04（不做电流采样）。

## DD-04：不做电流采样

**问题**：是否需要测量舵机总电流？

**选择**：**不做**

**理由：**

```
① 每个舵机自带 Present Load / Present Current 反馈 → 单舵机电流信息已有
② 总电流的用途有限（本项目不做功率优化）
③ 省掉一个采样电路与一个 ADC 通道
```

**代价：** 无法监测整机功耗。对当前目标无影响。

## DD-05：控制频率 100 Hz（不是 200 Hz 或 1 kHz）

**问题**：控制环频率该定多少？

**选择**：**100 Hz（10 ms 周期）**

**理由：**

| 因素 | 说明 |
|---|---|
| **总线时间** | 单总线带 12 舵机时，读一轮的串行时间决定了频率上限（约 2.5 ms） |
| **RL 需求** | 策略 50~100 Hz 已足够 |
| **舵机内环** | 舵机内部有 PID 内环，扰动抑制不依赖外环带宽 |
| **余量** | 100 Hz 下总线占用约 25%，留足余量给协议与传感器 |

**代价：** 理论上更高的控制频率能改善动态响应，但对本项目的步态无必要。

## DD-06：不用 ROS 2

**问题**：是否用 ROS 2 作为机器人软件框架？

**选择**：**不用。日志与遥测用普通 Python。**

**理由：**

```
① STM32F103C8 只有 20 KB RAM，跑不动 micro-ROS
② 本项目的通信需求简单（10 ms 周期、固定帧、12 个关节）
③ ROS 2 引入大量依赖与学习成本，收益不成比例
```

**代价：** 失去 ROS 生态的工具（RViz、rosbag 等）。用自定义工具替代。

---

## DD-07：关节零位 = 弯腿站立姿态（不是"腿伸直"）

**问题**：URDF 的关节角 0 应该对应什么姿态？

**选择**：**0 = CAD 装配好的弯腿站立姿态**

**理由：**

| 因素 | 说明 |
|---|---|
| **可重复性** | 站立姿态是机器人**自然稳定**的姿态，真机标定无需特殊夹具 |
| **避开奇异点** | "腿完全伸直"是**运动学奇异点**（雅可比退化），零位放这里会导致训练不稳定 |
| **上电自标定** | 机器人开机时大概率就在站立姿态 → 可做"上电自标定" |
| **`q_default` 全零** | 观测/动作/奖励都围绕 0，非常干净 |

**⚠️ 已实测确认**：`default_joint_angles` 全为 0，机器人成功站立（`Sim/RL/RL-CAT-训练实施报告.md` §4.3）。

**代价：**

```
· 真机标定时需要一个"偏置"把关节角映射到舵机角 —— 但这是任何方案都要做的
· 文档表述容易混淆（曾因此产生一个错误结论，见 archive/README.md 勘误 1）
```

**否决的方案：** 零位 = 腿完全伸直 —— 站不住、需夹具、是奇异点。

## DD-08：坐标系约定（X 前 / Y 左 / Z 上）

**问题**：机身坐标系怎么定？

**选择**：**X 向前、Y 向左、Z 向上；原点 = 机身中段中心的地面投影**

**理由：** 与 URDF/RViz/Isaac Gym 的常规习惯一致（Z-up），减少转换错误。

**代价：** 与某些航空惯例（NED，Z-down）不同，需要留意。

## DD-09：不用足底开关（v1）

**问题**：是否装足底接触开关？

**选择**：**v1 不装；改用舵机 `Present Load` 判断触地**

**理由：**

```
① 减少走线与装配复杂度
② 舵机 Present Load 已经能反映足端是否受力
③ 预留了 PB12~PB15 与 5 脚连接器，将来可加
```

**代价：** 触地检测精度低于专用开关。对当前步态够用。

## DD-10：观测用重力向量（不用欧拉角）

**问题**：姿态观测用什么表示？

**选择**：**重力向量（3 维，从四元数反算）**

**理由：**

```
欧拉角在 ±90° 附近有万向节奇异（gimbal lock），
重力向量没有奇异点，且直接反映"哪边是下"。
```

**⚠️ 同理，`TEL_FAST` 里传的是四元数而不是欧拉角** —— 四元数是完整姿态信息，Pi 侧可以按需算重力向量/欧拉角/旋转矩阵。

**代价：** 需要一次四元数 → 重力向量的计算（很便宜）。

---

## DD-11：观测 47 维（不是 legged_gym 原生的 48 维）

**问题**：观测向量用多少维？

**选择**：**47 维**（删除原生 48 维里的 3 维机身线速度）

**理由：**

```
legged_gym 原生 48 维含 3 维【机身线速度】。
但真机没有这个传感器 —— 策略一旦依赖它，sim-to-real 必崩。
```

**代价：** 策略失去机身速度的直接观测，需要用历史观测隐式推断。

**⚠️ 原设计文档写的 50 维是【目标值】，47 维是【当前实现】（见 `docs/30-firmware.md` §5.1）。**

## DD-12：关节零位用 URDF 的装配姿态（保持 CAD 一致性）

**问题**：URDF 的关节轴与零位如何确定？

**选择**：**从 SolidWorks 装配体导出（SW2URDF），零位 = 装配姿态**

**理由：**

```
① 保证 URDF 与 CAD 严格一致，改模型后重新导出即可
② 避免手工定义关节轴带来的偏差
③ 关节轴心位置由 CAD 保证精度
```

**代价：**

```
· 需要建参考坐标系（易出错，见 Mekanik 整理的记录）
· 导出后需手工修正质量属性（SW2URDF 用 STL 算质量，不准）
· 出现过两处 1.5 mm 的左右不对称导出误差，需手工修正
```

## DD-13：质量属性用 SolidWorks 实测值（不用 SW2URDF 的 STL 估算）

**问题**：URDF 的 `<inertial>` 从哪来？

**选择**：**SOLIDWORKS 的【覆盖质量属性】+ 逐 link 读数值**

**理由：**

```
SW2URDF 用 STL 网格算质量 —— 而 STL 不含材质信息，
所以密度是默认值（1000 kg/m³），算出的质量严重偏差。
实测：某个 link 的 STL 估算质量是 54 g，真实是 70 g。
```

**做法：**

```
① 在 SolidWorks 里给每个 link 设正确的质量属性
② 在质量属性对话框里选「报告与以下项相对的坐标值」= 该 link 的坐标系
③ 读数：质量 / 重心 / 惯性张量（「由重心决定」那组）
④ 手工填入 URDF（惯性 ×1e-6 从 kg·mm² 转 kg·m²）
```

**代价：** 17 个 link 的数值要手工填（已用脚本 `patch_mass.py` 自动化）。

## DD-14：安全保护放在 STM32（不放在树莓派）

**问题**：低压/超温/失联保护在哪实现？

**选择**：**STM32 上独立实现**

**理由：**

```
① 保护不能依赖上位机的正常运行 —— 链路失联本身就是需要保护的情形
② STM32 是直接控舵机的一方，能在最小延迟内执行保护动作
③ 树莓派崩溃或卡死时，STM32 仍能保证机器人安全
```

**代价：** 保护逻辑需要在 STM32 上重复一部分系统状态（电压、温度）。

## DD-15：通信协议用自定义二进制帧（不用 ROS/Modbus/JSON）

**问题**：树莓派 ↔ STM32 用什么协议？

**选择**：**自定义二进制帧**（`0xAA 0x55` 头 + LEN + SEQ + TYPE + PAYLOAD + CRC16）

**理由：**

| 备选 | 否决理由 |
|---|---|
| ROS 2 / micro-ROS | F103 跑不动 |
| Modbus | 帧开销大，不适合 10 ms 周期 |
| 纯文本（JSON/CSV） | 解析慢、带宽浪费、易出错 |
| **自定义二进制** | ✅ 帧小、解析快、完全可控 |

**关键设计点：**

```
· 双字节帧头（0xAA 0x55）—— 单字节头在二进制流里容易误触发
· CRC-16/CCITT-FALSE —— 标准算法，有测试向量（0x29B1）
· 序列号 SEQ —— 用于检测丢帧
· LEN 上限 128 —— 防止错误长度导致缓冲区溢出
```

**代价：** 两端都要自己实现编解码与单元测试。

## DD-16：ESP32 桥用两个 TCP 口（3333 透传 / 3334 控制）

**问题**：[`32-esp32-bridge.md`](32-esp32-bridge.md) §4.1 的方案是"单口 3333，TCP 客户端发来的数据里非 `0xAA 0x55` 开头的当成本地文本命令"。这样够用吗？

**选择**：**拆成两个口** —— `3333` 是纯字节管道（STM32 ↔ 笔记本），`3334` 是 ESP32 自己的文本命令/日志/统计口。

**理由：**

```
单口方案下，ESP32 自己的日志与 STM32 的二进制帧混在同一条流里，
客户端必须【解帧】才能区分；拿 netcat 看一眼都不行。
拆口后：3333 永远是干净的二进制通道，3334 永远是文本。
```

**代价：** 调试时可能要开两个连接（或一个 TCP 工具 + 一个 netcat）。

**⚠️ 记录在** [`36-esp32-plan.md`](36-esp32-plan.md) §3.4。

## DD-17：ESP32 的单关节调试命令用【关节角增量】，不用舵机步数

**问题**：[`32-esp32-bridge.md`](32-esp32-bridge.md) §4.2 设计的是 `s <id> <pos>`（`2048` = 舵机中位）。ESP32 能实现吗？

**选择**：**改成 `s <关节号> <角度增量>`**，实现上复用 `CMD_JOINT`。

**理由：**

```
舵机步数 ↔ 关节角 的换算需要 STM32 的标定表（dir / offset），ESP32 拿不到。
要按步数控制，就得给协议加一条 CMD_SERVO_RAW(0x0A) —— 负责人已否决改协议。

改用"关节角增量"后：
  · 不需要新增任何协议消息（填 12 个关节的当前 q，只覆盖目标关节）
  · 其余 11 个关节保持当前姿态，不会因为填 0 而乱动
  · dir / offset 的误差在增量里自然抵消 ⇒ 未标定也能安全测试
```

**代价：** 不能指定绝对舵机步数（那属于 STM32 侧调试命令的范畴）。

**⚠️ 记录在** [`36-esp32-plan.md`](36-esp32-plan.md) §3.5。

## DD-18：ESP32 的指令仲裁按【完整帧 + CRC】判断，且失败时保守拒绝

**问题**：[`32-esp32-bridge.md`](32-esp32-bridge.md) §4.3 说"只需要解析 TEL_FAST 的 `status` 字段（偏移 94），不需要解析整个帧"。够不够？

**选择**：**走完整帧状态机 + CRC16 校验**，从 `status`（帧偏移 **99** = 5 + 94）读 `STAT_LINK_OK`；**状态过期（> 500 ms）或未知时禁止注入**。

**理由：**

```
① 不做 CRC 时，一个位翻转就可能让 ESP32 误判"Pi 在线"，
   从而吞掉工程师正在用的调试指令 —— 这类错误极难排查。
② 96 B × 100 Hz 对 160 MHz 的 C3 是零压力，没有省这一步的理由。
③ 失败安全：宁可拒绝调试指令，也不要"以为 Pi 离线"而抢控制权
   （32-esp32-bridge.md §6 第一条事故场景）。
```

**代价：** ESP32 从"哑管道"变成"懂协议"（设计文档已认定这是有意取舍）。

**⚠️ 前提：** STM32 侧必须把 `STAT_LINK_OK` 实现为**只表示 USART1/Pi 近期有帧**，否则 ESP32 自己的注入会把该位置 1 → 自锁（见 [`36-esp32-plan.md`](36-esp32-plan.md) §2 契约第 4 条）。

## DD-19：ESP32 本轮不做硬急停

**问题**：ESP32 是否实现硬急停线（GPIO → STM32 输入引脚）？

**选择**：**本轮不做**（负责人确认）：不做 `safety.c`、不接急停 GPIO、命令集去掉 `e`。

**理由：** STM32 侧本轮也不实现急停输入（[`33-firmware-plan.md`](33-firmware-plan.md) §0，`RLCA_ESTOP_INPUT_EN = 0`），单侧接线没有意义；先把手动调试链路打通。

**代价：** 现阶段没有"一条线就能停"的兜底。**恢复方式**：STM32 侧开 `RLCA_ESTOP_INPUT_EN` + ESP32 侧加 `safety.c`（文档 §5 的设计仍在）。

## DD-20：ESP-IDF 版本跟随 PlatformIO 平台默认（5.5.3），不钉旧版

**问题**：本机已有 riscv32 工具链 8.4.0（908 MB），能否钉 `framework-espidf@~3.40407.0`（IDF 4.4.7）省下下载？

**选择**：**不钉，使用平台默认的 IDF 5.5.3**。

**理由：**

```
platform-espressif32 的 platform.py（L124-142）对【纯 espidf 工程】会强制
拉取最新的 RISC-V 工具链（14.2.0+20251107），并移除旧工具链条目。
钉住旧 IDF 只会造成"新工具链 + 旧 IDF"的错配，省不了下载还多一层风险。
```

**代价：** 首次安装下载约 1.5 GB（工具链 908 MB + 框架 + cmake/ninja 等）。一次性。

## DD-21：ESP32 工具链目录放 D 盘，并在含空格路径上使用 SUBST 别名

**问题**：本机构建 ESP-IDF 工程时反复失败（`HomeDirPermissionsError`、`PermissionError [Errno 13]`、空格路径报错）。

**选择**：用 [`firmware/tools/pio.ps1`](../firmware/tools/pio.ps1) 统一入口：core/packages/platforms/build 全在 `D:\Work\EspIDF\`，仓库路径含空格时自动建 **SUBST 别名 `R:`** 并在别名下构建。

**理由（两条硬约束）：**

```
① 工作区被沙箱打上 Low 完整性级别 ⇒ 工作区内的 python.exe 一运行就是 Low 进程，
   写不了 Medium 级别的 D 盘（Windows no-write-up）。
   ESP-IDF 的 CMake 恰好调用工作区里的 venv python ⇒ 必须把 venv 放到工作区外。
② ESP-IDF 不支持含空格的工程路径（显式检查 + -fmacro-prefix-map 参数被切碎）
   ⇒ 但仓库就在 "C:\Users\<user name>\..." ⇒ 用 SUBST 别名提供无空格路径。
   （不用目录 junction：junction 会被解析回真实路径，空格又回来了。）
```

**代价：** 构建必须走 wrapper；换机器需要重做这两条适配（清单见 [`36-esp32-plan.md`](36-esp32-plan.md) §4.1）。

## DD-22：ESP32 桥的健壮性三件套（看门狗 / NVS 配置 / 日志镜像）+ 板上自检

**问题**：无线桥挂掉时怎么知道、怎么恢复？配置怎么改？板子装到机器人上后 USB 口够不着怎么办？

**选择**：

```
① 任务看门狗：UART 泵、socket 任务、仲裁任务三处订阅（超时 5 s，触发即 panic 重启）
② 配置存 NVS：控制口 `cfg` 可改 WiFi 密码与两个 TCP 端口，重启生效
③ 日志镜像：ESP_LOG 同时写进 3334 控制口（LF→CRLF）
④ 板上自检：开机跑一遍与主机侧相同的协议向量，并提供 `selftest` 命令随时重跑
```

**理由：**

```
① 卡死比重启危险：桥卡住时操作员既看不到遥测、也发不出指令，而 STM32 有自己的
   失联保护（30 ms 降级 / 100 ms 慢趴），所以让桥重启不会把机器人留在危险状态。
   ⚠️ 喂狗点必须覆盖所有可能长期阻塞的调用（读 UART 用 20 ms 超时、
      poll 用 200 ms、队列等待从 portMAX_DELAY 改成 1000 ms）。
② 板子装进机器人后 USB-Serial-JTAG 往往够不着，改密码/端口只能走无线 —— 但
   WiFi 密码又必须在连上之前生效，所以只能"存 NVS + 重启生效"。
③ 没有 3334 的日志镜像，就只能靠 USB 串口看 ESP32 在想什么；装了机就看不到了。
④ 主机侧测试证明的是【PC 上的编译结果】；板上自检证明【真实 CPU + 真实优化】下的
   同一套向量，能挡住对齐/端序/优化器带来的意外。
```

**代价：**

```
· 每新增一个会阻塞的任务，都必须记得 esp_task_wdt_add/reset（漏了就重启）
· panic=1 时看门狗触发会重启桥（可用 RLCA_TWDT_PANIC=0 临时关掉，但不要长期关）
· NVS 里的值不可信：读回来必须过校验（rlca_cfg_valid_*，18 项主机侧测试覆盖）
· cfg clear 会 nvs_flash_erase，顺带清掉 WiFi 校准数据（下次启动重新校准）
```
