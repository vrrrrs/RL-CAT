## 2. 为什么**不能**直接跳到 sim2real

**三个理由，按严重性排序：**

### ① 工程前提不成立：机器人没在地面上站过

**策略的 episode 从"站立姿态"出发**（仿真里 `_reset_dofs` 就是 `q=0` ±0.15 rad）。
如果真机一上电就站不住，策略第一步就崩，**根本没机会展示它会不会走**。

### ② 最大的 sim2real 缺口在**执行器**

| 仿真里 | 真机上 |
|---|---|
| PD 控制器：`stiffness=20`、`damping=0.5`、**力矩输出** | **舵机内部 PID**，收位置指令，增益不可精确对齐 |
| 无摩擦、无齿隙、无回差 | 有摩擦、有齿隙，腿部连杆有柔性 |
| 地面是刚体 | 桌面/地面材质未定 |

**⇒ 这是"策略能不能落地"的核心风险，必须**低速、有保护**地试。**

### ②b ⚠️⚠️ **仿真里没有驱动器延迟** —— 这是最被低估的风险

**2026-10-18 Linux 侧交付报告指出（`docs/47-policy-export-report.md` §6）：**

**仿真里的舵机是"理想伺服"** —— 给了目标角度，**下一个物理步就到位**，延迟 ≈ 0。

**真机上：**

```
总线 SyncWrite 发出        ~1 ms
舵机内部 PID 响应          ?
→ 总延迟约 1~3 个控制周期 = 10 ~ 30 ms
```

**⚠️ 后果：**

| 现象 | 为什么 |
|---|---|
| **真机会震荡，仿真里完全看不出来** | 10~30 ms 延迟在 100 Hz 回路里相当于**1~3 个周期的纯延迟**，闭环相位裕度被吃掉 |
| **吊起时看不出来，落地才暴露** | 吊起时不承重，关节几乎不受外力，延迟的影响被掩盖 |
| **策略是在"无延迟"的世界里练出来的** | 它的增益/节奏隐含假设"指令立即生效" |

**⇒ 应对（按成本排序）：**

| 方案 | 成本 | 效果 |
|---|---|---|
| **① 真机上降速跑**（`action` 乘 0.5，或降低策略频率） | 免费 | 立刻减小延迟的相对影响 |
| **② 仿真里加"动作延迟队列" + 域随机化**（每次 reset 随机 1~3 步） | 改仿真 + **重训一版** | ⭐ **根治** |
| **③ 提高舵机内部 PID 刚度** | 调参 | 减小稳态误差，但不解决延迟 |

**⚠️ 我的判断：①②都做。先用①上真机验证"能站"，如果震荡明显就做②重训。**

### ③ 一旦摔了，分不清是谁的错

**如果同时改"部署代码"和"策略参数"，摔了无法定位。**
**⇒ 所以要有**逐段可验证**的路径：每段都有独立判据，摔了能定位到具体一层。**

## 3. 建议的三段式主线

```
M1 地面站立  ──►  M2 脚本步态  ──►  M3 sim2real
  (Gate)          (可独立交付)       (项目目标)
```

### M1 · 地面站立 —— ⭐ **这是 Gate，必须先过**

| 项 | 内容 |
|---|---|
| **目标** | 机器人在桌面（有吊带作保险）上，不借助吊带**自主站立 10 秒** |
| **做什么** | ① 把机器人放上桌面（不再是吊起）；② `pose.py --pose zero` 送它到站姿；③ 保持 10 s，记录关节角漂移 |
| **判据** | 关节角偏差 **< 3°**、不塌、不抖、`torque_actual = 1` 全程 |
| **为什么先做** | 它是 M2 和 M3 的共同前提，而且**暴露最基础的问题**（力矩够不够、零位是不是有效站姿、电源能不能撑住） |
| **风险** | 力矩不足（`stiffness` 对应不了）／零位姿态重心不对／12 V 压降 |
| **失败时的分支** | 若站不住 ⇒ 先改**站姿**（调 `q_default`，比如膝盖多弯一点降低重心）或**伺服增益**，而不是急着上策略 |

**⚠️ 安全检查：吊带要留 2~3 cm 余量 —— 站住了则不受力，摔了才拉住。**

### M2 · 脚本步态 —— 可独立交付的价值

| 项 | 内容 |
|---|---|
| **目标** | 机器人**原地踏步**稳定，然后**前进 0.1 m/s** |
| **现状** | `pi/gait.py` 是**关节空间正弦**（thigh 正弦摆 + calf 半波抬腿）。相位来自 STM32（3 Hz），四腿对角协调 —— **但**没有足端轨迹、没有支撑相/摆动相区分，实际只会"晃腿" |
| **缺什么** | ① 足端**笛卡尔**轨迹（抬腿-前摆-落地-后蹬）；② 单腿**逆运动学**（hip/thigh/calf ← 足端 xyz）；③ 支撑相时长占比（duty） |
| **判据** | ① 原地踏步 10 s 不摔；② 前进速度可控且方向正确；③ 机身横滚/俯仰 < 8° |
| **价值** | 即使 M3 失败，项目也有一个**能演示的步态**（开源时很重要） |
| **风险** | 开环步态没有平衡反馈，容易越走越歪 ⇒ 需要 IMU 做简单的姿态修正 |

**⚠️ 与 M3 的关系：M2 不是 M3 的必由之路，但它**(a) 验证舵机在动态负载下的表现，(b) 给 M3 提供一个"已知能站能走"的对照。**

### M3 · sim2real —— 项目目标

| 项 | 内容 |
|---|---|
| **目标** | 训练出的策略在真机上**维持站立 ≥ 10 s**，然后**跟随速度指令前进** |
| **前置** | L1（策略导出）+ Pi 推理层 + M1 通过 |
| **关键工作** | ① 47 维 obs 构造（全部在真机可复现，见下）；② 100 Hz 策略循环；③ 安全兜底（摔倒检测、指令限幅） |
| **判据** | 阶段 1：速度指令全 0 时站立 ≥ 10 s 不摔；阶段 2：`vx = 0.1 m/s` 能走起来；阶段 3：转向 |
| **最大风险** | 伺服 PD ≠ 仿真 PD；IMU 姿态噪声；观测归一化不一致 |
| **失败时的分支** | 若一上就摔 ⇒ 用 L3 录的**仿真轨迹**逐位对比 obs，先排除"部署错"再怀疑"策略不行" |

**⭐ 好消息：47 维观测在真机上**全部可复现，没有传感器缺口：**

```
[0:3]   重力向量     ← IMU 四元数
[3:6]   机身角速度   ← IMU 陀螺
[6:9]   速度指令     ← 脚本/遥控
[9:21]  关节位置×12  ← TEL_FAST.q
[21:33] 关节速度×12  ← TEL_FAST.qd
[33:45] 上一帧动作×12 ← 内部状态
[45:47] 相位(sin,cos) ← ⭐ TEL_FAST.gait_sin/cos（STM32 本来就在发）
```

**⭐ 而且 `action_scale = 0.25`（固件已一致）、`decimation = 2`（100 Hz）、
相位每步 +0.03（固件已一致）—— 三处关键契约都已经对上。**

## 4. 并行要还的"技术债"

| # | 债 | 影响 | 什么时候还 |
|---|---|---|---|
| 1 | **IMU I2C 超时 ⇒ 周期 15~21 ms** | 丢周期；到 M2/M3 会变成相位抖动 | ⭐ **M1 之前或同时** |
| 2 | `cont` 未持久化 ⇒ 跨 0/4096 时 `q` 跳 2π | 目前关节范围不会触发，**但步态大行程可能触发** | ⭐ **M2 之前** |
| 3 | `rb_calf` 限位（−60~+60）疑似复制错误 | 可能限制步态抬腿幅度 | M2 期间 |
| 4 | ~~`RLCA_LINK_LOST_MS = 80` 对非 RT Linux 是否够~~ | **已解决（2026-10-18）**：开发期放宽到 150/1200，见 `docs/49` §4-D2 | ⚠️ M2/M3 后要改回 80/300 做安全回归 |

**⇒ 建议：技术债 1、2 在 M1 之后、M2 之前一并清掉（一次烧写）。**
