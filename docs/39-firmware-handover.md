## 2. 系统架构（一图）

```
        ┌──────────────┐   USART1  1 Mbps  【交叉】   ┌──────────┐
        │              │◄────────────────────────────►│ 树莓派 5 │
        │              │   协议帧 + ASCII shell        └──────────┘
        │              │
        │  STM32F103   │   USART2  1 Mbps  【直连】   ┌──────────┐
        │  C8T6        │◄────────────────────────────►│ 舵机控制板│
        │  72 MHz      │   Feetech STS 半双工          └────┬─────┘
        │              │                                    │ 12 个 STS 舵机
        │              │   USART3  115200 【交叉】    ┌─────┴────┐
        │              │──── 遥测镜像（非阻塞）──────►│ ESP32-C3 │
        │              │◄─── 调试注入（未解析）────────└──────────┘
        │              │
        │  PB8/PB9 ────┼── 软件 I2C ──► JY901P（姿态）
        │  PA0 ────────┼── ADC ──────► 电池分压
        │  PA8/PC13 ───┼── 心跳 / 状态灯（PC13 低电平点亮）
        └──────────────┘
```

**100 Hz 控制环的 9 个步骤**（`app_cycle_100hz`）：

```
① 取上轮 SyncRead 反馈 → 关节状态快照
② 收 Pi 指令（中断入环形缓冲）
③ 读 IMU 姿态 + 电池电压
④ 组并发 TEL_FAST（103 B，同时镜像给 ESP32）
⑤ 等本帧 CMD_JOINT（模型 A，4 ms 窗口）
⑥ 消费指令 → 模式状态机 + 安全评估 → 生成目标角
⑦ 合法化（NaN/限幅/限速）→ 发起舵机事务
⑧ TEL_STATUS（10 Hz）
⑨ 相位时钟推进
```

## 3. 七个阶段：做了什么、结果如何

### P0 编译基线 + 参数表 ✅

| 项 | 结果 |
|---|---|
| AC6 编译 | ✅ 命令行 armclang，0 error 0 warning |
| 参数集中 | ✅ 全部参数在 `rlcat_config.h`（唯一改动点） |
| ⚠️ 发现的阻碍 | **编译器选择不在 `.uvprojx`/`.uvoptx` 里**（三个位置都试过），只能 GUI 手动切。绕开办法：命令行构建 |

### P1 纯逻辑层 + PC 单测 ✅

`rlca_crc16` / `rlca_frame` / `rlca_phase` / `rlca_math`，**288 项单测**。
CRC-16/CCITT-FALSE 用标准向量 `0x29B1` 验证。

### P2 BSP 层 ✅

三路 UART（中断接收 + 环形缓冲、USART2 用 DMA+IDLE）、DWT 微秒计时、
软件 I2C、Flash 标定持久化、**ASCII shell（上机自检的命令行）**、上电自检。
→ 验收单 **P2 节 8 项**

### P3 舵机总线 ✅

自实现 Feetech STS 编码（SyncWrite/SyncRead）+ 非阻塞事务状态机。
**143 项假总线单测**。→ 验收单 **P3 节 9 项**

**⭐ 关键修正**：STS 反馈帧是 **15 字节**（`H0 H1 ID LEN ERR data[9] CHK`），
最初漏算 CHK 写成 14 → 12 帧反馈全被丢弃。

### P4 链路 + 树莓派模拟器 ✅

`link_proto`（编解码）+ `link_pi`（状态机）。**267 项 C 单测 + 161 项 Python 测试**。
`pi/sim_esp32.py` 在没有树莓派、没有 ONNX 的情况下实测模型 A 的时序可行性。
→ 验收单 **P4 节 9 项**

### P5 传感器 ✅

`imu.c`（JY901P，软件 I2C）+ `battery.c`（ADC → 分级）。
**196 项单测**（含假 JY901P）。→ 验收单 **P5 节 7 项**

### P6 标定 + 模式 + 安全 ✅

| 模块 | 内容 |
|---|---|
| `rlca_calib_proc` | 标定状态机：卸力矩→等沉稳→采样→**逐关节测方向**→回位→读零点→校验 |
| `rlca_safety` | **纯逻辑安全判据**：由信号算出"要不要卸力矩/趴下" |
| `app_safety` | 执行层：**缓慢趴下斜坡** + 4 s 独立超时兜底 |
| `app_mode` | 模式状态机 + **ACTIVE 五道准入** |

**115 项单测**（含假舵机总线跑完整标定流程）。→ 验收单 **P6 节 6 项**

**⭐⭐ 这是"安全保护必须独立于上位机"的落地阶段。**
分级设计（有意为之）：

| 触发 | 后果 | 理由 |
|---|---|---|
| 操作者急停 / **链路失联>100ms** / 电压≤9.3V / 舵机>70°C | **趴下 + 卸力矩** | 不停就要出事 |
| 电压≤9.9V / 舵机错误码 | **限幅**，继续跑 | 还能走，没必要停 |
| 电压≤10.5V | 仅告警 | — |
| **IMU 失效** | **只禁 ACTIVE，不趴下** | "姿态不可信"该拦的是"别跑策略"；当急停会让"IMU 线松了"变成"机器人趴下" |
| 电压读数失效 | 不置任何电压位 | 不把"读不到"当成"正常"，也不当成"0 V" |

### P7 联调 + 文档回填 ✅ / 🟡

| 项 | 状态 |
|---|---|
| 部署手册 | ✅ `35-firmware-deployment.md` |

## 5. 开发中发现并修复的缺陷

### 5.1 真实代码缺陷（24 个）

按严重程度排：

| # | 缺陷 | 后果 | 怎么发现的 |
|---|---|---|---|
| 1 | `STS_MAX_PAYLOAD=32` 装不下 12 舵机 SyncWrite（38 B） | 返回参数错，且调用方 `n-1` **下溢成 65535** → 循环死锁 | 单测 |
| 2 | `STS_FB_FRAME_LEN` 漏算 CHK（写成 14） | **12 帧反馈全部丢弃** | 单测 |
| 3 | 标定：进方向测试时没给第一个关节下指令 | 必然 `NO_MOTION`，**标定 100% 失败** | 假总线单测 |
| 4 | 标定：采样阶段卸了力矩，方向测试前忘重新使能 | 同上 | 假总线单测 |
| 5 | 标定：**最后一个关节从没被回位** | 停在 `base+98`，offset 错掉 | 假总线单测 |
| 6 | 标定：方向测试后立刻读 offset | 回位还没走完，offset 偏 40 步 | 假总线单测 |
| 7 | `offset` 范围检查写成 `offset > 4096` | 对负值恒真，**负的超范围 offset 漏检** | 单测 |
| 8 | 相位按 π/2 归约 | 补角达 2.32 rad 跑出泰勒区间，误差 2.6e-4 | 单测（改十六分区后 3.58e-6） |
| 9 | `RLCA_IMU` 用 `s_last_poll_ms != 0` 当初始化哨兵 | 上电 t=0 时节流失效，连采好几次 | 单测 |
| 10 | 安全判据降级（`link_level==1`）没置原因位 | Pi 只能从 severity 反推 | 单测 |
| 11 | `calib_validate_result` 先做整体检查 | 笼统的 LIMIT 盖掉"方向不明"这个具体原因 | 单测 |
| 12 | `link_pi_wait_cmd` 纯自旋 | 微秒源不前进时**死循环锁死主循环** | 代码审查 |
| 13 | `servo_bus` 只等"收满 12 帧" | 掉一个舵机就白等满 3 ms 且丢弃已收帧 | 单测（改"短暂静默"判结束） |
| 14 | `parse_feedback_frames` 用 `k--`（uint8_t） | 可下溢成 255 → 无限循环 | 代码审查 |
| 15 | 标定期间跳过整个控制环 | SyncRead 不跑 → 反馈永不刷新 → `get_pos` 必失败 | 代码审查 |
| 16 | `app_calib_start` 不检查反馈新鲜度 | 拿 0 值当零点 | 代码审查 |
| 17 | 发送侧**没有任何错误计数** | ESP32 不读数据会**静默丢帧** | 设计审查 |
| 18 | UART3 镜像用**阻塞发送 + 100 Hz** | **把 100 Hz 环拖到 ~92 Hz**，破坏 RL 时序契约 | ⭐ **ESP32 侧真机观测** |
| 19 | 让 `link_pi.c` 直接依赖 `esp_fwd.c` | 拖着 HAL，**6 个测试套件全部链接失败** | 测试 |
| 20 | `main.c` 是**混合编码**，24 字节损坏 | 中文注释乱码；`read` 工具报 "invalid UTF-8" | 编辑时发现 |
| 21 | `battery.c` 采样节流用 0 当哨兵 | 上电瞬间连采 | 单测 |
| 22 | `0 Errors, 1 Warning` 被当成编译错误 | 构建误判失败 | 构建 |
| 23 | CubeMX `startup_*.s` 用 Arm 传统语法 | armclang 报"invalid instruction"（需 `-masm=auto`） | 构建 |
| 24 | PowerShell 5.1 把无 BOM 的 UTF-8 `.ps1` 当 GBK | 中文注释破坏脚本解析 | 构建 |

### 5.2 工程文件损坏（`.uvprojx`）⭐ 最曲折的一个

**现象**：Keil 里**魔术棒点不开**，无法烧录；其它工程都正常。

**根因**：`stm32.uvprojx` **丢了整个 `<TargetArmAds>` 块**
（ARM 编译器/汇编器/链接器的全部选项都在这里）。

```
                  损坏版    修复后
TargetArmAds   →    0    →    1
Cads（C 编译） →    0    →    1
Aads（汇编）   →    0    →    1
LDads（链接）  →    0    →    1
```

**⚠️ 为什么之前所有检查都没发现**：丢失后剩下的 XML **完全良构** ——
`<TargetCommonOption>` 之后直接跳到 `<Groups>`。所以：
- `check-uvprojx.ps1` 过（只比对 Groups 文件列表）
- 命令行 armclang 构建过（它不读 `.uvprojx`）

**修复**：以参考工程（`reference/servo/...`，**同一颗 STM32F103C8**）
为完整模板，用 .NET XML API 做**节点级**修改：
**288/288 个叶子路径与模板完全一致**，两级子节点顺序也一致。

**⚠️ 我第一版修复是错的**：把 `TargetArmAds` 插在了 `TargetCommonOption`
之后，而正确位置是 **`TargetOption` 的最后一个子节点**（`Utilities` 之后）
→ uVision 解析到顺序不对就**闪退**。

**⚠️ 顺带修了第二个 bug**：`<uAC6>` 值是 **8**，
而正常 AC6 工程都是 **1**（我的字符串替换误伤）。

**最终修复的字段**：

| 字段 | 值 |
|---|---|
| `Device` | STM32F103C8 |
| `PackID` | `Keil.STM32F1xx_DFP.2.4.1`（**必须与已装版本一致**，原抄成 2.3.0） |
| `FlashDriverDll` | `...STM32F10x_128.FLM`（原来**空值**） |
| `RegisterFile` / `SFDFile` | 器件头 / SVD（原来**空值**） |
| `uAC6` | **1**（ARM Compiler 6） |
| `TargetName` | `stm32`（原来残留 `SCServo`） |

**⚠️ 三个字段为空就是闪退原因** —— uVision 要填充 Flash 下载与器件视图，
空值会导致崩溃。

### 5.3 链接失败（`L6406E`）：Flash 装不下

**现象**：`Could not load file 'stm32\stm32.axf'`（下载失败）。
**真相**：`.axf` 根本没生成 —— **链接失败**，那个对话框只是表象。

**排查**：`Optim` 的取值是**枚举**，我靠猜设成 4 → 失败。实测矩阵：

| `Optim` | 结果 |
|---|---|
| 1 | ❌ 超 0x5108 |
| **2** | **✅ 成功** ← 采用 |
| 3 / 4 / 5 | ❌ 超 0x454c / 0x5eb8 / 0x5df4 |
| 6 | ✅ 成功 |

**教训**：`.uvprojx` 里的**数字型枚举不能靠猜，只能靠试**。
（同样的问题也发生在 `PackID` 上。）

### 5.4 ⚠️ 超出原定范围的一项：USART3 转发

`docs/33-firmware-plan.md` §0 原定「**USART3 转发 TEL_FAST 暂不处理**」。
2026-10-10 ESP32 侧完成后要求补齐 TX 方向，于是**超出范围**实现。

**第一次实现是错的，且是 ESP32 侧先发现的**：

```
ESP32 观测到 rx ≈ 9.5 kB/s，而不是 10.3 kB/s
→ 说明 STM32 控制环被拉到 ~10.8 ms ≈ 92 Hz
→ 根因：镜像用了【阻塞发送】（103 B @921600 = 1.12 ms）
```

**⚠️ 92 Hz 不是"稍微慢一点"，而是破坏了 RL 的时序契约**：
训练侧 `decimation = 2` 要求控制环**严格 100 Hz**，
掉到 92 Hz 会让策略看到的"每步时间"与训练不一致
→ **属于会静默劣化策略的故障**。

**正确实现（三件事必须同时成立）**：

| # | 项 | 值 |
|---|---|---|
| 1 | 波特率 | **115200**（原 921600） |
| 2 | 发送方式 | **中断 `HAL_UART_Transmit_IT`**（非阻塞） |
| 3 | 镜像频率 | TEL_FAST **100 Hz → 10 Hz** |

**⭐ 最大的教训**：**离线单测覆盖不了"时序有没有被破坏"**。
1028 项单测全绿的同时，真机周期已经掉到 92 Hz。
这类问题必须靠**真机观测或周期耗时统计**。

### 5.6 ⭐ IMU 手册到手后的两处修正（2026-10-11）

`reference/JY901P_I2C协议.md` 到手后逐条核对，**查出 2 个会影响功能的真 bug**：

| # | 项 | 错在哪 | 后果 |
|---|---|---|---|
| 1 | **角度换算** | 写成 `raw × 0.01°/LSB` | 手册是 `raw/32768 × 180°`，**差了 1.831 倍**：90° 会被算成 164°，所有姿态全错 |
| 2 | **器件 ID 寄存器** | 读 `0x00` | `0x00` 是 **SAVE**（保存/重启/恢复出厂，**可写**）；只读版本号在 `0x2E` |

**⚠️ 第 2 条的严重性容易被低估**：读 SAVE 至少无意义，但它是**可写**寄存器 ——
0xFF 会让模块重启、0x01 会恢复出厂设置。把它当"器件 ID"放在自检路径上，
等于给未来的自己埋了一个"顺手写一下 ID"的坑。

**⚠️ 第 1 条为什么 202 项单测全绿却没抓到**：

```
我原来的测试辅助函数 build_angle_buf() 也用【同一个错误假设】编码
（按 0.01°/LSB 把角度写成 raw）
→ 等于"用一把错的尺子量自己"，编解码两边同时错，恒定通过
```

**修法**：测试辅助函数改为**按手册编码**（`raw = deg/180×32768`），
并新增回归断言钉死"raw 16384 == 90°"，固件一改错立刻红。

**⭐ 这条教训值得单独记**：**当测试的输入生成器和被测代码共享同一个假设时，
那个假设永远测不出来。** 手册是唯一的外部真值来源。

**顺带核实正确的项**（不是全错）：

```
从机地址 0x50      ✅ 对（手册 §IICADDR 默认值）
ACC  0x34~0x36     ✅ 对（AX/AY/AZ）
GYRO 0x37~0x39     ✅ 对（GX/GY/GZ）
ANGLE 0x3D~0x3F    ✅ 对（Roll/Pitch/Yaw）
陀螺换算 /32768×2000°/s  ✅ 对
加计换算 /32768×16g      ✅ 对
```

**新发现的可选改进**：手册 §q0~q3 表明模块**直接提供四元数**（`0x51~0x54`，
`raw/32768`）。当前固件走"读欧拉角→自己转四元数"，多一次三角运算、
也多一个坐标约定的出错点。若实测发现欧拉角路径的坐标约定与 Isaac Gym
不一致，**改读 0x51 即可**（配置里已留 `RLCA_IMU_REG_QUAT`）。

**⚠️ 仍需在上位机里做的两件事**（固件设不了）：

```
① RRATE@0x03 = 0x09  → 100 Hz（手册默认 0x06 仅 10 Hz，不改会读到阶梯状姿态）
② 确认 GYRORANGE=±2000°/s、ACCRANGE=±16g 与固件常量一致
```

### 5.7 ⭐⭐ IMU 字节序：大端假设是错的（实测修正）

**这是整个项目里最隐蔽的一个 bug** —— 它让 203 项单测全绿的同时，
真机上所有姿态数据都是错的。

| 项 | 错的 | 实测正确 |
|---|---|---|
| I2C 寄存器字节序 | **大端**（低字节在后） | **小端**（低字节在前） |
| 函数名 | `imu_be_i16`（"be" = big endian） | `imu_i16`（已改名，防止继续误导） |

**⚠️ 错误是怎么来的**：注释里写着"WIT 模块用大端"，
依据是"WIT **串口**协议用大端"这个常识 —— 但那是**串口**协议的约定，
I2C 寄存器未必相同。**而手册通篇没有写字节序**，所以这是个纯假设，
从未被验证。

**⭐ 实测证据（`I` 命令 dump 的原始字节）**：

```
ACC   0x34~36 = 05 FF 84 00 F2 07
   小端 -> (-0.123, +0.064, +0.993) g   |a| = 1.003 g   <- 静止时应 ~1 g  ✅
   大端 -> (+0.750, -15.500, -1.747) g  |a| = 15.6 g    <- 离谱       ❌

QUAT  0x51~54  小端 + 自然分量顺序 -> 推出的重力与加速度一致（偏差 0.000）
               大端 -> 6 种分量排列没有一种能对上

ANGLE 0x3D~3F  小端 -> 推出的重力与加速度一致（偏差 0.000）
               大端 -> 最好也差 0.48

旁证（不需要物理推导）：三个出厂默认值只在【小端】下与手册吻合
   RSW   = 1E 00 -> 0x001E = 30   （手册默认 0x1E）
   RRATE = 06 00 -> 6            （手册: 6 = 10 Hz）
   BANDWIDTH = 04 00 -> 4        （手册: 4 = 20 Hz）
```

**判据用的是物理约束，不依赖任何假设**：
四元数必须归一化、且它推出的重力方向必须与**加速度计实测的重力**一致
（两者描述同一物理姿态）。三组独立寄存器全部收敛到同一个答案。

**修正后的验证**（同一批原始字节离线重算）：

```
Roll = +3.71 deg, Pitch = +7.03 deg        <- 水平放置，小角度 ✅
q = (0.5135, -0.0360, 0.0592, 0.8553), |q| = 0.999952
gravity(body) = (+0.122, -0.064, -0.990)   <- 接近 (0,0,-1) ✅
accel = (-0.123, +0.064, +0.993) g, |a| = 1.0028 g
加速度推出的重力 == 四元数推出的重力        <- 完全一致 ✅
```

**⭐ 顺带修掉的第二个同类 bug**：`imu_selftest()` 里手工拼字节
`(ver[0]<<8)|ver[1]`（大端），没走 `imu_i16` —— 同一个错误在代码里的第二处。
测试立刻抓到（`got 513, want 258`）。

#### ⚠️⚠️ 为什么 203 项单测全绿却没发现

**测试的"输入生成器"用了和被测代码【同一个假设】**：

```
假 JY901P 按【大端】编码  ->  固件按【大端】解码  ->  两边同时错，恒定通过
build_angle_buf() 也按大端编码  ->  同上
```

**这和之前的 `0.01°/LSB` 是同一类问题，而且我犯了两次。**
只有**外部真值**（手册、或上机 dump 的原始字节）能打破它。

**修法**：测试的编码函数改为按**实测的小端**写出，
并新增回归断言（`raw 16384` 必须是 90°、`0x00 0x08` 必须是 2048）。

#### 附带好处

I2C 侧现在与舵机总线、协议帧**一样都是小端** ——
全项目只有一种字节序，少了一整类坑。

**⚠️ 一条差点犯的错**：我一度以为 `ACCRANGE = 0x03` 意味着 ±4 g。
但**小端下 |a| = 1.003 g**，说明手册的 `raw/32768×16g` 公式是对的，
固件常量没错 —— `0x03` 就是出厂默认，**不是量程编码**。
差一点又基于"看着不像 ±16g"的直觉去改一个本来正确的常量。

### 5.8 ⭐⭐⭐ UART2 接收问题：5 个真实缺陷 + 一条方法论教训

**现象**：`A`（PING 12 个 ID）永远全 no response，而 `B` 里偶尔能看到
某一个关节的 pos/V/T。排查共 8 轮，其中 **5 处是真实缺陷**。

#### 五个真实缺陷（按被发现顺序）

| # | 缺陷 | 位置 | 后果 |
|---|---|---|---|
| 1 | **`servo_bus_abort()` 是死代码**（全项目零调用） | `servo_bus.c` | 阻塞式单机指令与后台同步读**抢总线** |
| 2 | **`txn_expect_ack()` 只读一次就判** | `servo_bus.c` | 应答被 DMA 边界切成两段时读半帧 → 判失败 |
| 3 | **DMA 接收被关后从不重启** | `bsp_uart.c` 回调 | HAL 出错时先 `UART_EndRxTransfer()` 关 DMA，回调只清标志；主循环的检查因标志已被清而**永不触发** → 一次 ORE 永久杀死 RX |
| 4 | **`bsp_uart_flush()` 对 DMA 端口语义错** | `bsp_uart.c` | 连错三次（只清环形缓冲 / 追平 `dma_last` / 先搬再丢），每次都吃掉"此刻到达"的字节 |
| 5 | ⭐ **`port_avail()` 读环形缓冲，但 DMA 没人搬** | `servo_port.c` | **最终根因**（见下） |

#### 第 5 个缺陷：最终根因

```c
void app_poll(void) {
    ① bsp_uart_poll_dma();   // 全程序唯一一次搬 DMA
    ② servo_bus_poll();
    ③ link_pi_poll();
    ④ bsp_shell_poll();      // `A` 在这里 → txn_expect_ack() 自旋 3 ms
}
```

**`s_port->avail()` 读的是【环形缓冲】，不是 DMA 寄存器。**
在那 3 ms 自旋期间没有任何人搬 DMA ⇒ 应答一直躺在 DMA 缓冲里 ⇒
`avail()` 恒为 0 ⇒ 判失败。

**修复**：把"搬 DMA"下沉到端口层：

```c
static uint16_t port_avail(void) {
    bsp_uart_poll_dma();                       // ⭐ 先搬，再报告
    return bsp_uart_available(&g_uart_servo);
}
```

**⚠️ 为什么放在端口实现里而不是 `servo_bus` 里**：`servo_bus` 是纯逻辑层，
刻意不依赖 HAL（之前加 `bsp_tick.h` 把 host 单测搞挂过）。
放在端口层既修了问题、又保住了分层。

#### ⚠️⚠️ 一条方法论教训：软件计数器会骗你

**排查"收不到数据"时，我一直在看 `rx_frames` / `bytes` / `dma_restarts`
—— 而这些指标【全部经过我自己写的代码路径】**
（`drain_dma` → 环形缓冲 → `parse_feedback_frames` → 状态机）。

**它们同时兼容两种完全不同的病因**：
- 总线上真的没字节（接线 / 适配器 / 舵机）
- 有字节但被我的软件丢了

**这两者要修的东西毫无关系**，于是我在这中间来回猜了 5 轮。

**转折点是为两个"不经过我代码"的测量**：

```
① dma_hw_bytes   —— 每次轮询直接读 DMA 的 CNDTR，累计它前进的字节数。
                    不写环形缓冲、不碰 dma_last。只回答
                    "USART2 接收线上到底有没有字节进来"。

② dma_wr_pos vs dma_last —— 硬件指针减去软件指针。
                    实测差 6 字节（正是一个 PING 应答）→ 直接指出
                    "有字节躺在 DMA 里没被搬走"。
```

**有了 ①，问题被一刀切成两半**：
```
dma_hw_bytes = 16896  -> 线上有字节，是我的软件问题
ring_rx_total = 274    -> 差了 60 倍，搬运丢字节
uart_overflow = 0      -> 而且不是"缓冲满丢的"，是被主动丢的
```

**⭐ 规则：排查"收不到数据"的第一步应该是读硬件寄存器
（DMA 的 EN/CNDTR、USART 的 CR1/SR），而不是在软件里加计数器。**
软件计数器只能告诉你"搬没搬"，硬件寄存器才告诉你"能不能搬"。

**⚠️ 而且连 HAL 的状态都不可信**：实测抓到
`dma_ccr.EN = 0`（硬件已停）而 `hal_dma_state = READY`（HAL 以为在跑）
—— **软件状态与硬件状态脱节**。所以恢复逻辑里加了"直接查 EN 位"这一道。

#### ⚠️ 另一个教训：诊断工具本身会误导

我在这一轮里三次设计出有缺陷的诊断工具：

| 工具 | 缺陷 | 后果 |
|---|---|---|
| `A` | 只报 ACK/no-response，看不到字节 | 无法区分"没回"与"回了但解析失败" |
| `U`（回环） | 只报收到几个字节，不报发出去几个 | `D1 recv = 0` 无法定位是 TX 还是 RX 的问题 |
| `Y` | 自己的等待循环里**显式搬了 DMA**，与 `servo_bus_ping` 走**不同通路** | **`Y` 的"成功"让我误以为链路是通的** —— 掩盖了第 5 个缺陷 |
| `B` 的 `drop_raw` | `record_drop()` 放在循环开头而非丢弃分支 | 记录的是"最后一次经过的位置"（一个**成功解析**的帧），完全误导 |

**⭐ 规则：诊断工具必须 ① 给出原始数据 ② 报告"发"与"收"两侧
③ 与被测代码走【同一条路径】。**
`Y` 违反了第 ③ 条 —— 它自己搬 DMA，所以它的成功不能用来论证
`servo_bus_ping` 的成功。

#### 门禁（修复后）

```
C 单测   1058 项全绿（servo_bus 143→161，新增 5 个回归测试）
```

**新增回归测试钉住的场景**：总线互斥（暂停后不发起新事务）、
碎片化应答（2+4 与 4+2 两种切法）、帧头前噪声的重同步、
部分舵机在位时每个应答都要标记 valid。

## 8. 经验总结（给后续接手的人）

### 8.1 三条最有价值的做法

**① 端口注入 → 离线可测**
把"碰硬件的那一小块"全部隔离到 `*_port.c`，业务逻辑只认注入的端口。
**收益**：1028 项测试能在 PC 上跑，包括**完整标定流程**与**链路 4 ms 窗口**。

**② 假模型要模拟"行为"，不要模拟"期望值"**
`test_safety_calib.c` 的假舵机总线模拟了"**没力矩就不动**"。
正因为如此，它抓到了"方向测试前忘了使能力矩"这个必然导致标定失败的真 bug。
如果假总线只是"返回期望值"，这个 bug 会一直留到上机。

**③ 每个"留待以后"的设计决定都要留证据**
`RLCA_ESTOP_INPUT_EN = 0` 且**无任何代码引用** ——
留一个无人用的开关，胜过留一段没人测过的代码。

### 8.2 三个踩过的坑（值得记住）

**① 离线单测覆盖不了时序**
1028 项全绿的同时，真机周期已经掉到 92 Hz（见 §5.4）。
**"逻辑正确"与"时序没被破坏"是两件事**，后者只能真机验。

**② `.uvprojx` 的数字枚举不能猜**
`Optim` 我猜 4（以为 `-Os`）→ 链接失败；`PackID` 我抄参考工程的 2.3.0
→ 与实际装的 2.4.1 不符。**两个都必须靠实测确定。**
另外这三个字段**为空就会让 uVision 闪退**：
`FlashDriverDll` / `RegisterFile` / `SFDFile`。

**③ 校验脚本要查"语义"，不能只查"语法"**
`.uvprojx` 损坏后**XML 完全良构**，所以文件列表校验全过。
因此给 `check-uvprojx.ps1` 补了**结构完整性**检查
（必需区块 + 空字段 + `uAC6` 合法性），并用残缺版做了**反向验证**
（准确报出全部 10 个问题）。

### 8.3 一条关于"超出范围"的提醒

USART3 转发是**原定不做**的项（§5.4）。我实现时**没先读
`36-esp32-plan.md` §2.2**（那里已经写明了"必须非阻塞 + 必须降频"），
结果第一版踩了两个禁区。

**教训**：**动手前先把该项目已有的相关文档读完** ——
即使那不在自己的任务文档集合里。这次是 ESP32 侧的真机观测
替我发现了问题，属于运气好。
