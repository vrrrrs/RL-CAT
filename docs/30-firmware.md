## 3. ⭐ 表二：关节限位

### 3.1 ⚠️⚠️ 两个 URDF 的 thigh 上限不同 —— 固件必须用哪个？

| 关节 | 硬件 URDF<br>`hardware/mechanical/URDF/robot.urdf` | 训练 URDF<br>`Sim/RL/urdf/robot_sim.urdf` |
|---|---|---|
| `*_hip` | 0 ~ +40° | 0 ~ +40° |
| **`*_thigh`** | **−35° ~ +30°** | **−35° ~ +90°** ⚠️ |
| `*_calf` | −60° ~ +60° | −60° ~ +60° |

**⭐ 结论：固件应采用【训练 URDF 的 90°】。**

**理由：** 训练好的策略是在 **90°** 限位下训出来的，它的摆腿动作依赖这 90° 的空间。如果固件按硬件 URDF 的 30° 限幅，真机上策略会被硬性削掉摆腿幅度，导致行走异常。

**⚠️ 这个不一致需要回填到硬件 URDF** —— 但目前 `hardware/mechanical/` 由人工负责整理，此处只记录结论。

### 3.2 固件应实现的限位（弧度与度）

| 关节类型 | lower (rad) | lower (°) | upper (rad) | upper (°) |
|---|---|---|---|---|
| **`*_hip`**（外摆） | `0` | 0° | `0.6981317` | **+40°** |
| **`*_thigh`**（髋俯仰） | `-0.61086524` | −35° | `1.5707963` | **+90°** |
| **`*_calf`**（膝） | `-1.0471975` | −60° | `1.0471975` | **+60°** |

**⚠️ `*_hip` 是不对称的（0 ~ +40°），不做内摆（负方向）。**

### 3.3 关节零位与偏置

```
URDF 的 q = 0  ←→  机器人处于【弯腿站立姿态】
```

**✅ 已实测确认**（`Sim/RL/RL-CAT-训练实施报告.md` §4.3）：`default_joint_angles` 全为 0，机器人确实站立成功。

**⚠️ 因此 `q_default = [0]*12`。**

**转换公式：**

```c
// 关节角(rad) → 舵机步数
int16_t joint_to_servo(uint8_t idx, float q_rad) {
    float steps = q_rad * (4096.0f / (2.0f * 3.14159265f));
    float s = g_joints[idx].dir * steps + g_joints[idx].offset;
    return (int16_t)(s + 0.5f);
}
```

**⚠️ `dir` 字段处理左右腿舵机安装方向差异（`+1`/`-1`），不要在上层写 if。**

#### 3.3.1 ⭐⭐⭐ 三个"零"必须分清（2026-10-16 上机验证通过，标定关结束）

**这一节是踩过多轮坑之后定下来的。混淆这三者会导致"标定完立刻大幅运动"。**

| 名字 | 姿态 | 关节角 | 舵机编码器读数 |
|---|---|---|---|
| **URDF 零位** | **弯腿站姿**（`default_joint_angles` 全 0） | **q = 0** | **= `offset`** ⭐ |
| **标定姿态** | **腿伸直、垂直向下、髋水平** | q = ±`q_calib`（**幅值**） | **2048**（上位机里设的） |
| 编码器零 | 舵机自己的 0 位 | 无关 | 0 |

**⇒ `offset[i]` 的精确含义：URDF 零位（弯腿站姿）下，舵机 i 的编码器步数。**
**⇒ 换算恒等式：`step(q) = dir × q × STEPS_PER_RAD + offset`。**

**转换公式（标定姿态 → offset）：**

```
已知 step(q_calib) = 2048（项目负责人在上位机里把"腿伸直"设成 2048）
⇒ offset = 2048 − dir × q_calib × STEPS_PER_RAD
```

**⚠️⚠️ `q_calib` 是【幅值，全为正】，符号完全交给 `dir` 表达。**

**这是本项目最容易搞错的一处，务必记住：**

> `dir` 本身编码了"关节角增大 → 编码器增大(+1) 还是减小(−1)"。
> 如果再给 `q_calib` 加上左右镜像符号，两个符号会**互相抵消**，
> 于是左右两侧的 `offset` 跑到 2048 的**同一侧** —— 那是错的。

**实测证据（项目负责人用 `W` 命令把关节送到 offset 看姿态）：**

| 关节 | dir | q_calib | offset | 与 2048 |
|---|---|---|---|---|
| lf_thigh | +1 | 45° | 2048 − 512 = **1536** | **< 2048** ✅ |
| rf_thigh | −1 | 45° | 2048 + 512 = **2560** | **> 2048** ✅ |
| lf_calf | −1 | 90° | 2048 + 1024 = **3072** | **> 2048** ✅ |
| rf_calf | +1 | 90° | 2048 − 1024 = **1024** | **< 2048** ✅ |

**左右分居 2048 两侧 = 物理镜像对称。**

**⚠️ 标定时机器人必须真的处于"腿伸直"姿态** —— 因为固件按 `q_calib` 反推。
若标定时腿是自然下垂/被外力顶住的，`q_calib` 的假设就不成立。

#### 3.3.2 关节方向表（`dir`，实测确定）

**`dir` 不能只从 URDF 推断**（它取决于舵机安装朝向），**必须实测**。

**⚠️ 2026-10-16 最终确定值（按舵机 ID）：**

```
1↔+1   2↔−1   3↔−1   4↔+1      ← hip    外摆时编码器增/减
5↔+1   6↔+1   7↔−1   8↔−1      ← thigh  前摆时编码器增/减
9↔−1   10↔−1  11↔+1  12↔+1     ← calf   （相对 thigh 的符号关系）
```

**⚠️ calf 那四个（ID 9~12）在 2026-10-16 被**整体翻转**过一次** —— 初版按"与 thigh 同号"猜测，实测定为反向。**这是"不能靠推断、必须实测"的最好例证。**

**集中定义在 `firmware/stm32/Core/Inc/rlcat_config.h` 的 `RLCA_JOINT_DIR_INIT`。上层代码不含任何 `if (左/右)`。**

**⚠️ 验证方法（`W` 命令，见 `docs/41-firmware-debug-commands.md`）：**

```
T 1                 ← 打开手动力矩覆盖（否则 ⑥b 会掐断位置帧）
W <j> <offset_j>    ← 把关节 j 送到它自己的 offset
K                   ← 确认停住 + 目视姿态
```

**若送到的位置正好是"弯腿站姿里该关节该在的位置"，则 `dir` 与 `offset` 都正确。**


**标定方法：** 机器人自然站立 → 卸载力矩 → 等稳定 → 读 12 个舵机位置 → 存为 `offset`。详见设计书 §6。

## 5. ⭐ 表四：观测 / 动作向量布局

### 5.1 观测：**47 维**（⚠️ 不是 50 维）

**⚠️ 旧交接文档写的 50 维是【设计值】，实际实现是 47 维（"方案 C"）。固件必须按 47 维拼接。**

| 索引 | 内容 | 维度 | 缩放 | 数据来源 |
|---|---|---|---|---|
| **0–2** | 重力向量（机身系） | 3 | 1.0 | IMU 四元数 → **Pi 反算** |
| **3–5** | 机身角速度（陀螺） | 3 | **×0.25** | IMU |
| **6–8** | 速度指令 (vx, vy, ωz) | 3 | 1.0 | **Pi 自己产生** |
| **9–20** | 关节位置（**相对 `q_default`**） | 12 | 1.0 | 舵机反馈 |
| **21–32** | 关节速度 | 12 | **×0.1** | 舵机反馈 |
| **33–44** | 上一帧动作 | 12 | **×4.0** | **Pi 自己缓存** |
| **45–46** | 步态相位 sin / cos | 2 | 1.0 | ⭐ **STM32 产生，经 TEL_FAST 下发** |
| | **合计** | **47** | | |

**⚠️ 三个关键点：**

| # | 要点 |
|---|---|
| 1 | **关节位置是相对 `q_default` 的**（即 `q - q_default`）。因为 `q_default = 0`，实际就是 `q` 本身 |
| 2 | **关节速度缩放是 ×0.1**，⚠️ upstream legged_gym 默认是 0.05，已按本项目改为 0.1 |
| 3 | ⭐ **步态相位由 STM32 产生**（不是 Pi）—— 理由见 §5.1.1 |

### 5.1.1 ⭐ 为什么步态相位由 STM32 产生

| # | 理由 |
|---|---|
| **1** | **唯一源头** —— 如果两边各产生一份，数值会不一致 |
| **2** | **时钟精度** —— STM32 的 TIM 精确到晶振级（±20 ppm）；Pi 5 的 Linux 用户态循环抖动 0.1~1 ms，**会累积相位误差** |
| **3** | **STM32 本来就是节拍源** —— 100 Hz 周期由 STM32 发起 |
| **4** | **成本极低** —— 查表或 `arm_sin_f32`，每周期 2 次 |

**⚠️ 相位算法（必须与训练侧严格一致，来自 `rlcat_env.py:104-106`）：**

```c
// 训练侧：phase = (phase + dt * gait_freq) % 1.0
//         sin_p = sin(2*pi*phase);  cos_p = cos(2*pi*phase)
// gait_freq = 3.0 Hz（rlcat_config.py 的 control.gait_freq）
// ⚠️ 每【控制周期】推进 3.0/100 = 0.03

#define GAIT_FREQ_HZ  3.0f
static float s_phase = 0.0f;

s_phase += GAIT_FREQ_HZ / 100.0f;      // += 0.03
if (s_phase >= 1.0f) s_phase -= 1.0f;

int16_t gait_sin = (int16_t)(arm_sin_f32(2.0f*PI*s_phase) * 32767.0f);
int16_t gait_cos = (int16_t)(arm_cos_f32(2.0f*PI*s_phase) * 32767.0f);
```

**⚠️ 推导（验证 0.03 正确）：**

```
训练侧每物理步推进：dt × f = (1/200) × 3.0 = 0.015
decimation = 2 → 每 2 个物理步组装一次观测
→ 每控制周期推进：2 × 0.015 = 0.03
一个完整周期 = 1/0.03 ≈ 33.3 周期 = 0.333 s  → 3.0 Hz  ✅ 自洽
```

**⚠️ 完整定义（含 TEL_FAST 字节偏移）见 [`firmware/doc/协议规范_树莓派通信.md`](../firmware/doc/协议规范_树莓派通信.md) §4.4.1。**

**⚠️ 旧文档的 50 维里那 3 个"保留维"，将来若要加，直接往后接（索引 47–49），已有顺序一字不动。**

**⚠️ legged_gym 原生 48 维里有 3 维机身线速度，已被**删除** —— 真机没有这个传感器，策略一旦依赖它在 sim-to-real 时必崩。**

**已导出的策略位置**：`Sim/RL/exported/`

**⚠️ ONNX 导出** —— 现有 `13_export_policy.py` 导出的是 TorchScript + numpy 权重，**需要补一条 ONNX 导出路径**（`torch.onnx.export`，`dynamic_axes=None`，固定 batch=1 × 47 维输入）。

**⚠️ 导出后必须做数值一致性验证：** 同一组输入下，ONNX 输出与 PyTorch 输出的最大偏差 **< 1e-5**。ONNX 导出偶有算子差异，这一步不能省。

## 8. 推荐推进顺序

```
第 1 步  按 [CubeMX配置清单] 修配置 + 跑通上电自检      ← 时钟/中断/缓冲是地基
   ↓
第 2 步  BSP 层：UART 中断 + 环形缓冲，用串口自测
   ↓
第 3 步  servo_bus：先控 1 个舵机 → 再到 12 个         ← 最难，留足时间
   ↓
第 4 步  link_pi：PC 端写 Python 模拟树莓派，跑通帧协议
   ↓
第 5 步  关节标定：读舵机位置 → 存 Flash
   ↓
第 6 步  app_mode + app_safety（状态机 + 安全机制）
   ↓
第 7 步  与树莓派联调
```

**⚠️ 第 3 步和第 4 步可以并行**（一个调舵机、一个调通信），互不阻塞。

**⚠️ 但第 1 步必须先做完** —— 8 MHz 时钟或未配对的中断会让后面每一层性能不足，排查时容易误判。

## 9. 三个最容易搞错的技术点

### 9.1 `SC.c` 和 `SCSerail.c` 是两个不同的文件

```
SC.c        = 协议层（组帧、校验、syncReadBegin、malloc 缺陷在这里）
SCSerail.c  = 串口底层（readSC、readSCTimeOut、IOTimeOut、SCDelay）← 拼写错误，实为 SCSerial
```

**搜超时相关代码去 `SCSerail.c`。**

### 9.2 官方 `uart.c` 必须整体替换

```
原因①：基于 StdPeriph 库，与 CubeMX 的 HAL 冲突
原因②：自带 USART1_IRQHandler / USART2_IRQHandler，与 stm32f1xx_it.c 重复定义
```

**确切签名（来自官方 `uart.h`）：**

```c
void    Uart_Init(uint32_t baudRate);
void    Uart_Flush(void);
int16_t Uart_Read(void);                      // ⚠️ 读【单字节】，空时返回 -1
void    Uart_Send(uint8_t *buf, uint8_t len); // ⚠️ len 是 uint8_t
```

### 9.3 ⚠️ 关节限位有个"两个 URDF 不一致"的坑

**见 §3.1：train URDF 的 thigh 上限是 90°，硬件 URDF 是 30°。固件用 90°。**
