## 0. ⭐ 核心定位

**ESP32-C3 的首要任务是：【在没有接入树莓派时，提供无线调试通道】。**

```
┌──────────────────────────────────────────────────────────────┐
│  阶段一：固件开发期（Pi 5 还没上）                              │
│                                                              │
│   笔记本 ──WiFi──→ ESP32 ──UART3──→ STM32 ──→ 舵机           │
│                                                              │
│   用途：                                                      │
│     · 测试单个舵机是否正常                                      │
│     · 跑关节零点标定流程                                        │
│     · 手动驱动某个关节运动                                      │
│     ⭐ 整个 servo_bus 和标定流程可以在【没有 Pi 5】的情况下调通   │
├──────────────────────────────────────────────────────────────┤
│  阶段二：接入 Pi 5 之后                                        │
│                                                              │
│   Pi 5 ──UART1──→ STM32        （唯一的策略指令源）              │
│   ESP32 ──UART3──→ STM32       （只读遥测 + 硬急停线）           │
│                                                              │
│     · 步态相位、急停 → 由 Pi 5 负责                             │
│     · ESP32 退居二线：遥测监控 + 独立的硬急停                     │
└──────────────────────────────────────────────────────────────┘
```

**⚠️ 这个设计的关键价值：固件开发不依赖 Pi 5 就绪。** 两个子系统可以并行开发。

## 1. 已确定的决策

| # | 决策 | 值 |
|---|---|---|
| 1 | **固件方案** | **自写透传（ESP-IDF）**，不用 ESP-AT |
| 2 | **WiFi 模式** | **AP 模式 + TCP Server** |
| 3 | **接口** | USART3（PB10/PB11），**115200**（低频调试通道） |
| 4 | **指令仲裁** | **Pi 在线时以 Pi 为准**；ESP32 只在 Pi 离线时可注入指令 |
| 5 | **急停** | **保留一根独立硬线** ⭐ |
| 6 | 波特率 | **115200**（与 STM32 侧 USART3 一致），见下 |

**⚠️ 波特率为什么是 115200 而不是 921600（2026-10-10 修订）：**

本条原定 921600。改成 115200 的理由是**可靠性优先于带宽**，
并由此带来两条必须同时成立的约束（详见 [`36-esp32-plan.md`](36-esp32-plan.md) §2.2）：

```
① 发送必须【非阻塞】（中断/DMA）
   阻塞发送 103 B 的耗时 = 103 × 10 / 波特率：
       921600 → 1.12 ms    （实测把 100 Hz 环拖到 ~92 Hz）
       115200 → 8.93 ms    （会砸到 ~53 Hz，控制环崩溃）
   而 RL 的 decimation=2 要求控制环【严格 100 Hz】。

② 镜像必须【降频到 10 Hz】
   115200 线速率约 11.5 kB/s：
       100 Hz 全量 = 10.3 kB/s = 90%  → 必然丢帧
        10 Hz      = 1.5 kB/s  = 13%  → 余量充足
   ⚠️ 10 Hz 完全够用：本模块的仲裁过期阈值是 500 ms。
```

**✅ STM32 侧现状**：已实现 `115200 + 中断发送 + TEL_FAST 降频到 10 Hz`
（`firmware/stm32/Core/Src/esp_fwd.c`）；TEL_STATUS（本就 10 Hz）与
HEARTBEAT（1 Hz）也镜像，但不再降频。

**⚠️ 为什么不用 ESP-AT：** 透传本身很简单，但**"能加逻辑"这个能力很值钱** —— 尤其是本地急停判断。ESP-AT 想加定制逻辑会很别扭，而且 AT 指令有额外延迟。

## 2. 硬件与引脚

### 2.1 与 STM32 的连接

| STM32 | ESP32-C3 | 说明 |
|---|---|---|
| PB10 (USART3_TX) | **RX** | ⚠️ 交叉 |
| PB11 (USART3_RX) | **TX** | ⚠️ 交叉 |
| GND | GND | 共地 |
| **（新增）某个 GPIO** | **急停输出** ⭐ | 见 §5 |

**⚠️ UART3 的接线是【标准交叉】**（和 USART1↔Pi 一样）—— 因为 ESP32-C3 上标的是它自己的 TX/RX。

**⚠️ 对照记忆：三路 UART 里只有 USART2（舵机控制板）是直连，USART1/USART3 都是交叉。**

### 2.2 ⚠️ 供电（必须确认）

**设计要求（来自 `archive/方案_v1.md` §7）：独立 3.3 V，≥800 mA。**

**理由：** WiFi 发射峰值 **500 mA**。如果挂在 STM32 核心板的 LDO（AMS1117，约 300 mA）上，会拉垮 3.3 V 导致 **STM32 复位**。

**⚠️ 但实测原理图显示三个器件挂在同一条 3.3 V 上：**

```
      独立 3.3V 降压（≥800mA）
              │
              ├──→ STM32
              ├──→ JY901P
              └──→ ESP32-C3
```

**这可能有两种情况：**

| 情况 | 判断 | 后果 |
|---|---|---|
| **A. 该降压模块本身 ≥800 mA** | ✅ 没问题 | 三器件共用一条足够强的 3.3 V |
| **B. 该降压实际能力不足** | ❌ **会复位** | WiFi 发射时 3.3 V 塌陷 → STM32 复位 |

**⚠️ 这是一个必须实测确认的硬件问题：**

```
测试方法：
  ① 让 ESP32 持续发射 WiFi（例如 iperf 打流）
  ② 用示波器量 3.3 V 轨的纹波与跌落
  ③ 同时监控 STM32 是否复位（看心跳 LED 是否重启）

判据：3.3 V 跌落 < 100 mV，STM32 不复位
```

**⚠️ 另外两个必做的硬件措施：**

| # | 措施 |
|---|---|
| 1 | **ESP32 的 5V/3.3V 输入加 100 µF 电解 + 100 nF 瓷片**（已列为"建议焊上"，**WiFi 尖峰必须靠这个**） |
| 2 | **天线净空** —— ESP32-C3 的板载天线周围要留空，不要贴金属 |

### 2.3 ⚠️ 待确认：UART3 是否挂了两个负载

**原理图里有 U6（标 ESP32）和 U9（标 ESP32-C3）同时用 TX3/RX3。**

**⚠️ 如果这是两个独立的接口，两个 TX 会互相打架（一个推高、一个拉低）。**

**必须确认：**
```
□ 是同一个接口的两种画法（则无碍）
□ 还是两个独立器件（则必须二选一，或加缓冲）
```

**⚠️ 这个问题不解决，ESP32 方案无法落地。**

## 3. 软件架构

```
esp32/
├── main.c           初始化 + 主任务
├── uart_bridge.c    ⭐ UART3 ↔ TCP 双向透传
├── wifi_ap.c        AP 模式 + TCP Server
├── injector.c       ⭐ 本地指令注入（调试模式）
├── safety.c         ⭐ 急停逻辑（本地判断 + 硬线驱动）
├── protocol.c       帧编解码（与 STM32/Pi 共用同一套）
└── config.h         SSID / 端口 / 波特率 / 超时
```

### 3.1 三个任务的职责

| 任务 | 职责 | 优先级 |
|---|---|---|
| **UART 收** | 从 STM32 收字节 → 推给所有 TCP 客户端 | 高 |
| **TCP 收** | 从 TCP 客户端收字节 → 交给 `injector` 判断 | 中 |
| **急停监控** | 监控本地输入 → 驱动硬急停线 | **最高** |

**⚠️ 急停任务必须优先级最高，且不能被其他任务阻塞。**

### 3.2 `uart_bridge.c` —— 透传

**核心逻辑很简单：**

```c
// 方向 1：STM32 → WiFi（广播给所有 TCP 客户端）
void uart_rx_task(void *arg) {
    uint8_t buf[256];
    while (1) {
        int n = uart_read(buf, sizeof(buf), portMAX_DELAY);
        if (n > 0) {
            // 广播给所有已连接的客户端
            for (int i = 0; i < MAX_CLIENTS; i++) {
                if (clients[i].active) {
                    send(clients[i].sock, buf, n, 0);
                }
            }
        }
    }
}

// 方向 2：WiFi → STM32（透传 + 拦截）
void tcp_rx_task(void *arg) {
    uint8_t buf[256];
    while (1) {
        int n = recv_active_client(buf, sizeof(buf));
        if (n > 0) {
            // ⚠️ 先交给 injector 判断是否是特殊命令
            if (!injector_handle(buf, n)) {
                uart_write(buf, n);          // 不是特殊命令 → 原样透传
            }
        }
    }
}
```

**⚠️ 三个注意点：**

| # | 注意 |
|---|---|
| 1 | **UART3 用 115200** —— 低速下逐字节中断完全够用，不必上 DMA；真正的要求在 STM32 侧：**发送必须非阻塞**（见 §1 的波特率说明） |
| 2 | **TCP 多客户端** —— 至少支持 2 个（一个看遥测、一个发命令） |
| 3 | **TCP 缓冲要够** —— 降频后是 10 Hz 发 103 字节帧，WiFi 拥塞时会积压；缓冲不够会丢数据 |
| 4 | **收发速率按 115200 配置** —— UART1 配 115200 8N1，不要沿用早期的 921600 |

**⚠️ 带宽核算（2026-10-10 修订为 115200 + 10 Hz）：**

```
STM32 → ESP32：TEL_FAST  103 B × 10 Hz = 1030 B/s
               TEL_STATUS 47 B × 10 Hz =  470 B/s
               HEARTBEAT   7 B ×  1 Hz =    7 B/s
               ─────────────────────────────────────
               合计                   ≈ 1500 B/s = 115200 线速率的 13%  ✅
ESP32 → WiFi  ：同样的量 → 约 12 kbps，对 WiFi 是极轻的负载  ✅

⚠️ 旧版这里写的是 "103 B × 100 Hz = 10.3 kB/s，约 82 kbps"。
   那是 921600 时代的数字。降到 115200 后必须同时降频，
   否则 10.3 kB/s 会占满 90% 线速率（详见 §1 的波特率说明）。
```

### 3.3 `wifi_ap.c` —— AP + TCP Server

| 参数 | 建议值 |
|---|---|
| SSID | `RL-CAT-XXXX`（XXXX 取 MAC 后四位，避免多机冲突） |
| 密码 | 固定简单密码（现场调试用）或开放 |
| IP | `192.168.4.1`（ESP-IDF 默认 AP 地址） |
| **TCP 端口** | **`3333`**（避免用 <1024 的保留端口） |
| 最大客户端 | 4 |

**⚠️ AP 模式的优点（项目已选）：笔记本连上就能用 TCP 工具收发，PC 侧零驱动。**

**⚠️ 但要注意信道冲突：** 现场如果有多个 WiFi，AP 的信道要能自动选择（ESP-IDF 默认会自动扫）。

## 4. ⭐ `injector.c` —— 本地指令注入（调试模式）

**这是"阶段一"能独立调试的关键。**

### 4.1 工作原理

**透传的数据流里，STM32 的帧和"人为发的命令"混在一起。用一个简单的区分规则：**

```
约定：TCP 客户端发来的数据里，
      · 以 0xAA 0x55 开头的   → 是标准协议帧 → 【原样透传给 STM32】
      · 其他任何内容           → 是【本地调试命令】→ 被 injector 拦截
```

**⚠️ 这样设计的好处：上位机（笔记本）可以用完全相同的协议帧格式给 STM32 发指令，也可以发简短的文本命令做本地操作。**

### 4.2 本地命令集（建议）

**用单字符命令，便于手动敲：**

| 命令 | 作用 |
|---|---|
| **`?`** | 打印帮助 |
| **`i`** | 查询 STM32 状态（转发一次 TEL_STATUS 请求） |
| **`s <id> <pos>`** | 直接驱动单个舵机（绕过 Pi）⭐ 测试用 |
| **`c`** | 进入标定模式 |
| **`z`** | 卸载力矩（舵机变软） |
| **`e`** | **软急停**（发 CMD_MODE(ESTOP)） |
| **`r`** | 复位/重连 |
| **`k`** | 保持连接（心跳） |

**⚠️ `s` 命令是"测试单个舵机"的核心** —— 它让固件开发者在没有 Pi 5 的情况下验证每个舵机。

**⚠️ 实现方式：`injector` 把这些文本命令翻译成标准的 `CMD_JOINT` / `CMD_MODE` 帧，注入到 UART3。**

### 4.3 ⚠️ 指令仲裁（关键设计）

**问题：Pi 和 ESP32 都能给 STM32 发指令，谁优先？**

**选定规则（按你的决策）：**

```
① 【Pi 在线时】—— 以 Pi 为准
     ESP32 的 CMD_JOINT / CMD_MODE 被【丢弃】（但仍允许查询类命令）
     判据：STM32 上发来的 TEL_FAST.status 里 STAT_LINK_OK 位 == 1

② 【Pi 离线时】—— ESP32 可以注入
     允许 CMD_JOINT / CMD_MODE / 标定命令

③ 【急停】—— 例外，任何情况下都允许（见 §5）
```

**⚠️ ESP32 怎么知道 Pi 是否在线？**

**两种做法：**

| 做法 | 说明 |
|---|---|
| **A. 解析 TEL_FAST 的 status 字节** ⭐ | 需要解帧，但信息最准确（直接来自 STM32） |
| B. ESP32 自己观察 UART 流量 | 简单（有流量就说明 Pi 在通信），但可能误判 |

**👉 推荐 A** —— 既然 STM32 已经告诉我们 `STAT_LINK_OK`，直接用最可靠。

**⚠️ 但 A 需要 ESP32 解析协议帧** —— 这会让它从"哑管道"变成"懂协议"。**这是有意的取舍：换来准确的仲裁依据。**

**⚠️ 实现要点：** ESP32 只需要解析 TEL_FAST 的 `status` 字段（偏移 94），**不需要解析整个帧** —— 找到帧头、读 LEN、跳到偏移 94、取一个字节即可。

## 5. ⭐ `safety.c` —— 硬急停线

### 5.1 为什么要有硬线

```
急停的价值在于【软件全挂了也能停】。

如果急停依赖：ESP32 的 WiFi 正常 + TCP 正常 + 固件正常 + STM32 的 UART 正常
→ 那它就不是最后一道防线。
```

**👉 一根线 + 一个按键的成本很低，但可靠性完全不同。**

### 5.2 建议的实现

```
物理急停按钮 ──┬──→ 直接切舵机动力（最高可靠性）⭐
              │
              └──→ 或 → ESP32 的一个 GPIO → STM32 的一个输入引脚
                        （STM32 检测到低电平 → 立即进入 ESTOP）
```

**两个方案对比：**

| 方案 | 可靠性 | 代价 |
|---|---|---|
| **A. 直接切舵机动力** ⭐ | **最高**（纯机械/电气） | 机器人会**瞬间瘫倒**（无缓冲） |
| **B. 经 ESP32/STM32 软处理** | 中（依赖 MCU 活着） | 可以**缓慢趴下**（更安全） |

**👉 建议两者都做：**

```
一级（按钮直切动力）→ 用于"要立刻停"的紧急情况
二级（软急停）      → 用于"要安全停下"的常规情况
```

**⚠️ 如果只做一个，选 A** —— 宁可瘫倒，也不要停不下来。

### 5.3 STM32 侧的配合

**STM32 需要一个输入引脚检测急停。建议：**

| 项 | 建议 |
|---|---|
| 引脚 | 从 PB12–PB15 里选一个（已预留） |
| 配置 | 上拉输入 + EXTI 中断（下降沿触发） |
| 中断优先级 | **最高**（不低于舵机总线） |
| 动作 | 立即进入 ESTOP：卸载力矩 → 进入安全状态 |

**⚠️ 这个改动需要同步到 [`30-firmware.md`](30-firmware.md) §4（引脚表）。**

## 6. 安全与健壮性

| 机制 | 说明 |
|---|---|
| **WiFi 断连保护** | 客户端断开时，ESP32 **不改变 STM32 状态**（不要假装 Pi 离线就抢控制权） |
| **注入速率限制** | 防止笔记本发太快把 UART3 塞满（STM32 的 USART3 缓冲有限） |
| **命令白名单** | 只允许预定义命令，防止误操作 |
| **日志** | ESP32 自己也要能输出状态（通过 TCP 或串口） |
| **看门狗** | 启用 ESP-IDF 的 task watchdog |

**⚠️ 第一条特别重要：**

```
ESP32 断连 ≠ Pi 离线。
不要在 WiFi 断开时让 ESP32 自动接管控制 —— 
那是"因为笔记本关机了，所以机器人开始乱走"的经典事故。
```

## 9. 开发顺序

```
① 让 ESP32 跑起 AP + TCP Server
   验收：笔记本能连上并收发任意字节

② UART3 透传（只做 STM32 → WiFi 方向）
   验收：笔记本能看到 STM32 的 TEL_FAST 字节流

③ 加上 WiFi → STM32 方向
   验收：能透传标准协议帧，STM32 正确响应

④ 加 injector（本地命令）
   验收：⭐ 用 `s 1 2048` 能驱动 1 号舵机

⑤ 加仲裁逻辑（解析 status）
   验收：Pi 在线时 ESP32 的关节指令被丢弃

⑥ 加硬急停
   验收：按下按钮，舵机立即卸力（或断电）
```

**⚠️ 第 ④ 步完成时，固件开发者就已经可以在没有 Pi 5 的情况下调试整个舵机子系统了。**
