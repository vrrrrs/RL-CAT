# 固件上机验收单（Firmware Bring-up Acceptance）

> **文档编号**：DOC-FW-ACCEPT-001 ｜ **版本**：v1.0 ｜ **日期**：2026-10-10
> **面向对象**：执行上机验证的人（负责人）
> **配套文档**：[`33-firmware-plan.md`](33-firmware-plan.md)（施工方案）
>
> **用法：** 每完成一个阶段（P），本文档对应增加一节。**按顺序做，每条都要留下结论。**
> 固件方无法接触硬件，所以**这一份就是"代码是否真的能用"的唯一判据**。
> 任何一条不通过，把现象（含串口输出、示波器读数）贴回来，固件方据此修。

---

## 通用准备

```
□ 硬件
  · STM32F103C8T6（Blue Pill），已焊/已插好
  · USB-TTL 串口模块 1 个（3.3V 电平！不要 5V）
  · ST-Link（或其它 SWD 下载器）
  · 万用表
  · 3S 电池 + 舵机控制板 + 至少 1 个 ST-3215-C018 舵机（P3 需要）
  · 示波器（P2 的 I2C 项、P3 的总线项需要；没有的话按"替代判据"做）

□ 串口工具（PC 端）
  · 推荐 PuTTY / MobaXterm / minicom
  · 波特率 1000000（1 Mbps），8N1，无流控
  · ⚠️ 很多工具的下拉框没有 1000000，要手动输入
  · 必须打开"本地回显"或用能看到自己输入的模式，否则敲命令看不到字

□ 烧写
  · 固件：firmware/stm32/build/stm32.hex（armclang 命令行构建产物）
    或 Keil 构建产物
  · ⚠️ 第一次烧写前先确认 BOOT0 = 0（从 Flash 启动）
  · ⚠️ PB2 (BOOT1) 必须悬空或下拉
```

## P2 —— BSP 层与上电自检

**本阶段验证：** 时钟、微秒计时、三路 UART 收发、软件 I2C 总线、Flash 标定页、LED/心跳。
**本阶段不涉及：** 舵机、树莓派协议、IMU 解析、状态机。

### 接线

```
USART1 PA9 (TX) ──→ USB-TTL 的 RX
USART1 PA10(RX) ←── USB-TTL 的 TX
GND           ────  USB-TTL 的 GND
（PA0 接电池分压、PA2/PA3 接舵机控制板 本阶段可不接）
```

---

### P2-1 LED 与心跳 ← 最先确认"程序在跑"

| 项 | 内容 |
|---|---|
| 动作 | 上电（或按复位） |
| 预期 | **PC13 上的板载 LED 灭**（自检全通过）或**慢闪**（I2C 总线异常）；**PA8 心跳以 1 Hz 翻转**（亮 0.5 s / 灭 0.5 s）|
| 判据 | 心跳必须是**稳定的 1 Hz**。用手机秒表数 10 次翻转 ≈ 10 s |
| ❌ 不通过的现象 | **PC13 以约 10 Hz 快闪** = 进了 `Error_Handler()`（时钟或外设初始化失败）；**完全不亮也不闪** = 程序没跑（查 BOOT0、供电、晶振）|

> ⚠️ **PC13 快闪（10 Hz）与慢闪（1 Hz）一定要分清** —— 这是固件唯一能告诉你的"启动失败"信号。
> ⚠️ **板载 LED 在 PC13 且是【低电平点亮】**（引脚拉低才亮）。
> 固件用 `RLCA_LED_ACTIVE_LOW` 统一处理极性，全模块只通过一个
> `led_write()` 碰 LED 引脚 —— 换板子只改这一个宏。
> ⚠️ 早期版本把 LED 错配在 PB0 且按高电平点亮写，导致**状态灯永远不亮、
> 所有状态指示（含"启动失败"提示）全部静默**。详见
> [`39-firmware-handover.md`](39-firmware-handover.md)。

### P2-2 时钟 = 72 MHz

| 项 | 内容 |
|---|---|
| 动作 | 串口敲 `s` |
| 预期 | `sysclk_hz = 72000000`、`pclk1_hz = 36000000`、`pclk2_hz = 72000000` |
| 判据 | 三个数**完全相等**才算通过（差一点都是晶振或 PLL 配置不对） |
| 替代判据 | 心跳周期若明显不是 1 Hz（比如 2 倍快/慢），几乎一定是时钟不对 |

**⚠️ 这一条是所有后续测试的地基。** 时钟不对时，1 Mbps 波特率会有误差、微秒延时全错、
心跳周期也不对 —— 后面每一条都会跟着失败，排查时会误判成别的问题。

### P2-3 DWT 微秒计时

| 项 | 内容 |
|---|---|
| 动作 | 串口敲 `s` |
| 预期 | `dwt_ok = 1` |
| 判据 | 必须为 1。为 0 说明 Cortex-M3 的 DWT 没使能，舵机总线的 3 ms 整帧超时会退化成 1 ms 分辨率 |
| 失败后果 | P3 的总线超时会不精确（但不会崩） |

### P2-4 串口 shell 能收发

| 项 | 内容 |
|---|---|
| 动作 | 串口敲 `h` |
| 预期 | 打印出命令帮助（`RL-CAT STM32 shell`…） |
| 判据 | 能看到完整帮助文本 |

**⚠️ 如果乱码：** 99% 是波特率不对（工具没设成 1000000），或 USB-TTL 是 5V 电平。
**⚠️ 如果能收到但敲进去没反应：** 检查 PA10(RX) 是否接到 USB-TTL 的 TX。

```c
// 用这条命令看接收计数是否在动
动作：敲 s
看   ：pi_total 的值
```

| 项 | 内容 |
|---|---|
| 动作 | 敲任意几个字符，再敲 `s` |
| 预期 | `pi_total` 每次都比上次**大**（增量 = 你敲的字符数） |
| 判据 | 计数在涨 = RX 通路正常 |
| 关注 | `pi_overflow` 必须**保持 0**。不涨说明 512 B 环缓够用 |

### P2-5 三路 UART 自发自收 1 万字节无丢失 ⭐

**这是 P2 的门槛项**（固件设计书 §8 阶段 A 验收标准）。

| 项 | 内容 |
|---|---|
| 动作 | 串口敲 `p 10000` |
| 预期 | 固件会往 USART1 发 10000 个递增字节（0x00…0xFF 循环） |
| 判据 | PC 端收到 10000 字节，**无缺失、无错序** |

**做法（有 Python 的话最省事）：**

```python
# 把 COM 口改成你的
import serial, time
s = serial.Serial('COM3', 1000000, timeout=3)
s.reset_input_buffer()
s.write(b'p 10000\r')
data = s.read(10000)
print("got", len(data), "bytes")
expect = bytes(i & 0xFF for i in range(10000))
print("match:", data == expect)
# 如果 match=False，打印第一个不匹配的位置
if data != expect:
    for i,(a,b) in enumerate(zip(data, expect)):
        if a != b:
            print("first mismatch at", i, hex(a), hex(b)); break
```

**⚠️ USB-TTL 模块的注意点：** 很多 CH340/CP2102 模块在 1 Mbps 下会丢字节。
**丢字节时先换一个模块或换成 FT232 再判固件的问题** —— 别急着改固件。

**判据：**
```
□ 收到 10000 字节
□ 内容与期望序列完全一致
□ 固件侧 rx_overflow = 0（敲 s 看）
□ 固件侧 pi_errors    = 0
```

### P2-6 软件 I2C 总线电平与上拉 ⭐（不需要 IMU 就能查硬件）

| 项 | 内容 |
|---|---|
| 动作 | 串口敲 `i` |
| 预期 | `bus_released_high = 1`，且逐个探测 0x50 / 0x51 / 0x68 / 0x6A / 0x6B |
| 判据 | **`bus_released_high` 必须为 1** |

**⚠️ 这一条的价值：** `bus_released_high = 0` 说明 PB8/PB9 释放后没有被拉高
→ **外部 4.7 kΩ 上拉没装、或接错、或总线被拉死**。
这比"读不到 IMU 数据"要早得多、也明确得多。

| 现象 | 含义 | 处理 |
|---|---|---|
| `bus_released_high = 0` | 上拉缺失/短路 | 用万用表量 PB8、PB9 对 3.3V 的电阻，应为 4.7 kΩ |
| 有 ACK | IMU 在线且地址正确 | 把应答的那个地址记下来，P5 用 |
| 全部 no ack | IMU 没接好 / 地址不在这几个里 / 供电没上 | 查 JY901P 的 VCC 与 GND；查手册确认从机地址 |

**示波器项（有条件就做）：**

```
测点：PB8 (SCL)
动作：敲 i（会触发 I2C 访问）
看  ：SCL 频率
判据：100 ~ 400 kHz（固件设计书 §5.4 目标区间）
现状：BSP_I2C_HALF_US = 1 µs ⇒ 理论 ~500 kHz，实测因 GPIO/上拉会更低
调整：偏离区间时改 rlcat_config.h 附近的 bsp_softi2c.h 里的 BSP_I2C_HALF_US
```

### P2-7 Flash 标定页读写

| 项 | 内容 |
|---|---|
| 动作 ① | 初次上电后敲 `s` |
| 预期 ① | `loaded = 0`，`hdr : FF FF FF FF FF FF FF FF …`（整页擦除态） |
| 动作 ② | 敲 `e`（擦除） |
| 预期 ② | `erased`，`loaded` 仍为 0 |
| 判据 | `hdr` 全 FF = 页确实被擦干净了 |

**⚠️ 注意：** P2 阶段还没有"写标定"的命令 —— 写入要等 P6（标定流程）才有。
本阶段只验证**擦除与读取路径**通了。

**替代判据（没有串口时）：** 用 ST-Link 的调试器直接看 `0x0800FC00` 处的内存，
应为 `0xFF` 填满。

### P2-8 遥测统计合理性

| 项 | 内容 |
|---|---|
| 动作 | 敲 `s`，看 `servo_*` 与 `esp_*` 两组计数 |

## P3 —— 舵机总线（servo_bus）

**本阶段验证：** 能否在真实总线上 Ping 到 12 个舵机、SyncWrite 12 个目标位置、SyncRead 12 份反馈。

### ⚠️ 开工前的三件事

```
① 舵机 ID 必须逐个改好（出厂默认都是 1，直接并接 12 个会全部冲突）
   用 Feetech 官方上位机：改一个 → 立刻拔掉 → 再接下一个
   目标 ID：逻辑索引 i → ID i+1
     索引 0..3  = lf_hip=1  lb_hip=2  rf_hip=3  rb_hip=4
     索引 4..7  = lf_thigh=5 lb_thigh=6 rf_thigh=7 rb_thigh=8
     索引 8..11 = lf_calf=9 lb_calf=10 rf_calf=11 rb_calf=12

② 舵机控制板跳线必须在【A 位】（A = UART 控制，B = USB 控制）

③ 接线是【直连】：PA2(TX) → 控制板 TX 端子、PA3(RX) → 控制板 RX 端子
   ⚠️ 控制板端子丝印是按 MCU 侧标注的，照丝印一对一接就是直连
   ⚠️ 与 USART1↔树莓派那条【交叉】接线不同，别搞混
```

### ⚠️ 安全（第一次上电务必这样做）

```
□ 机器人【吊起来】或【架空】，轮子不承重、腿能自由摆动
□ 3S 电池先不接舵机动力，只给控制板与 STM32 供电
   —— 先确认通信通了，再上舵机动力
□ 手边能随时拔掉动力线
```

### P3-1 总线 Ping（12 个 ID）⭐

| 项 | 内容 |
|---|---|
| 动作 | 串口敲 `A` |
| 预期 | 逐个打印 `id 1 -> ACK` … `id 12 -> ACK`，末尾 `found 12 / 12` |
| 判据 | **found = 12** |

**按现象定位问题：**

| 现象 | 最可能的原因 |
|---|---|
| `found 0`，全部 no response | ① 跳线不在 A 位 ② TX/RX 接反了（该直连却交叉了）③ 控制板没供电 ④ 没共地 |
| 只有 `id 1` 应答，其余全无 | **舵机 ID 没改**（12 个都是出厂 ID 1，同时接上就冲突） |
| 应答的 ID 与预期不符 | 改 ID 时记错了；固件侧只改 `RLCA_SERVO_ID(i)` 一个宏即可，逻辑不动 |
| 间歇性 ACK / 时好时坏 | 地环路、供电不足、或线太长；量一下逻辑地对电池负极的压差（应 < 50 mV） |

### P3-2 力矩卸载 / 使能

| 项 | 内容 |
|---|---|
| 动作 ① | 敲 `T 0` |
| 预期 ① | `torque OFF (all)`；**用手能轻松转动每个关节**（舵机变软） |
| 动作 ② | 敲 `T 1` |
| 预期 ② | `torque ON (all)`；**关节变硬、用手掰有明显阻力** |

**⚠️ 这一步必须先于任何控位动作** —— 力矩没使能时舵机不动，看起来会像"通信坏了"。

### P3-3 单关节控位 ⭐（验证方向与限幅）

| 项 | 内容 |
|---|---|
| 准备 | 敲 `T 1` 使能力矩 |
| 动作 | 敲 `P 8 0`（把逻辑索引 8 = `lf_calf` 写到步数 0） |
| 预期 | 该舵机移动到其编码器 0 位附近 |
| 再试 | `P 8 500`、`P 8 1000`，观察是否单调移动、方向是否与 URDF 正方向一致 |

**⚠️ 现在还没有标定，所以 `step` 是【编码器绝对位置】**，不是"相对站姿的角度"。
本步只验证"能控、能动、方向合理"，精确的角度对应关系要等 P6 标定。

| 判据 | 说明 |
|---|---|
| ✅ | 目标舵机动、其余不动 |
| ✅ | 给的步数变大时朝同一方向移动 |
| ❌ 现象：舵机嗡嗡响但不动 | 目标位置超出该舵机的机械/寄存器限位；换一个步数 |
| ❌ 现象：动了但方向与 URDF 相反 | **记下是哪个关节** —— 这就是 P6 要把 `RLCA_JOINT_DIR_INIT` 里对应项改成 `-1` 的依据 |

### P3-4 SyncWrite 12 个舵机同时动作 ⭐

| 项 | 内容 |
|---|---|
| 动作 | 敲 `F 2048 0` |
| 预期 | **12 个舵机同时**开始运动到 2048 附近（不是依次、不是有先有后） |
| 判据 | 同时性用肉眼判断；要量化就用示波器看信号线上的帧 |

**⚠️ 如果看到"依次动"**，说明帧被拆成了 12 条单机指令 —— 那是 `servo_bus_write_one` 的路径，
不是 `start_cycle` 的 SyncWrite 路径。检查 `P`/`F` 的用法区别。

**⚠️ 这一步会真的让 12 个舵机同时上电堵转电流**，务必确保电池能提供 ≥25 A 连续，
且舵机动力走 16 AWG 粗线直供（绕过控制板）。

### P3-5 SyncRead 反馈 + 统计 ⭐

| 项 | 内容 |
|---|---|
| 动作 | 等 1 秒，敲 `B` |
| 预期 | `state = 0`（空闲）、`ok_reads` 在稳定增长、`failed_reads`/`timeouts`/`crc_err` 保持很小 |
| 判据 | **连续跑 1 分钟，`crc_err` 与 `timeouts` 应该基本不涨** |

**关键字段解读：**

```
tx_frames     发出去的帧数（SyncWrite + SyncRead 各算一次）
rx_frames     成功解析的【舵机反馈帧】数（每轮正常是 12）
ok_reads      完整读回 12 帧的轮次  ← ⭐ 这个应该 ≈ tx_frames/2
failed_reads  没读全 12 帧的轮次
timeouts      整帧 3 ms 硬超时次数（应为 0）
idle_timeouts 靠"短暂静默"提前判结束的次数（正常情况会有，属正常）
crc_err       校验错（应为 0；不为 0 说明丢字节或噪声）
short         丢弃的杂散字节（正常为 0）
last_txn_us   上一轮事务耗时（预期 2000~3000 µs）
max_txn_us    最大事务耗时（预期 < 3000）
last_txn_us 必须 < 3000  ← ⭐ 验收 #12
```

**下面这行是最有信息量的：**

```
动作：敲 B
看  ：j0 id=1 pos=... spd=... load=... V=... T=... err=... V
判据：12 行末尾都应该是【V】（valid）
      pos 值应与你刚才 P/F 命令指定的步数接近
      V 列（电压，0.1 V 单位）应 ≈ 电池电压 × 10（例如 11.5 V → 115）
      T 列（温度）应接近室温
```

**⚠️ 若 `V=` 读数明显不对**（比如 0 或几百），说明反馈帧里的字节偏移理解错了 —— 把 `B` 的完整输出贴回来。

### P3-6 掉线恢复 ⭐（验收 #7）

| 项 | 内容 |
|---|---|
| 动作 ① | 保持 `B` 在跑，**热拔掉一个舵机的线** |
| 预期 ① | `failed_reads` 开始增长，`rx_frames` 每轮变 11；**其余 11 个舵机的 `V` 仍为 valid** |
| 动作 ② | 插回去 |
| 预期 ② | `failed_reads` 停止增长，`ok_reads` 恢复增长 |
| 判据 | **掉一个舵机不能让总线停摆**，也不能让 STM32 卡住 |

**⚠️ 关键点：** 拔掉一个舵机后，回复只有 11 帧。
固件用"短暂静默（200 µs）"判回复结束，所以**不需要等满 3 ms** 就能解析完 11 帧 ——
这也是 `partial round took xxxx us` 那类统计的意义。

### P3-7 总线断开（全部丢帧）⭐（验收 #8）

| 项 | 内容 |
|---|---|
| 动作 | **拔掉控制板的信号线**（或拔舵机总线），敲 `B` |
| 预期 | `timeouts` 开始增长；`last_txn_us ≈ 3000` 量级；`err_flags` 出现 BUS_TIMEOUT 位 |
| 判据 | **每一轮必须在 ~3 ms 内返回**，不能无限等 |

**⚠️ 这一条是官方库的致命缺陷所在**（伺服总线模块设计 §3 缺陷 1）：
官方 `readSC` 的超时是"字节间隔"，12 个舵机全失联会累计 6~12 ms，直接吃掉整个 10 ms 周期。
我们的实现是外层 3 ms 整帧硬超时。

**量化判据：**
```
□ last_txn_us ≤ 3200
□ max_txn_us  ≤ 3500
□   —— 超过就说明整帧超时没生效，必须回传
```

**⚠️ 还要看周期有没有被拖长：** 敲 `s` 看 `uptime_ms`，
让它跑 60 s，`uptime_ms` 应该涨 60000 左右（±1%）。若涨得慢很多，说明周期被阻塞了。

### ✅ 本阶段的"未核实项"已关闭（2026-10-11）

```
早期状态：reference/ 里没有 JY901P 手册，所以 IMU 的寄存器映射是按

| # | 项 | 曾经的错 | 现在（已核实） |
|---|---|---|---|
| 1 | 器件 ID 寄存器 | 读 `0x00` | **`0x00` 是 SAVE（可写！）**；只读版本号在 **`0x2E`** |
| 2 | 角度换算 | `raw × 0.01°/LSB` | **`raw/32768 × 180°`**（原来的错了 1.83 倍） |
| 3 | ⭐ 字节序 | 按**大端**解析 | **实测是小端**（原来姿态全错、加速度模 15.6 g）|

**现在生效的映射**（`rlcat_config.h` §3b，全部已核实）：

```
RLCA_IMU_I2C_ADDR      0x50    7 位从机地址（手册 §IICADDR 默认 0x50）
RLCA_IMU_REG_VERSION   0x2E    VERSION，只读 16 位  ← 自检读这个，不校验固定值
RLCA_IMU_REG_ACC       0x34    AX/AY/AZ 各 16 位，连读 6 字节
RLCA_IMU_REG_GYRO      0x37    GX/GY/GZ 各 16 位，连读 6 字节
RLCA_IMU_REG_ANGLE     0x3D    Roll/Pitch/Yaw 各 16 位，连读 6 字节
RLCA_IMU_REG_QUAT      0x51    q0~q3（备用路径，模块已融合好）

⚠️ 字节序：【小端】（低字节在前）—— 手册没写，靠上机原始字节实测确定
⚠️ 量程：ACC ±16g、GYRO ±2000°/s、ANGLE 满量程 ±180°（与手册公式一致）
```

**⚠️ 两项必须在上位机设、固件改不了的：**

```
· 带宽   BANDWIDTH@0x1F = 2  （98Hz，上位机最高档）
· 回传速率 RRATE@0x03   = 9  （100Hz）
  ⚠️ 出厂默认 6 = 仅 10Hz，不改会让姿态观测呈阶梯状、策略会抖
  ⚠️ 面板里的"通讯速率"（4800）是【串口】波特率，I2C 用不到，不用改
```

**⭐ 排查姿态问题的正确姿势**：敲 `I` 看**原始字节**。
它会同时打印 `|BE:`（大端）与 `|LE:`（小端）两栏解释 ——
哪一栏数值合理，字节序就是哪种。只看换算后的数值区分不了
"地址错 / 字节序错 / 换算系数错"这三种病因。

#### ⚠️ 这一节的判据换过一轮（旧判据有两处是错的）

| 旧判据 | 为什么错 | 现在用什么 |
|---|---|---|
| `chip_id = 80`（0x50） | 固件原来读 `0x00` 当器件 ID，**而 0x00 是 SAVE**（可写，写它=重启/恢复出厂）。只读的版本号在 **`0x2E`**，且手册明说"不同产品版本号不一样" | 改看 **`I` 的 `VERSION (0x2E)`** 能否读到；**不校验固定值** |

#### ✅ 实测通过的证据（2026-10-11）

```
IICADDR   (0x1A) = 50 00  -> LE 0x50      ✅ 从机地址
RRATE     (0x03) = 09 00  -> LE 9 = 100Hz ✅
BANDWIDTH (0x1F) = 02 00  -> LE 2 = 98Hz  ✅
ORIENT    (0x23) = 00 00  -> 水平安装      ✅
AXIS6     (0x24) = 00 00  -> 九轴          ✅

ACC   小端 -> (0.42, 0.16, 0.91) g, |a| = 1.013 g      ✅ 静止应为 ~1g
ANGLE 小端 -> roll +13.0°, pitch -16.5°                 ✅ 合理小角度

交叉验证（两条独立路径，必须一致）:
  加速度计推出的重力 = (-0.417, -0.154, -0.896)
  欧拉角推出的重力   = (-0.284, -0.216, -0.934)
  点积 = +0.988  ->  夹角 8.7°                          ✅ 一致
```

**⚠️ 那 8.7° 是正常的传感器融合偏差**（模块用陀螺积分 + 加计滤波），
不是错误。判据是"两条独立路径方向一致"，不是"逐位相同"。

|---|---|---|
| `RSW = 0x0008` | 只开了 ANGLE 输出 | 不影响固件（固件直接读寄存器）。但**开着 ACC/GYRO（改回 0x001E）能让你用 USB-TTL 接模块串口独立复现读数**，便于交叉验证 |
| `M` 的 `version` 显示 0 | 而 `I` 每次都能读到 `05 C1` | 逻辑上应显示 0xC105。**待重烧固件后复看**；若仍为 0 需深挖 |

### P5-3 I2C 时序实测（有条件就做）

| 项 | 内容 |
|---|---|
| 测点 | PB8（SCL） |
| 动作 | 敲 `M`（会触发 I2C 访问） |
| 判据 | **SCL 频率 100 ~ 400 kHz** |
| 现状 | `BSP_I2C_HALF_US = 1` ⇒ 理论 ~500 kHz，实测受 GPIO/上拉会更低 |
| 调法 | 偏离区间时改 `firmware/stm32/Core/Inc/bsp_softi2c.h` 的 `BSP_I2C_HALF_US`（值越大越慢） |

**⚠️ IMU 读一帧的耗时预算（固件设计书 §5.4）：**
```
读 acc(6) + gyro(6) + angle(8) = 20 数据字节，
加地址/寄存器/ACK 开销约 12 字节等效：
  @ 400 kHz ≈ 0.72 ms   ← 目标
  @ 100 kHz ≈ 2.9 ms    ← 占 10 ms 周期的 29%，偏多
```
**周期耗时怎么量：** 敲 `s` 看…（P5 还没有直接的周期耗时输出）
**替代判据：** 观察 `S`（心跳）是否仍然稳定 1 Hz；若明显变慢，说明 IMU 读占了太多时间。

| 动作 | 万用表量 STM32 模块的 3.3 V 引脚（对 GND） |

**不达标时怎么调：**

```
若 V_fw 系统性偏低/偏高一点 → 微调 rlcat_config.h 的 RLCA_BATT_DIV_NUM

□ 3S 电池能提供 ≥25 A；舵机动力走 16 AWG 粗线
□ 手边能随时拔掉动力线
□ 做 P6-3 的电压项时，用可调直流电源而不是真电池（要拉到 9.3 V 以下）

### P6-1 模式状态机 ⭐（不产生运动，先做这个）

| 项 | 内容 |
|---|---|
| 动作 | 敲 `R` |
| 预期 | 打印 `mode_requested` / `mode_active` / `torque_on` / `active_block` / `safety_*` / `calib_*` |

**逐个模式试一遍：**

| 动作 | 预期（看 `R` 的 `mode_active` 与 `torque_on`） |
|---|---|
| 敲 `N idle` | `mode_active = 0`，`torque_on = 0`（**关节可以用手轻松转动**） |
| 敲 `N stand` | `mode_active = 1`，`torque_on = 1`（**关节变硬，保持在站姿**） |
| 敲 `N damp` | `mode_active = 3`，`torque_on = 0`（关节软下去） |
| 敲 `N active` | ⚠️ **现在应该进不去**：`mode_active` 会停在 `1`（STAND） |

**⭐ 最关键的一条：`active_block` 必须解释"为什么进不了 ACTIVE"**

```
0 = 通过          1 = 未标定          2 = 链路不活
3 = IMU 不可用    4 = 安全层禁止      5 = 舵机反馈不新鲜
```

| 现象 | 含义 | 处理 |
|---|---|---|
| `active_block = 1` | 没标定 | 做 P6-2 |
| `active_block = 2` | 树莓派没连着/没发指令 | 正常（PC 上没 Pi）。跑 `python pi/sim_esp32.py` 就会有链路 |
| `active_block = 3` | IMU 不可用 | 回到 P5-1/P5-2 |
| `active_block = 5` | 舵机反馈读不全 | 回到 P3-5，看 `ok_reads` 是否在涨 |

**⚠️ ACTIVE 的设计意图就是"条件不满足就降级到 STAND，而不是掉到 IDLE"。**
站着比瘫着安全，而且操作者一眼能看出"力矩还在"。

### P6-2 ⭐ 关节标定

#### 方式 A（推荐先用）：手动零点

| 项 | 内容 |
|---|---|
| 准备 | 敲 `N idle` 卸力矩，**用手把机器人摆成装配好的弯腿站姿**（与 URDF 的 q=0 一致） |
| 动作 | 扶稳后敲 `C zero` |
| 预期 | `manual zero recorded from current positions` |
| 再敲 | `R` 看 12 行的 `off=` 值 |

**判据：**
```
□ 12 个 off= 值各不相同（完全相同说明读的是同一个舵机 → ID 有冲突）
□ off= 值在 0~4095 之间
□ 重新上电后敲 R，flash_loaded = 1，off= 值不变 ← 证明落盘成功
```

**⚠️ `C zero` 只定 offset，`dir` 保持默认（全 +1）。**
接着做方式 B 才能把方向测出来。

#### 方式 B：全自动（测方向）

| 项 | 内容 |
|---|---|
| 准备 | 机器人架空；清场，**每个关节会动约 0.15 rad** |
| 动作 | 敲 `C start` |
| 预期 | `calibration started (~10 s)`；约 10 s 后敲 `R`，`calib_state = 8`（DONE）、`calib_err = 0` |
| 判据 | 见下 |

**标定状态码（`R` 里的 `calib_state`）：**
```
0 IDLE  1 UNLOAD  2 SETTLE  3 SAMPLE  4 DIR_TEST
5 DIR_SETTLE  6 FINAL_READ  7 VERIFY  8 DONE  9 FAILED
```

**失败码（`calib_err`）：**
```
0 无错   1 读位置失败   2 写位置失败
3 舵机没动（力矩没使能/机械卡死）   4 位移太小，方向判不出   5 结果超出合理范围
```

| `calib_err` | 含义与处理 |
|---|---|
| 1 | 读位置失败 → 回到 P3-5 看反馈是否稳定 |
| 3 | **舵机没动** → 力矩没使能（查 12V 动力、`T 1`）、或机械卡死 |
| 4 | 位移太小 → 该关节阻力大/被限位挡着；确认它是自由的 |
| 5 | 结果不合法 → 把 `R` 的输出贴回来 |

**⭐ 标定成功的判据：**

```
□ calib_state = 8（DONE）、calib_err = 0
□ R 的 12 行 dir= 与【物理现实】一致：
    用手把某个关节往正方向推（关节角增大），读 R 的 off= 应该
      · dir=+1 → off 增大
      · dir=-1 → off 减小
  ⚠️ 这是"dir 到底对不对"的唯一真判据 ——
     如果反了，机器人会朝指令的反方向走，非常危险。
□ 重新上电后 flash_loaded = 1，off/dir 都被保留
```

### P6-3 ⭐⭐ 安全触发逐项验证（本阶段最重要）

#### ① 链路失联 → 100 ms 后趴下 ⭐（核心要求）

|---|---|

| 判据 | 阈值精确（9.4 V 不该触发） |

#### ③ 电池 L2（≤9.9 V）→ 只限幅，不趴下

| 项 | 内容 |
|---|---|
| 动作 | 调到 9.9 V |
| 预期 | `severity = 2`、`amp_scale_x100 = 50`（限幅到 50%）、**不趴下** |
| 判据 | `sitdown_active = 0` |

#### ④ 电池 L1（≤10.5 V）→ 只告警

| 项 | 内容 |
|---|---|
| 动作 | 调到 10.5 V |
| 预期 | `severity = 1`、`amp_scale_x100 = 100`、不趴下 |
| 判据 | 见上 |

#### ⑤ 舵机过温（>70 °C）→ 强制趴下

| 项 | 内容 |
|---|---|
| 动作 | 把某个舵机加热到 70 °C 以上（**或**轻堵转 1~2 秒让它自己升温） |

|---|---|

| 预期 | `severity` 回到 0、`torque_on = 1`，机器人重新站起来 |
| 判据 | **不需要复位固件** |

### P6-4 ⭐ 缓慢趴下（不是"直接断电"）

### P6-5 安全链路自检（拔掉树莓派）
