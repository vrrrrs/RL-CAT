### 3.3 策略（已验证到"精确 0"）

**网络：** `47 → 256 → 128 → 64 → 12`，ELU，**54220 参数**，`action_scale = 0.25`。

**47 维观测布局（从仿真轨迹反解，不是猜的）：**

```
obs[t] = [
    gravity[t-1]        单位向量（机体系）
    base_w[t-1] * 0.25  陀螺
    cmd[t-1]    * 2.0   ⚠️ 指令也乘 lin_vel=2.0（最容易漏）
    q[t-1]      * 1.0
    qd[t-1]     * 0.1
    action[t-1]         上一帧动作
    phase[t]            (sin, cos)，**不平移**，步进 2π×0.03
]
```

**⚠️ 关键：状态段全部是 `t-1`（上一拍）** ⇒ 真机天然正确：读遥测 → 构造 obs → 推理 → 下发。

**⚠️⚠️ 关节顺序（最容易致命的一条）：**

```
训练侧（Isaac Gym 按 URDF 顺序）= leg-major：
    lf_hip, lf_thigh, lf_calf, lb_hip, lb_thigh, lb_calf, ...
协议 / 固件 / config.py          = group-major：
    lf_hip, lb_hip, rf_hip, rb_hip, lf_thigh, ...
```

**判据（用实机 URDF 限位衡量 1000 步仿真回放）：**

| 解释 | 总限位违反量 |
|---|---|
| group-major | **18384 度·步**（`rf_hip` 到 −36°，实机下限 0°） |
| **leg-major** | **544 度·步** ✅ |

**⇒ 少 34 倍 ⇒ 策略输出是 leg-major。已在 `rl_policy.py` 里做换算，调用者无需关心。**

**对拍结果：**

```
① obs 重建（44 维，六段）   全部 max|diff| = 0.000e+00
② 策略前向（重建 obs→action）相对误差 2.5e-07
③ q_target = 0.25*action      max|diff| = 0.000e+00
```

### 3.4 几何标定表（本次的关键简化）

**前提（项目负责人在机械上逐台确认）：标定姿态（腿伸直）下 12 个舵机编码器都读到 2048。**

**⇒ offset 可完全由常量算出，不读 flash、不需要标定流程：**

```
offset = 2048 − dir × q_calib × (4096/2π)
```

| 关节 | dir | q_calib | 几何表 offset | 逐台实测 | 差 |
|---|---|---|---|---|---|
| hip ×4 | ±1 | 0° | **2048** | 2026~2088 | 0.2~3.5° |
| lf/lb_thigh | +1 | 45°/40° | **1536 / 1593** | 1570 / 1562 | 3.0° / 2.7° |
| rf/rb_thigh | −1 | 45°/40° | **2560 / 2503** | 2545 / 2482 | 1.3° / 1.8° |
| lf/lb_calf | −1 | 90°/85° | **3072 / 3015** | 3002 / 2950 | 6.2° / 5.7° |
| rf/rb_calf | +1 | 90°/85° | **1024 / 1081** | 996 / 1039 | 2.5° / 3.7° |

**平均绝对偏差 2.78°。**

**⚠️⚠️ 关键点：`offset` 不是 2048，也不该是 2048。**
`offset` 是"**URDF 零位（弯腿站姿）**"的读数；2048 是"**标定姿态（伸直腿）**"的读数。
两者相差 `q_calib`（thigh 45°、calf 90°）。**直接用 2048 会让 thigh 偏 45°、calf 偏 90°。**

**⭐ 由它导出的强不变量（已写成单测）：**

```
step_to_q(2048) == q_calib     ← 与 dir 无关
```

## 4 · 踩过的坑（按类别，带根因与教训）

> **这一节是全篇最重要的部分。** 每个坑都标了「怎么发现的」——那决定了以后能不能早发现。

### A. 致命类（不修就摔 / 硬件损坏）

#### A1 · 关节顺序两套不一致 ⭐⭐⭐

| | |
|---|---|
| **现象** | 无（**尚未上机，纯靠分析发现**） |
| **根因** | Isaac Gym 的 dof 顺序由 **URDF 的 `<joint>` 出现顺序**决定（leg-major），而协议/固件用 group-major |
| **若未发现** | **每条 action 都发到错误关节 ⇒ 上机立刻摔** |
| **发现方式** | 用"实机 URDF 限位违反量"给两种解释打分：18384 vs 544 度·步 |
| **修法** | `rl_policy.py` 统一对外用协议顺序，内部用 `PERM_TRAIN_TO_PROTO` 换算 |
| **教训** | **逐元素对拍抓不到顺序错误**（对拍与顺序无关）。要用**物理合理性**（限位/运动学）校验 |

#### A2 · 循环内 `print` 阻塞控制循环 ⭐⭐⭐

| | |
|---|---|
| **现象** | 链路掉标、EST换闪烁；`pose.py` 出现"事件正反馈"（打印→延迟→更多降级→更多打印） |
| **根因** | `print` 到 SSH 管道是**阻塞**的，一次几十毫秒；期间不发帧 ⇒ 空档 ⇒ 降级 |
| **证据** | 同一台机器：`linkprobe.py`（不打印）丢帧 **0%**；`stand_test.py`（2 Hz 打印）**14.3%** 掉 ACTIVE。10 s ÷ 20 次 × ~70 ms ≈ 1.4 s = **14%**，精确吻合 |
| **修法** | 实时循环内**禁止**任何 `print`；进度只在结束时汇总 |
| **教训** | **同一个错误犯了 4 次**（`pose.py` → `status_panel` → `stand_test` → `rl_run`）。已加 `link.py` 的「发帧看门狗」自动报警 |

#### A3 · 只观察模式一帧不发

| | |
|---|---|
| **现象** | `stand_test.py --observe` 跑 0.5 s 就报"非 ACTIVE/ESTOP 持续 0.6 s" |
| **根因** | `if not args.observe: send(...)` —— 观察模式**完全不发帧** ⇒ 300 ms 后必失联 |
| **修法** | 观察模式也发帧，目标 = **当前实测姿态**（不动，但链路活着） |
| **教训** | **"不命令关节目标" ≠ "不发帧"**。这两个概念必须分清 |

### B. 标定 / 运动学类

#### B1 · 分压比错误导致"关节到不了目标角"

| | |
|---|---|
| **现象** | 目标 20° 只到 ~13.7°，关节**往复摆动**，保持 1 s 后下垂 7.34° |
| **根因** | 分压比写成 122/22（5.545），实际硬件是 100k/20k（**6.000**）⇒ 电压读低 **7.6%** ⇒ 长期落在 `VOLT_STOP` 区间 ⇒ 幅度被压到 50% |
| **修法** | 改分压比；并 `RLCA_BATT_LIMIT_EN = 0`（限幅只是性能调节，不该拿错误读数压幅度） |
| **教训** | **测量错误会伪装成控制错误。** 先确认"测量链对不对"，再查控制器 |

#### B2 · `q_range` 双乘 `dir` ⭐⭐

| | |
|---|---|
| **现象** | `lb_hip` / `rf_hip` 发**正角完全不动** |
| **根因** | `rlca_q_range()` 里 `limit * dir * k`，而 `limit` 本来就是用 `dir=1, offset=0` 算出的 **q 空间**量 ⇒ 对 `dir=−1` 的关节**再取反一次** ⇒ hip 范围从 [0°,40°] 变成 [−39°,0°] ⇒ 正角被夹成 0 |
| **波及** | **6 个关节**（`dir=−1` 的 lb_hip/rf_hip/rf_thigh/rb_thigh/lf_calf/lb_calf）；calf 因范围对称恰好看不出来 |
| **修法** | 去掉 `* dir` |
| **为何潜伏很久** | 已有测试只覆盖了"`dir=+1` 且范围不对称"和"`dir=−1` 但范围对称"——**恰好漏了 `dir=−1` × 不对称**这个组合 |
| **教训** | **测试要按组合矩阵设计，不能只挑几个代表。** 补的回归测试断言"限位与 dir 无关"，且**临时还原 bug 验证它真的会红** |

#### B3 · `servo_bus` 持有旧标定表副本

| | |
|---|---|
| **现象** | 标定后 `R` 显示 offset 正确，但上报的 `q` 仍是 ±3.14 rad（boot 时的零 offset 表），必须重启 |
| **根因** | `servo_bus_init` 里 `s_calib = *calib` 复制了一份，后续标定只改 `app_main` 的 `s_calib` |
| **修法** | `servo_bus_set_calib()` 热更新 + 三处调用点 + 回归测试 |

#### B4 · "概率变成未标定" ⭐⭐

| | |
|---|---|
| **现象** | 每次重启 STM32 有**概率**显示未标定 |
| **根因（三层）** | ① `s_calib_ok = bsp_flash_save_calib(...)` —— **落盘失败就判未标定**，落盘失败还是**静默**的<br>② 另一条路径 `s_calib_dirty` 忽略失败却直接置 `true` ⇒ 本次正常、**下次重启才暴露**<br>③ **`app_init` 末尾有一行无条件的 `s_calib_ok = bsp_flash_calib_loaded();`**，把前面所有判断**全部覆盖**<br>④ 烧写工具若用「全片擦除」，标定页（`0x0800FC00`）被擦掉 ⇒ 这才是"概率"的来源 |
| **修法** | 改用**几何标定表**（不读 flash）；删掉那行覆盖；`s_calib_ok` 只取决于"表是否合法" |
| **教训** | **"晚到的重复赋值"极难发现。** 一个变量只应该有一处权威设定 |

#### B5 · `q_calib` 必须取幅值

**现象的根因是"符号被应用了两次"（与 B2 同类）。已修，并写进注释作为规则：**
**凡同时带 `dir` 的两处换算，都要检查是否重复应用了符号。**

### C. 通信 / 链路类

#### C1 · shell 抢 USART1 接收 → 47% 丢帧（被误判为 EMI）

| | |
|---|---|
| **现象** | Pi → STM32 丢帧 47%，但**下行完美**（`cycle_lost = 0`） |
| **误判** | 一度认为是 EMI（因为"只有上行坏"很像干扰） |
| **真因** | `bsp_shell_poll()` 调 `sh_feed(&g_uart_pi, 0)`，把 `link_pi_poll()` 要解析的**同一个 RX 环**抽走了 |
| **决定性证据** | `rx_timeouts = 5134` **超过**实际发送的 2928 帧 ⇒ 不可能全是线路问题 |
| **修法** | `RLCA_SHELL_ON_PI_PORT = 0` ⇒ 2923/2923 帧，所有错误计数归零 |
| **教训** | **"上/下行不对称"不等于硬件问题。** 先找"谁还在读这个端口" |

#### C2 · `sh_puts` 阻塞 170 ms

**shell 输出期间 `link_pi_poll()` 被饿死 ⇒ LINK_OK 掉 ⇒ ACTIVE↔STAND 抖动。**
**修法：分 64 字节块写，块间 `link_pi_poll()` + `bsp_uart_poll_dma()`。**

#### C3 · 两个进程抢 `/dev/ttyAMA0`

**字节被静默瓜分（丢 28~50%，但 CRC 全 0）。修法：`link.py` 用 `flock` 独占。**

#### C4 · 波特率与 ORE

**500 kbps 下 USART1 走**单字节中断**，一个字节只有 20 µs，ISR 延迟就 ORE。**
**已实测：`rx_errors = 0` / `rx_ovf = 0` / `restarts = 0` / `bytes = 帧数 × 38` ⇒ **当前链路字节级完美**。**
**⚠️ 但若将来出现不明丢帧，应优先考虑把 USART1 改成 DMA（USART2 已用 DMA+IDLE）。**

### D. 安全层类

#### D1 · `SERVO_ERR` 含 BUS_TIMEOUT → 幅度被压到 0.75

**现象：目标 20° 变成 15°。根因：总线超时被当成"舵机自报错误"。**
**修法：`hard = flags & ~BUS_TIMEOUT`，只有真错误才限幅；2 s 自动清除让错误位闪烁，放大了这个 bug。**

#### D2 · **温度坏读数导致 7 次误急停** ⭐⭐（M1 阶段的最后一块石头）

| | |
|---|---|
| **现象** | 6% 的周期 ESTOP（卸力矩）；但姿态漂移 0.00° |
| **排除过程** | 链路：零丢帧、`seq_lost=0` ⇒ 排除<br>电压：11.8 V ⇒ 排除<br>舵机错：`servo_err=0` ⇒ 排除<br>**⇒ 只剩过温** |
| **决定性数据** | 分原因计数：`estop_cnt_temp = 7`、`estop_lvl0 = 7`（那 7 次链路完全正常）、`last_estop_temp_c = 30`、12 个舵机 28~32℃、阈值为 70℃ |
| **真因** | `servo_bus_max_temp()` 在某些周期返回 **>70 的坏值** |
| **修法** | ① `>125℃` 视为坏读数直接丢弃；② 需**连续 5 次（50 ms）越阈**才认（热惯性以秒计） |
| **结果** | `estop_cnt_temp: 7 → 0`；M1 通过 |
| **教训** | **别急着"放宽阈值"**——那会让真过温也失去保护。正确做法是**过滤坏数据 + 迟滞** |

#### D3 · 诊断数据必须聚合，不能只留"最后一条"

**我最初只保存"最近一次急停快照"，结果最后一次总是**工具退出后的长空档**（46 秒），
把前面 7 次的真凶**全部覆盖**，把我和用户都引向了"链路"这个错方向。**

**⇒ 改成**分原因计数**，一次就挖出来了。这条记在 §5。**

### E. 工具 / 流程类

| 坑 | 现象 | 教训 |
|---|---|---|
| **`pump()` 里 `return` 插错位置** | `run_checks exit=1`（一字节都不读） | **改完必须跑测试** —— 光读代码看不出来 |
| **`layers[1:]` 把输出层算进 hidden** | 网络结构错 ⇒ 唯一独立验证**静默跳过** | 验证函数**不能静默跳过**，必须返回 bool |
| **检查点选错（第 8 轮）** | 奖励 72.11 看着最好，其实 episode 891 = **在摔** | **平均奖励不能跨 episode 长度比较** |
| **`temperature` 是 12 元列表** | 工具崩溃（`int(list)`） | 遥测字段要先确认类型再写代码 |
| **PowerShell `\n` 字面量** | 写进 Python/C 源码造成语法错 | 单引号 here-string 里 `\n` **不转义** |

### F. 硬件直觉 vs 代码推理

**用户在三个问题上直接反驳了我，而**每一次都是用户对**：**

| 我的错误结论 | 用户的理由 | 结果 |
|---|---|---|
| "全设 2048 不行" | "我在机械上验证过，标定姿态就是 2048" | **用户对**：offset ≠ 2048，但可以用 2048 推导 |
| "是过温误触发"（第一次） | "舵机很凉，且有自带保护" | **用户对**：确实是坏读数，但**不是真的热** |
| "别关 ESTOP" vs "先做完成度" | 完成度优先 | **折中**：只放宽链路阈值，保留电池/过温 |

**⇒ 规则：用户对**硬件事实**的陈述优先于我的代码推理。我应该做的是"用代码去解释用户的现象"，而不是"用现象去迁就我的代码理解"。**

## 5 · 方法论（可复用的经验）

### 5.1 测量优先于推理

**这个项目里我犯的每一次"根因误判"，都是因为**用有限数据倒推**，而不是**在事件点记录证据**。**

| 反模式 | 正模式 |
|---|---|
| "四个来源都排除了 ⇒ 一定是第五个" | **在触发瞬间记录全部输入**（`app_estop_snapshot_t`） |
| 只留"最后一次"快照 | **分原因聚合计数** |
| 用 std 判抖动 | **std + 峰峰值**（2° 振幅的正弦 std 只有 1.41°，会误判为通过） |

### 5.2 测试要按组合矩阵设计

**`q_range` 的 bug 潜伏很久，就是因为测试刚好漏了 `dir=−1` × 不对称范围。**

**⇒ 新加的回归测试对 `{+1,−1} × {hip,thigh,calf} × 4 条腿` 全组合断言，**
**并**临时还原 bug 验证测试真的会红**——不会被测试的断言等于没做。**

### 5.3 实时循环的硬规则

> **≥50 Hz 的循环里禁止出现：`print` / `input` / 文件 I/O / 网络 I/O / flash 擦写。**
> **需要进度输出 → 独立线程 + 队列，或循环结束后汇总。**
> **只要串口开着，就必须持续发帧。"不命令目标" ≠ "不发帧"。**

**已加两道自动检测：**
- 固件：`poll_gap_max_us` + `POLL STARVED` 提示
- Pi：`link.py` 的**发帧看门狗**（300 ms 不发帧就警告）

### 5.4 顺序 / 符号 / 单位 —— 用物理合理性校验

**"逐元素对拍误差 0"只能证明**公式**对，不能证明**顺序**对。**

**⇒ 顺序类错误必须用**运动学/限位/对称性**去校验（本次用"限位违反量"）。**

### 5.5 安全功能的价值在于"该响时响"

**ESTOP 在零丢帧状态下卸了 12 次力矩 —— 那不是安全，是噪声。**
**但正确的修法不是关掉它，而是：**
- **放宽"体验类"判据**（链路空档：80/300 → 150/1200，开发期）
- **保住"硬件类"判据**（电池 ≤9300 mV、舵机 >70℃ 不动）
- **修掉"坏数据"**（温度过滤 + 迟滞）
